# The loop context

Part of the project's guidance for agents; the index is [`CLAUDE.md`](../../CLAUDE.md). Read this document before changing code in `backend/app/services/loop/`.

- **Folder:** `backend/app/services/loop/`
- **Responsibility:** Driving a sprint's tasks: the task worker (dispatch, prompt, execution, delivery, recording, review, closing), the review digest, the edit plan, board moves, carry-over, replicas, sprint control, close and archive, a person's run review, and the company bootstrap. It decides what happens next from the evidence; it never computes a verdict itself.
- **May import:** [contracts](contracts.md), [platform](platform.md), [tasks](tasks.md), [models](models.md), [evidence](evidence.md), [workspace](workspace.md), [tools](tools.md), [learning](learning.md), [planning](planning.md), [producers](producers.md) (`docs/architecture/contexts.json`, checked by `scripts/check_architecture.py`).
- **Modules:** `answers`, `board_moves`, `carry_over`, `company_service`, `console_host`, `delivery_checks`, `edit_plan`, `foundation_setup`, `replicas`, `review_digest`, `run_review`, `sprint_archive`, `sprint_close`, `sprint_control`, `task_routing`, `task_worker`, `wiki_close`, `worker/board_writes`, `worker/close`, `worker/deliver`, `worker/execute`, `worker/intake`, `worker/messages`, `worker/procedures_round`, `worker/prompt`, `worker/prompt_budget`, `worker/qa_review`, `worker/quality_gate`, `worker/record`, `worker/related`, `worker/review`, `worker/sprint_notes`, `worker/task_run`, `worker/wiki_section`.

## Components

### Reviews of a run

**`backend/app/services/loop/run_review.py`** / **`routers/reviews.py`** — Reviews as on a pull request: `ReviewComment` (a line of a changed file, new or old side, or the run) and `RunReview` (`comment`, `approve`, `request_changes`, with its `outcome`). A Manager writes them, a Viewer reads them. A submitted review carries the open comments; on a task-worker run it acts only where the loop waits for a person (`request_changes` sends a task `waits_for_a_person` back to `todo` with a send-back note and one `NEEDS WORK:` comment listing `path:line: comment`, which `board.pending_rework_feedback` hands to the Developer; `approve` accepts an `awaits_risk_acceptance` hold), and anything else is a 409 with the reason; on another producer's run it records an `AgentRunApproval` (`record_approval`, shared with `POST /approve`). Audited as `run_review_<event>` (with `user_id` and `via`: `web`, or `slack`/`teams` when the decision came from chat through `routers/chat_interactions.py`, [integrations](integrations.md#approvals-in-slack-and-teams)); never evidence. The Files changed tab's line threads and form are `components/LineComments.tsx`, the review form and history `components/ReviewPanel.tsx`.

### The company bootstrap and its foundation sprint

**`backend/app/services/loop/company_service.py`** / **`foundation_setup.py`** / **`routers/enterprise.py`** — `POST /v1/init_company` creates the company, its agents, its credentials and its project row, and plans "Sprint 0 — Foundations" (`services/planning/sprint_planner.py`) — unless the sprint is not wanted (retrospective F8, `test_foundation_sprint.py`). The request's `foundation_sprint` asks for it (`true`) or declines it (`false`); `null` (the default) leaves the decision to the workspace daemon's observation of the folder: `foundation_setup.observe_folder` sends the one `workspace.inspect` (with its file snapshot) whose `project` the route also hands to `git_setup.is_repository`, and a folder observed to be a repository whose files include source code (`planning.stack_detection.has_code_files`) gets no sprint. The observation is the daemon's, never a claim in the request (`detected_stack` decides nothing); an unobserved folder — no daemon answered, no folder was named, or an answer without a snapshot — keeps the old behaviour and the sprint is planned. `foundation_setup.decide` returns what the response carries as `foundation_sprint`: `planned`, the `reason` (`requested`, `declined`, `repository_with_code`, `folder_without_code`, `no_folder`, `daemon_unobserved`), its `detail` sentence, and `observed_repository_with_code` — the observation itself (`null` without one), apart from the decision. With no sprint the summary's `sprint_id` is `null`, and the New company wizard lands on the sprint list saying why (`companyNew.foundationOutcome`).

### Sprint control and autonomy

**`backend/app/services/loop/sprint_control.py`** / **`routers/sprint_control.py`** — Who decides when a sprint's agents work. A sprint runs only while `active` (or `needs_split`); `planned` (Sprint 0 left unstarted by the New company wizard, `start_now: false` on `POST /v1/init_company`, always at autonomy 1), `paused` and `cancelled` are halted: the worker neither dispatches, reviews nor retries their tasks (`is_halted`). `POST /v1/sprints/{id}/start` starts a planned sprint, `/pause` and `/resume` pause it (resume dispatches its waiting tasks), `/stop` cancels it for good (unfinished tasks blocked with a note, no follow-up), `/dispatch` re-queues `todo` tasks of a running sprint; all Manager. When a provider refuses a call for lack of credit (402, or a 429 that names a quota or balance; `credit_failure`), the worker pauses the sprint with `pause_reason` and puts the task back to `todo` instead of blocking it, so resuming runs it again and a sprint of failures cannot loop into follow-ups; a company with a planned or paused sprint gets no follow-up on its own. `GET`/`PUT /v1/companies/{id}/autonomy` reads (Viewer) or changes (Manager) the autonomy level: at 1 every task QA approves waits for a person like a high-risk delivery (`HUMAN_LED_REASON` in the hold note), at 2 only high-risk ones, at 3 follow-ups and procedures also run on the company's own. The Sprint page shows a banner on every tab for a planned or paused sprint (Start / Resume, the reason) and the Board tab's controls (`components/SprintControls.tsx`): Dispatch, Pause, Stop, Autonomy.

### Moves on the board

**Moves on the board** (`services/loop/board_moves.py`, `services/loop/sprint_close.py`, `routers/board_moves.py`): a Manager moving a card to To do from another column (`PATCH /v1/backlog/{id}`) starts it. Without a comment of the person's the move is recorded as a send-back (`Sent back to work by a person (moved to To do on the board).`, so the rework budgets restart); a `completed` sprint (closed once every task settled) or a `cancelled` one is reopened to `active` with a conditional update from the status read, audited as `sprint_reopened` under `sprint:<id>:admin` with `from_status` and the task; an archived sprint is a 409; a `planned` or `paused` one is not started and the answer says why; a task whose dependencies are done gets its `task.assign` outbox event at once (the review cycle's second assignment loses `replicas.claim_todo`). The answer adds `queued`, `reopened`, `sprint_status` and `reason`, and the board shows them. A reopened sprint closes again when it settles, but what a sprint does once happened at its first close: a close after a reopening from `completed` (`board_moves.closed_before`) answers `reclosed_after_reopen` and opens no follow-up, posts no retrospective, measures and proposes no procedures and writes no engram; the integration of its branches runs again (it only moves forward). A sprint reopened from `cancelled` never closed, so its first close is a full one. "Move to sprint…" on a blocked or To do card (`components/MoveToSprint.tsx`, `services/boardMoves.ts`; Managers only) lists the company's open sprints (`GET /v1/backlog/{id}/carry_targets`, Viewer: planned, active, paused or needing a split, not archived, not its own) and a new sprint, and `POST /v1/backlog/{id}/carry_over` (Manager, `{target_sprint_id}`; none creates an active sprint `Carried from <name>`) carries it through `carry_over.carry_over`: once per task (409 after), only a task blocked for a person (a To do task is first blocked by the System with a `manual triage` note saying a person moved it), into an open sprint of the company with room under `SCOPE_HARD_MAX` (404 another company's, 409 archived or not open), queued when that sprint runs.

### Editing and removing a sprint

**`routers/sprint_crud.py`** / **`services/loop/sprint_archive.py`** — Editing and removing a sprint. `PATCH /v1/sprints/{id}` (Manager) edits `sprint_name`, `goal` (empty clears it) and `duration_days` (1–90), nothing else (status, company and tasks are 422), and refuses an archived sprint (409); audited as `sprint_updated` with each field's before and after. `DELETE /v1/sprints/{id}` (Owner; an API token, at most a Manager, cannot, nor the Manager agent: `delete_sprint` is in `manager_policy.ALWAYS_ESCALATE`) takes only a halted sprint, `planned`, `cancelled` or `completed` (`active`, `needs_split` and `paused` are a 409: stop it first). A sprint without evidence is deleted with its backlog items, their bookkeeping events (the System's dependency notes and the block a stop writes), their run secrets and the outbox rows queued for them (`{"deleted": true, "removed": {...}}`, audited as `sprint_deleted`, naming the sprint by id in JSON only). Evidence (`evidence_of`) is any AgentRun of the company for one of its tasks (`task-<id>`) or naming it in `subject.sprint_id`, any other TaskEvent, an AgentMessage, a SprintIntegration, a sprint progress snapshot (issue #531, [tasks](tasks.md)), a Procedure proposed from it or measured after it, a ManagerDecision on one of its tasks, an audit row of the company about it or its tasks other than its own administration rows (`sprint:<id>:admin`), or a `performance_metrics` row; with any, the sprint is archived instead (`archived_at`, `archived_by`, `archive_reason`, migration `0017`; `{"archived": true, "archived_at": ..., "evidence": [...]}`, audited as `sprint_archived`). An archived sprint leaves `GET /v1/sprints` (unless `include_archived=true`), the inbox (blocked tasks, risk holds, integrations), the Manager agent's items, the integration retries and carry-over (a 409); its board, runs, events and audit rows stay readable by id and the audit chain is never touched. `POST /v1/sprints/{id}/unarchive` (Owner) brings it back (`sprint_unarchived`). The Sprints page (`components/SprintAdminActions.tsx`, `services/sprintAdmin.ts`) offers Edit to a Manager, Delete (with the confirmation that a sprint with recorded work is archived) and Unarchive to an Owner, and a toggle to show archived sprints; a Viewer sees no action.

### The weight of a prompt

**`backend/app/services/loop/worker/prompt_budget.py`** (#443) — The Developer's task prompt (`worker/execute._developer_prompt`) is a list of named sections, in the order the prefix cache relies on: `output_format`, `standards_and_procedures`, `lessons`, `task`, `requirements`, `repository`, `related_code`, `wiki`, `memory`, `previous_attempt`, `completed_tasks`, `sprint_board`, `console_assistant_notes`, `architect_brief`, `review_feedback`. `fit` joins them and measures each (characters and estimated tokens, characters / 4 rounded up; the provider's tokenizer is not here and the proxy reports only the total). With a budget (`PROMPT_BUDGET_<ROLE>`, else `PROMPT_BUDGET`, in estimated tokens; `docs/CONFIGURATION.md`) an over-budget prompt loses whole sections from the highest priority number down (console notes 6; memory and completed tasks 5; lessons, the wiki and the sprint board 4; repository and related code 3; requirements, standards and previous attempt 2), the later one first among equals, and ends with `## Left out of this prompt` naming them so the model reads them through its tools; priority 0 (format, task, brief, review feedback) is never cut. The measure (`budget`, `tokens`, `chars`, `system_tokens`, `sections` with `cut`, `cut`) goes on the run's evidence as `prompt_sections` (`worker/record`), an observation of the backend's own; without a budget nothing is cut and the prompt is the same text as before. Studied: Aider's map token budget and OpenHands' condenser; no code taken.

### The related code's seeds

**`backend/app/services/loop/worker/related.py`** (#438) — Where a task's `## Related code` section starts (`services/tools/code_graph.py`, [tools](tools.md)): the `path` of every module of the approved architecture (`planning.arch_author.approved_for`) that covers one of the task's requirements (`spec_planning.covers_of`; a criterion `REQ-1.2` names `REQ-1` too), then the files the daemon reports the task's own earlier runs wrote (`evidence.touched.written_by_task`), at most 50. `related_code_section` builds it for a role with the workspace tools while the daemon is reachable, in the task's tool root (`developer_tools.tool_root`), and `_developer_prompt` adds it as the `related_code` section (priority 3) right after `repository`; with no seeds, `CODE_GRAPH_MAX_CHARS` at `0` or no daemon it is empty, `fit` skips it and the prompt and its measure are what they were before.

### The model by difficulty

**`backend/app/services/loop/task_routing.py`** (#319) — Before each Developer attempt `worker/execute._execute_task` calls `route_task`: it reads the task's plan and board (the approved architecture's modules and paths for its criteria via `planning.arch_author`, its `depends_on`, the `delivered` events so far, the `NEEDS WORK:` requests and a person's send-backs), estimates the difficulty (`models.difficulty`), reads the company's routing policy else the deployment's (`models.routing_policy.effective`) and lets `models.model_routing.route` choose. It stores the estimate and the routing on the task as an `estimated` event (actor `system`, no comment) and returns them; the worker keeps them on the agent so `worker/record` puts them on the run's evidence as `difficulty` and `routing`, beside `AgentRun.model`, the model the proxy reported. Any failure falls back to the deployment's routing with no event; no policy, the role default ([models](models.md)).
### The sprint board in the worker

**`backend/app/services/loop/worker/wiki_section.py`** / **`backend/app/services/loop/wiki_close.py`** (#445, [design](../design/PROJECT_WIKI.md)) — `wiki_section.section` is the `wiki` section of every Developer-path prompt, priority 4, before the vector memory: the company's pages in force (never `stale` or `proposed`) for the task's modules (by name, or by the module's path holding a file the task touches, `sprint_notes.task_scope`) and the concept pages linking its files or requirements, then the decisions and the glossary, within `WIKI_MAX_CHARS`, with control-looking lines quoted (`wiki.for_prompt`). `task_run._gather_context` asks `wiki_then_memory` instead of the vector memory: the engram search runs only when no module or concept page applies. `wiki_close.after_close` runs at a first sprint close, after the procedures round: it gathers the structured inputs (verified runs and their files from `evidence.touched.verified_writes`, the retrospective, the board's active notes, the approved architecture, the requirements), compiles (`learning.wiki_compile`), lints every page (`lint_company`: the evidence, and the daemon's `workspace.hash` of cited files without the Git workflow), optionally writes the compiled pages to `docs/wiki/` through `workspace.generate` (on `fabrique/wiki` with the workflow), and audits `wiki_compiled` / `wiki_written_to_repo`; it never raises.

**`backend/app/services/loop/worker/sprint_notes.py`** (#439, [design](../design/SPRINT_BOARD.md)) — After a delivery is recorded, `record_from_delivery` (called from `deliver._deliver_artifacts`) writes the deliverable's `NOTE … END` blocks as notes of the sprint (`services/tasks/sprint_board.add`) with the role, name, task and run, records the blocks that were not notes with their reason, drops a `supersedes` that names no active note while the note stands, and skips a note the task already left word for word; a failure never stops the delivery. `board_section` is the `sprint_board` section of every task prompt, priority 4: the sprint's active notes relevant to the task (`task_scope`: files named in the task, its modules' paths and earlier writes from `related.seeds_for`, its modules' ids and names, its requirements; `board_notes.relevance`), matched before sprint-wide, newest first, within `SPRINT_BOARD_MAX_CHARS`, then the format. Beside each file a note names, `with_observations` puts the latest verified run that wrote it (`evidence.touched.verified_writers`) in `observed`, a field apart from the claim.

### Acceptance tests on a task branch, and the verification an event names

**`backend/app/services/loop/delivery_checks.py`** (`guard_test_files`) / **`backend/app/services/loop/worker/board_writes.py`** (#329 retrospective) — Under the Git workflow a delivery's `acceptance` (read after the daemon's `git` answer, `deliver._deliver_artifacts` passing it to `evidence.acceptance.evidence_for`) holds the test files of the task branch's lineage in `test_hashes` and the sprint's other test files in `other_test_hashes`. The guard asks the daemon's `workspace.hash` for both: a sibling's file reported `present` (its base holds it) joins the guarded files, one that is not goes to `acceptance.not_on_branch` and is neither restored nor run, so a task is never refuted for a test written on a sibling branch; the sprint's integration (`release/integration.py`) still runs the whole suite. `board_writes` adds to every `verified` event that names a run the run's latest `Verification`, as `verification_id` and `payload.verification` (`{id, verdict}`), which the documentation pack joins on.
