# The tools context

Part of the project's guidance for agents; the index is [`CLAUDE.md`](../../CLAUDE.md). Read this document before changing code in `backend/app/services/tools/`.

- **Folder:** `backend/app/services/tools/`
- **Responsibility:** What a model may call during a task: the bounded tool loop, MCP servers and their configuration, the Developer's workspace tools and their replies, the checked edits and the lint after an edit, the repository map and the related code, the research tools and the compressed history. Each call is recorded as an observation; the tools never decide a verdict.
- **May import:** [contracts](contracts.md), [platform](platform.md), [evidence](evidence.md), [workspace](workspace.md) (`docs/architecture/contexts.json`, checked by `scripts/check_architecture.py`).
- **Interface** (`public` in `docs/architecture/contexts.json`, ADR 0018, checked by `scripts/check_architecture.py`): `code_graph`, `developer_tools`, `mcp_tools`, `registry_lookup`, `research_tools`, `signature_lookup`, `workspace_edits`. Another context imports only these modules and the package; the rest are internal.
- **Modules:** `code_graph`, `developer_tool_replies`, `developer_tool_schemas`, `developer_tools`, `edit_lint`, `mcp_client`, `mcp_config`, `mcp_tools`, `registry_lookup`, `repo_map`, `research_http`, `research_registries`, `research_schemas`, `research_tools`, `signature_lookup`, `tool_history`, `workspace_edits`.
- **HTTP adapters** (`http_adapters` in `docs/architecture/contexts.json`, checked by `scripts/check_architecture.py`, issue #511): `mcp_client` (the MCP transports) and `research_http` (`default_http`, raising `ResearchFetchError`, a `ResearchError`; `research_tools` re-exports it). Only these modules of the context may import an HTTP library; each returns data and raises named errors, and the rest of the context calls it.

## Components

### MCP tools

**`backend/app/services/tools/mcp_tools.py`** / **`mcp_config.py`** / **`mcp_client.py`** / **`routers/mcp.py`** — MCP (Model Context Protocol) tools for the task worker's producers. A Manager configures a company's servers with the standard `mcpServers` map (`POST /v1/mcp/servers`: `command`/`args` for stdio, `url` for streamable HTTP or SSE, `env`/`headers` as secrets, optional `roles`); `McpServer` rows keep the secrets Fernet-encrypted and the API lists only their names (`GET /v1/mcp/servers`, Viewer; `PATCH`/`DELETE`, Manager; `GET /v1/mcp/servers/{id}/tools` connects now and lists what the server advertises). The worker loads the role's `Toolbox` (`mcp_tools.Toolbox.load`), offers the tools to the model as `<server>__<tool>` in the OpenAI `tools` shape (the proxy passes them to every provider; `llm-proxy/gemini.py` translates them for Gemini) and runs the bounded loop (`chat_with_tools`): at most `MCP_MAX_TOOL_ROUNDS` rounds, then one request without tools, so a task always ends in a deliverable. Each call is an observation the backend made (server, tool, arguments, error, duration, sha256 of the result) kept on the Verifier's evidence as `tool_calls` and shown as the `tools_used` check; the model's reading of a result is a claim. Results are masked for the server's own secrets and cut at `MCP_RESULT_MAX_CHARS`; a tool without a read-only annotation raises the delivery's risk tier to at least `medium` (`risk.raise_for_tool_calls`). A server that cannot be reached is named in the toolbox's `unavailable` and the task goes on without it. stdio servers run inside the backend container, so their runtime (`npx`, `uvx`, …) must be in that image; remote servers need only a URL. Built on the official `mcp` package.

### The research tools

**`backend/app/services/tools/research_tools.py`** / **`research_registries.py`** / **`research_schemas.py`** — The research tools, offered in the same loop to the roles that decide (`RESEARCH_ROLES`; `offered_to`): `research__fetch` (one page as text, `html_to_text`, from a host on the list: the defaults `DEFAULT_HOSTS`, `RESEARCH_ALLOWED_HOSTS` and `Company.research_hosts`, `allowed_hosts`; https only unless the host was named explicitly; a redirect is followed only while it stays allowed; no credential; cut at `RESEARCH_FETCH_MAX_BYTES`), `research__package` (`research_registries.package_record`: PyPI, npm, crates.io, the Go proxy) and `research__advisories` (OSV, `advisory_rows`). `ResearchToolbox` has the `mcp_tools.Toolbox` shape; `toolbox_for` builds it for a task (the worker's `developer_tools.toolbox_for` combines it with the workspace and MCP toolboxes, `CombinedToolbox` taking any built-in boxes; `research` is a reserved server name) and `toolbox_for_request` for a draft (`spec_author.ask_with_tools` runs `chat_with_tools`; `prepare` puts the company's hosts and the `## Sources` prompt section, `prompt_section`, into the request). Every call is an observation (`url`, `host`, `allowed`, `fetched_at`, `status`, `sha256`, `bytes`, package and ecosystem); `sources_of` keeps those fields on `Specification.sources` and `Architecture.sources`, and `check_sources` is the Verifier's `sources` check (the sources, the refusals, and the dependencies the delivery's manifests name without a registry lookup, `packages_in`), present when tools were offered. `GET`/`PUT /v1/companies/{id}/research` (`routers/sprint_control.py`, Viewer / Manager) read and replace the company's hosts (`valid_host`). The frontend shows a draft's sources (`components/SourcesConsulted.tsx`). A web search is an MCP server the company configures.

### The delivery-time registry answers

**`backend/app/services/tools/registry_lookup.py`** — The registry answers the Verifier's `grounded` check reads (`services/evidence/grounding.py`). When a delivery writes a manifest, `observe` takes each dependency it named that no answer covers yet, asks its registry through `ResearchToolbox.lookup_package` (`research_registries.package_record` with the exact version) and appends the observation to the evidence's `registry_lookups`: package, ecosystem, version, `exists` (`false` only on a 404, `null` when it could not be asked), `requested_exists` (never claimed for the Go proxy, which answered `@latest`), `versions_complete`, latest, and the fetch's URL, status and sha256. It is bounded by `GROUNDING_MAX_LOOKUPS` and off with `GROUNDING_LOOKUPS_ENABLED`; a package the run already looked up through `research__package` is not asked again. `sources.check_sources` counts these rows as answered.

**`backend/app/services/tools/signature_lookup.py`** — The signatures the `grounded` check compares calls with (`services/evidence/signatures.py`). After a delivery is written, `observe` reads the delivered Python files' calls (`signatures.wanted`: the names imported from project files the delivery did not write whole, within the daemon's bounds, `capped` when cut) and asks `workspace.signatures` in the folder the files went to (the task's worktree with the Git workflow), within `TIMEOUT_SECONDS` (10). The reply goes on the evidence as `signatures` (`asked`, `files` with each file's sha256), or `observed: false` with the reason: the delivery was not written, no daemon answers the subject (an older daemon), a timeout or a refusal. It never fails or holds the delivery, and re-verification reads the record without asking again.

### The Developer's workspace tools

**`backend/app/services/tools/developer_tools.py`** — The Developer's workspace tools, offered beside the MCP tools in the same loop to the roles that deliver files (`TOOL_ROLES`, `roles.FILE_ROLES`: the Developer roles, QA and the Designer) when the company's project path is known: `workspace__list`, `workspace__read`, `workspace__search`, `workspace__find_file` (the daemon's `workspace.list` / `read` / `search` / `find`, `vscode-daemon/workspace_read.py`, bounded and never outside the project), `workspace__edit` (below) and `workspace__run_tests` (`workspace.execute` with the project's detected test command, or a narrower one that starts with the same runner; offered only with `DELIVERY_TESTS_ENABLED`). `toolbox_for` replaces `mcp_tools.Toolbox.load` in the worker and returns a `CombinedToolbox` that dispatches by the built-in tools' exact names (the server name `workspace` is reserved in `mcp_config`); `tool_root` points the tools at the task's worktree once it delivered there (Git workflow), else the project; `bind` gives the module the worker's NATS client and loop, since the LLM call runs in a thread (`_request_from_thread`). `repository_section` puts the top two levels of the tree and the repository map into the task prompt (`## Repository`, below). Each call is an observation like an MCP call (`read_only: true`); a read also carries the file's `path`, `sha256` and `bytes` as the daemon read them, and `services/evidence/context_read.py` holds the evidence side: `check_context_read` is the Verifier's `context_read` check (which of the files the delivery modified, the daemon's `change == "modified"`, were read first and which were not; `workspace_tools_used` says the tools were in use at all, a listing or a failed read included), `redact_secrets` keeps a secret-looking line (`standards.secrets_in`, which also reads a typed assignment such as `password: str = "…"`, and `standards.secret_line`, which fails closed at the prompt: a secret-looking name, then `=` or `:`, then anywhere later on the line a quoted run of 8 or more characters without a space that is no placeholder, unless the line reads the environment; never used for a verdict) out of what the model is shown; `risk.raise_for_unread_changes` raises the tier to `medium` for a modified file never read while the tools were in use. The tool schemas live in `services/tools/developer_tool_schemas.py`. The daemon never opens a file that may hold secrets (`workspace_read.SENSITIVE_NAMES`, `SENSITIVE_DIRS`) or a symlink that leads out of the project, hashes a file in chunks and indexes only its first `READ_SCAN_BYTES`, and runs a search in a child process killed at `SEARCH_TIMEOUT_SECONDS`. Settings: `DEVELOPER_TOOLS_ENABLED`, `DEVELOPER_TOOL_ROUNDS`, `REPO_MAP_MAX_CHARS`, `EDIT_LINT_ENABLED`, `EDIT_LINT_TIMEOUT_SECONDS`, `TOOL_HISTORY_KEEP_ROUNDS` (forwarded by `docker-compose.yml`).

### Reads, searches and checked edits

From SWE-agent's agent-computer interface (MIT, issue #359; `services/tools/developer_tool_replies.py` writes what the model sees): a read is a window of `READ_MAX_LINES` (100) numbered lines headed `[path: lines X–Y of N]`, with the `start_line` to page on or go back, cut at whole lines to the toolbox's result budget before the range is stated; a search over `SEARCH_MAX_MATCHES` answers how many matches there are and the count per file (`match_count`, `per_file`) and asks to refine instead of cutting silently, and `workspace__find_file` (a name or glob, `FIND_MAX_RESULTS`) does the same; an empty answer says so (`(the command finished with no output)`, `No line matches …`, an empty file or folder). **`workspace__edit`** (`services/tools/workspace_edits.py`, daemon `vscode-daemon/workspace_edit.py`) replaces a line range or one SEARCH/REPLACE block of an existing file, and the daemon applies it only if the file still parses (`compile`, `json`, `node --check` on a copy outside the project when `node` is on PATH, and a check that cannot complete refuses; other types unchecked, and the reply says so), else refuses with the error and the file untouched; never outside the project, into VCS metadata (`_resolve_target_path`) or a file that may hold secrets, at most `EDIT_MAX_BYTES` per file and `EDIT_MAX_FILES` per task, only the file types a delivery writes. It is offered only where the task's files may be touched (`workspace_edits.allowed`): the task's own worktree, or a project without the Git workflow, never the person's checkout of a company that delivers on branches. Each applied edit is an observation (`path`, `sha256_before`, `sha256_after`, `checked`; `read_only: false`, which `risk.raise_for_tool_calls` leaves to the delivery's paths). The edits are a working copy: the first edit of a file keeps its original under `FABRIQUE_EDIT_STATE` (daemon side, default `~/.fabrique-daemon/edits`), later reads and test runs see the edit, and when the tool loop ends `WorkspaceToolbox.close` asks `workspace.edit.finish`, which answers with each edited file's final text and puts the original back; it reads and restores a file only while its path still leads to it (`_saved_target`: inside the project, no VCS metadata, no symlink along the way, not a secret) and it holds the bytes the session last wrote (`sha256_written`, also checked before a later edit), and otherwise leaves the file as it is, keeps its original in the journal and reports it (`error`, `conflict`), never delivered. The worker delivers the texts beside the answer's files (`with_tool_edits`, `source: workspace_edit`; a file the answer delivers itself keeps its block), so the daemon's diff, the commit and the Verifier see them as any delivery's; `observe_tools` keeps them on the evidence as `tool_edit_files` (and the reports as `tool_edit_conflicts`), apart from the claims, where the `standards` check scans them with the answer's files (on re-verification too), `acceptance.test_sources_of` restores QA's tests from them and the minimum-deliverable gate counts them; `claimed_files_present` does not look for them in the answer's text (`context_read.files_edited`). An edit never delivered never stays on disk.

### Lint after an edit

**Lint after an edit** (`services/tools/edit_lint.py`, after Aider's lint-and-fix and SWE-agent's linting edits, ideas only): once the daemon has applied an edit, the stack profile's `lint` command (`stack_profiles`, the company's override first, read once per toolbox by `load_profile`) runs through `workspace.execute` in the company's sandbox, under the daemon's command policy, bounded by `EDIT_LINT_TIMEOUT_SECONDS`; a command ending in ` .` is narrowed to the edited file, another runs as named and only what it says from the file's first mention on is shown; the result leads the edit's own text so the model fixes it in the same turn. Only the stack's own file types are linted; a linter that is not installed (exit 127, "command not found", "No module named"), a refusal, a timeout or a project with no lint command (the syntax check is then the only one) is said as such. The lint never writes: a command naming an autofix or write option (`--fix`, `--write`, `-w`, `rubocop -a`, `ruff format`, `cargo fix`, `dotnet format` without `--verify-no-changes`…), or `npm run lint` whose package script names one (the node profile keeps it, with the `prelint` and `postlint` scripts npm runs around it, as `lint_script`), is not run and the result says why (`writes_files`: the command is split into its simple commands on `&&`, `||`, `;`, `|` and line breaks and each is judged on its own words with the shell's quotes removed, so `ruff check '--fix' .` and `black --check . && isort .` are refused; a substitution, a backtick, a here-document, `eval`, a nested `sh -c` or a shell comment (a `#` starting a word outside quotes: `black . # --check`) is refused as unreadable), since a file it rewrote would sit outside the edit's working copy; a dry run is fine. What the linter printed is shown with secret-looking lines redacted (`context_read.redact_secrets`) before it is cut. The run is part of the edit's observation (`lint`: command, `narrowed`, exit status, `available`, sha256 of the output as printed), never a verdict.

### The repository map

**The repository map** (`services/tools/repo_map.py`, daemon `vscode-daemon/repo_map.py`; the idea is Aider's repository map, Apache-2.0, no code taken): `workspace.map` walks the project or the task's worktree (the folders a listing skips, hidden files, files that may hold secrets, symlinks out of the project and anything but a regular file (a FIFO named `x.py`) never opened; at most `MAP_MAX_FILES` files of `MAP_MAX_FILE_BYTES`, `MAP_MAX_TOTAL_BYTES` in all, `MAP_DEADLINE_SECONDS` of parsing, past which it says `partial`) and reads definitions with the standard library only, so the daemon keeps `nats-py` as its one dependency: `ast` for Python (top-level classes and functions and the methods of top-level classes, with signatures; references by name, the language's own names left out), a conservative line extractor for JavaScript and TypeScript (function, class, interface, type, enum and top-level or exported arrow declarations, methods of a class). A deterministic PageRank over the files that refer to each other's definitions ranks them (a private name, one defined in many files or a test file's counts less, a long compound name more); a name defined in more than `MAP_MAX_DEFINERS` (20) files gives no edges, and the ranking stops at the parsing's deadline (`partial`); the best fit the budget (`REPO_MAP_MAX_CHARS`), grouped by file with their line numbers and how many files use each. A Python parameter whose name looks like a secret has its default replaced by `"[redacted]"` in the syntax tree before the signature is written (an f-string or an annotation holding commas included), a string literal bound to a secret-looking name in a JavaScript or TypeScript signature (`password="…"`, `apiKey: string = "…"`) and a value shaped like a known token are replaced the same way before the signature is clipped or cached, and the JavaScript references are read with string, template and comment contents removed, so a literal never becomes a cached reference; failing closed, a file with a template literal nested in another's `${…}`, an unclosed comment or a quote left unbalanced keeps its definitions and records no references (`refs_skipped`, listed in the reply's `files_without_refs`), and the backend redacts the map again at the prompt (`context_read.redact_secrets`). It is cached under `FABRIQUE_MAP_STATE` (versioned by `MAP_VERSION`, 4, so an older cache is discarded) keyed by the files' sha256 set and the budget, each file's parse by its sha256, so a changed file is parsed again alone. The backend puts it beside the tree in the Developer's and QA's task prompts, the Architect's consultation brief and the Architect's draft of an architecture (`fetch_section`, through the backend's NATS); a daemon without `workspace.map` leaves the tree alone. Context, never evidence.

### The related code

**The related code** (`services/tools/code_graph.py`, daemon `vscode-daemon/code_graph.py`, issue #438, first slice): `related_section` asks the daemon's `workspace.related` for the files around a task's seeds (`services/loop/worker/related.py`: the paths of the approved-architecture modules its requirements map to, and the files its earlier runs wrote), one hop in both directions, at most `MAX_FILES` (30), within `TIMEOUT_SECONDS` (10), and renders `## Related code`: the starting files, what they use and what uses them (the files a change could break), each `path: names` with the names that tie them, and `### Recent runs that touched these files` from `services/evidence/touched.runs_touching` (task title, verdict, the files written; a refuted run marked `REFUTED`). The daemon computes the graph on demand from the repository map's candidates, guards and parse cache, with `repo_map.reference_edges`, the map's own edge rule (a name defined in more than `MAP_MAX_DEFINERS` files gives no edge): a request names at most `MAX_SEEDS` (50) project-relative seeds, a path ending in `/` or naming a folder standing for every candidate file under it; `hops` 1 or 2, `max_files` at most 60; the reply carries for each reached file its path, sha256, hop, whether it is a seed, at most `MAX_EDGES` (10) edges each way with at most `MAX_NAMES` (8) names and how many edges were left out, `partial` when the project's caps, `max_files` or the deadline (`DEADLINE_SECONDS`, 8, inside the backend's wait) cut it, and the seeds matched and unmatched (a path outside the project, a file that may hold secrets or one a listing skips matches nothing); never a file's contents. The section is cut at `CODE_GRAPH_MAX_CHARS` (2500; `0` leaves it out and asks nothing) and redacted like the map (`context_read.redact_secrets`). No seeds, a daemon without the subject, a timeout, an error or an empty reply leave it out, and the prompt is the same text as before. Context, never evidence: a name used is not a call proven, and the runs are past observations about other deliveries. Design and later slices: [`docs/design/CODE_GRAPH.md`](../design/CODE_GRAPH.md).

### Compressed history

**Compressed history** (`services/tools/tool_history.py`, after SWE-agent's history processors, the idea): in `mcp_tools.chat_with_tools`, before each request the results of rounds older than the last `TOOL_HISTORY_KEEP_ROUNDS` become one line built from their observation (`read src/x.py lines 1–100 of 240 (sha256 …)`, `searched 'foo': 12 matches`, an edit's hashes and lint status, a test run's exit status, a research source, an MCP call's size and hash), prefixed so the model knows it can call again; a result already shorter than its line stays, and the assistant messages (the calls and any provider signature on them) are never changed. The observations on the evidence (`tool_calls`) stay whole.
