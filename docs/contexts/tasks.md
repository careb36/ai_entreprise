# The tasks context

Part of the project's guidance for agents; the index is [`CLAUDE.md`](../../CLAUDE.md). Read this document before changing code in `backend/app/services/tasks/`.

- **Folder:** `backend/app/services/tasks/`
- **Responsibility:** A task's record: its events and their hash chain (task_events), the projections that answer the board's questions (task_projection, TaskRecord), the comment-thread readers (board), the dependencies between a sprint's tasks. It records and answers; it never dispatches, reviews or calls a model.
- **May import:** [contracts](contracts.md), [platform](platform.md) (`docs/architecture/contexts.json`, checked by `scripts/check_architecture.py`).
- **Modules:** `board`, `dependencies`, `events`, `progress`, `progress_snapshot`, `relations`, `saved_views`, `sprint_board`, `task_events`, `task_filter`, `task_projection`.

## Components

### Dependencies between a sprint's tasks

**`backend/app/services/tasks/dependencies.py`** — Dependencies between a sprint's tasks: `BacklogItem.depends_on` holds the ids of the tasks that must be done first. The PO's plan names them by title (`spec_planning._validate_tasks` maps them to positions and breaks a cycle at the edge that closes it), `POST /v1/start_sprint` takes each task's `depends_on` as positions in `backlog_items` (`check_positions`: an unknown position, self or a cycle is a 422), keeps the ids and queues only the tasks that can start, with a `Waits for task …` note on the rest. The worker follows the order instead of the queue's: `sprint_control.dispatch_todo` and `_dispatch_todo_items` queue a `todo` task only when `is_ready` (every dependency done), `_on_task_assign` asks the same before touching a task that arrived early, and each review cycle `settle_active` blocks a `todo` task waiting on one a person must act on (`Blocked: waits for task …, which waits for a person.`, an explicit block reason, so the sprint closes around it and the inbox shows what the decision unblocks) and releases a task so blocked once its dependencies are done, or back in work (`Released: …`). The hold is the System's last note on the task (a comment anyone appends does not hide it); a chain of holds follows its root, so a task sent back to `todo` behind a held one is held again while the root is stuck; `sprint_settled` reconciles the holds before a sprint counts as settled, so it never closes over a task that could run. With the Git workflow, `git_workflow.delivery_spec` names the branches of the done tasks a task depends on (`merge`) and the daemon merges them into the task's worktree before writing (`git_workspace.merge_branches`, `merged` in its report; a conflict is an error). A carried task keeps a dependency carried with it and drops the rest. The board lists `depends_on` and `waiting_for` per task; `history_check.py` refuses a task that delivered before every task it depends on had closed, comparing its first deliverable with the dependency's last approval or person's note (`worked_before_dependency`).

### The readers of a task's comment thread

**`backend/app/services/tasks/board.py`** — The pure readers of a task's comment thread, shared by the task worker, `routers/inbox.py` and `services/loop/carry_over.py`: which comment is the deliverable to review, the pending `NEEDS WORK:` requests, whether a blocked task waits for a person (`blocked_item_next_step`, `item_is_settled`) and its `block_reason`. No engine, no I/O; the gate author names (`Quality gate`, `Verifier`) live here too. The advice a task got (the worker's console-advice note, the Architect's `ARCHITECT_CONSULTED:` brief) is never a verdict, and the phrases that keep a task blocked count only from the system, a gate or a person (`BLOCK_VERDICT_AUTHORS`), never from a deliverable.

### A task's life as events

**`backend/app/services/tasks/task_events.py`** / **`task_projection.py`** / **`routers/events.py`** — A task's life as events (issue #324, after OpenHands' event stream: typed events with a source and a cause). `task_events.record(session, item, kind, actor, text=, author=, status=, run_id=, verification_id=, payload=)` is the one function a transition goes through: it appends a `TaskEvent` (`models/event.py`, company-scoped: `event_type` the kind — `claimed`, `advised`, `delivered`, `verified`, `reviewed` with `payload.verdict` `approved`/`needs_work`, `sent_back`, `blocked`, `released`, `escalated`, `decided`, `approved_by_person`, `carried_over`, `risk_hold`, `review_failed`, `retried`, `recovered`, `paused`, `moved`, `note`, `integration`, `estimated` (the task's difficulty before an attempt and the routing it led to, `services/loop/task_routing.py`; no comment), `relation` (a typed relation to another task changed, on both tasks, no comment), `legacy`; `actor` `system`/`gate`/a role/`person`, which must match the comment's author; the task's status after it in `task_status`), seals it in the task's own hash chain (`seq`, `prev_hash`, `chain_hash`, keyed with `AUDIT_SIGNING_KEY` like the audit chain but a separate chain, `verify_chain`) and renders it as the board comment with the event's `event_id`, setting the status; the thread is read again under the chain's lock before the comment is appended, so a writer holding a stale task never drops a comment committed meanwhile. A person's text is kept whole; text the platform writes is capped at `TEXT_LIMIT` (4000). With a key, `verify_chain` reports an unsigned event after a signed one as `downgrade`, as the audit chain does. The caller commits; `record_by_id` opens its own session. The task worker (`_update_item_status`, `_append_item_comment` and every review-loop transition), `dependencies.note` (hold, release, waiting note), `carry_over` (both tasks), `sprint_control` (stop, credit pause), `run_review` (a person's accept, send-back and feedback), `scrum_master.record_decision` (`decided`, no comment), the escalation before a triage (`escalated`) and `PATCH /v1/backlog` (`person_kind`) write through it. The flags the board's questions need (`verdict`, `explicit_block`, `needs_person`, `retryable`, `retry`, `frozen`) go into the payload when the event is written (`flags_for`, the same rules `board.py` applies). `task_projection` answers the board's questions from the events (`pending_rework_feedback`, `block_reason`, `awaits_risk_acceptance`, `blocked_item_next_step`, `waits_for_a_person`, `status_from_events`) when they render the whole thread (`covers`: every comment names one of the task's events and none is a `legacy` marker), and falls back to `board.py` otherwise. `TaskRecord` is what a decision reads: the task's comments and events (rows, or `task_events.as_dict` dicts the worker carries in its task dict, `snapshot` / `record_from_dict`), the source picked once (`covers_thread`), and every question answered from it (`frozen`, `deliverable`, `pending_rework_feedback`, `rework_requests_by`, `rework_request_count`, `review_failures` counted as `review_failed` events, `next_step`, `block_reason`, `awaits_risk_acceptance`, `is_settled`, `waits_for_a_person`, `rework_since_send_back`, `last_send_back_at` from the person's `sent_back` event, `carried` from the `carried_over` event's `direction`, `held_by_dependency` from the hold's `payload.hold == "dependency"`). Every decision site reads through it: the task worker (the rework feedback in the prompt, the freeze checks, the deliverable QA reviews, the delivery gate's and QA's rework budgets, the failed-review limit, a blocked task's retry or recovery, dispatch), `dependencies` (`settle`, `sprint_settled`, the holds), `replicas.recover_inflight`, `carry_over`, the ScrumMaster's triage prompt and `triages_for`, the procedures' numbers, the retrospective, the inbox, the review form and the Manager agent's inbox and its further facts (`manager_inbox_extra.qa_approved`, `person_since`, the carry-over mark `TaskRecord.carry_mark`, which the agent's mark and a person's take-back write in their payload as `carry_mark`); a loop over many tasks loads their events once (`records_for`, `histories_for` → `task_events.for_tasks`). Only the webhook listener (`webhooks.py`, inside a flush) still reads the thread. The Manager agent's acceptance and a person's override of it are events too (`moved`, `payload.accepted_by`). A sprint's integration writes each task's part as its `integration` event (`services/release/integration_events.py`: merged, skipped because already in, stopped at its conflict, branch missing or refused; by the System, rendered as its comment, the status unchanged; a task the request never reached gets none). Migration `0014` backfills events from existing threads (marked `legacy`, unchained, each comment's whole text; a thread with a comment it cannot tell also gets a `legacy` event, so it stays read from its comments). `GET /v1/tasks/{id}/events` (Viewer) lists a task's events with its chain's state and which record the board reads; `GET /v1/sprints/{id}/events` a sprint's.

### The sprint board

**`backend/app/services/tasks/sprint_board.py`** / **`models/board_note.py`** / **`routers/board_notes.py`** (issue #439, [design](../design/SPRINT_BOARD.md)) — The short, typed notes a sprint's tasks leave each other (`sprint_board_notes`, migration `0023`): `add` writes a note checked by `services/contracts/board_notes.check` and a `board_note` event with its author (on the author task's chain, or the sprint's own for a person; no comment, no change to the task's state: `task_projection._ADVICE_KINDS`), and marks the note it supersedes `superseded`; `mark_wrong` is a person's, with who, when and why; `rejected` records the blocks of a delivery that were not notes (`board_note_rejected`); `notes_of`, `notes_by_sprint` and `counts` read; `contradiction_rework` is the issue's measure, the `NEEDS WORK:` requests that say they contradict another task of the same sprint. A note is a claim: nothing here reads or writes an observation. `GET /v1/sprints/{id}/board_notes` (Viewer) lists a sprint's notes with what was observed beside each file and the board's numbers; `POST /v1/sprints/{id}/board_notes` and `POST /v1/board_notes/{id}/mark_wrong` (Manager) are audited under `sprint:<id>:board`. A sprint with notes is archived, never deleted (`sprint_archive.evidence_of`).

### Filters and saved views of a company's tasks

**`backend/app/services/tasks/task_filter.py`** / **`saved_views.py`** / **`models/saved_view.py`** / **`routers/task_views.py`** (issue #535, [design](../design/SAVED_VIEWS.md)) — `task_filter.query` evaluates a filter (`services/contracts/task_filters`: a JSON tree of conditions under AND/OR groups over the allowlist `status`, `verdict`, `risk_tier`, `producer`, `assignee_role`, `rework_count`, `waits_for_person`, `covers`, `sprint_id`) over a company's tasks from the records the board reads: the row (a status outside the five read as `todo`, as the board places it), `TaskRecord` (`rework_request_count`, `waits_for_a_person`) and the Verifier's latest verification of the task's latest run (`verdict`, the `risk_tier` check; never the run's claims), with `producer` from that run. The query is the company's tasks narrowed to the filter's sprints by bound parameters; every condition is evaluated in Python, and only the facts the filter, order and grouping need are loaded for every task. `saved_views` keeps a `SavedView` (`filters`, `group_by`, `order_by`, `layout`, `visible_columns`, `access` private or company, `locked`; migration `0033`) and each person's `SavedViewPreference` apart: a private view is its author's alone, a company view its author's or a Manager's to change, a locked one a Manager's; a stored filter that no longer parses is reported `valid: false`. `GET /v1/tasks` (Viewer; 422 naming a field outside the allowlist), `GET`/`POST /v1/companies/{id}/views`, `GET`/`PUT`/`DELETE /v1/views/{id}` and `GET`/`PUT /v1/views/{id}/preferences`, audited under `company:<id>:views`.

### A sprint's progress: claimed done versus verified

**`backend/app/services/tasks/progress.py`** / **`progress_snapshot.py`** / **`models/progress.py`** / **`routers/sprint_progress.py`** (issue #531) — A sprint's progress as a time series built from its task events, never from a task's mutable fields. `progress.build(events, task_ids, sprint_id=, granularity="day"|"event")` is pure: it replays the events in order (`created_at`, then id) and, after each day (or each event), counts the tasks by status (`task_status` of their latest event that has one; `todo` before any) and, apart, by the latest verdict the Verifier gave on their delivery (`verified`, `refuted`, `unverifiable`, `none`). Two lines are kept and never merged: `claimed`, the tasks with a `delivered` event (the producer's claim), and `verified`, the tasks whose latest `verified` event carries the verdict `verified` (the observation); `gap` is the tasks claimed and not verified. The result has `points`, `final` and `by_task`; `canonical_bytes` is the one encoding it is compared and hashed in, and the same events give the same bytes whatever order they come in. The verdict is on the `verified` event's payload (`payload.verification`, written by `worker/deliver._verdict_payload` since #531); an older event gets the verdict of the Verification it names, else the latest Verification of its run observed before it (`progress_snapshot.normalised`; Verification rows are never edited, so the answer does not move). When a sprint closes (`worker/close._finalize_sprint_if_ready`, once across replicas), `progress_snapshot.seal_at_close` stores the series and the retrospective's counts (`RETRO_FIELDS`, numbers only) as a `SprintProgressSnapshot` (`sprint_progress_snapshots`, migration `0099`, renumbered at merge), computes its digest itself (`sha256:` over the canonical bytes of `{v, company_id, sprint_id, close_number, series, retrospective}`) and writes it into the company's audit chain as `sprint_progress_sealed` under `sprint:<id>:progress` (`details.snapshot_id`, `result.digest`, the claimed, verified and gap counts); best-effort, a failure never undoes the close. A row is never edited: a sprint a person reopened and that closes again gets the next `close_number`, and its first snapshot stays. `verify` recomputes the digest, compares it with the audit row and walks the chain (`intact`). `claim_gap(session, sprint_ids)` sums the gap over sprints from each one's first snapshot, else its events: the number the procedures are measured against ([learning](learning.md)). `progress.coverage(requirement_ids, covers_by_task, by_task)` says, per requirement (a criterion `REQ-1.2` counts for `REQ-1`), how many covering tasks were claimed, done and verified and its state (`verified`, `done`, `claimed`, `open`, `uncovered`). `GET /v1/sprints/{id}/progress` (Viewer, `granularity=day|event`) answers an open sprint's live series (`source: live`) and a closed sprint's latest snapshot (`source: snapshot`), with every snapshot and its check; `GET /v1/specifications/{id}/progress` (Viewer) the coverage across the specification's sprints. A sprint with a snapshot is archived, never deleted (`sprint_archive.evidence_of`). The Sprint page's Overview shows the two lines (`components/SprintProgress.tsx`, `SprintProgressChart.tsx`, `hooks/useSprintProgress.ts`, `services/api/progress.ts`). Design studied from Plane (`makeplane/plane`, AGPL-3.0, commit `290383d7`: `utils/analytics_plot.py` `burndown_plot`, `cycle_transfer_issues.py` `progress_snapshot`, the cycle's `progress_snapshot` field and its view), no code taken; unlike Plane, history is never rebuilt from a mutable `completed_at`.

### Typed relations between tasks across sprints

**`backend/app/services/tasks/relations.py`** / **`models/task_relation.py`** / **`routers/task_relations.py`** (issue #533) — `depends_on` links tasks only within one sprint; a duplicate, related work in another sprint or the attempt a carry-over made had no link anyone could query. A `TaskRelation` (`task_relations`, migration `0099`) is that link: `task_id` is `kind` of `related_task_id`, the kind one of `blocked_by`, `duplicate`, `relates_to` (`KINDS`), the state `proposed` or `confirmed`, with `proposed_by` / `proposed_role` (`person`, `system` or an agent's role) and `confirmed_by` (a person's email, or `rule:<name>` for a deterministic rule). One row per pair of tasks: `pair_low` / `pair_high` hold the two ids in order under a unique constraint, so the pair cannot be related twice whichever way round. The name read from the other task (`blocking` for `blocked_by`; `duplicate` and `relates_to` are their own reverse) comes from one fixed table, `REVERSE`, at read time; a request may say `blocking`, which is stored as `blocked_by` with the tasks swapped (`normalise`). `propose` refuses a task related to itself (422), tasks of two companies (404, as if the other did not exist), a task of an archived sprint and a pair already related (409); with `confirmed_by` it writes the relation confirmed. `confirm` is a person's; `reject` (a proposed relation) and `remove` (either) delete the row, and the events keep what it was. Every change is a `relation` event on both tasks (`task_events.record`, no comment, payload `action` `proposed`/`added`/`confirmed`/`rejected`/`removed`, the relation named from that task's side, the other task, the state, `claim` while proposed), so both hash chains cover it; the kind is in `task_projection._ADVICE_KINDS`, so it never changes what the board answers about a task. **Dispatch:** a proposed relation, and every relation other than a confirmed `blocked_by` between two tasks of one sprint, is information only. Confirming that one adds the blocker to the task's `depends_on` while the task is still `todo` (`added_dependency`; a circle among the sprint's dependencies is refused with 409), and from there `dependencies.py` holds the task as it holds a plan's dependency; removing the relation takes out only what it added. Carry-over writes a confirmed `relates_to` from the new attempt to the original (`rule:carry_over`); the duplicate decision at intake is to write `duplicate` the same way. `sprint_metrics` counts a sprint's relations by state and kind and the issue's measure, `duplicates_delivered`: confirmed duplicate pairs with a task in the sprint whose two tasks are both done. Agents cannot propose relations yet (no block in a delivery is parsed for one); `propose` takes an agent's role when they do. `GET /v1/tasks/{id}/relations` and `GET /v1/sprints/{id}/relations` (Viewer), `POST /v1/tasks/{id}/relations` (Manager; `confirm: true` writes it confirmed) and `POST /v1/task_relations/{id}/confirm`, `/reject`, `/remove` (Manager), each audited under `task-<id>`. The design follows Plane's issue relations (AGPL-3.0-only, commit 290383d7f92fa8995ea2adbd12442220b3b9b525: `db/models/issue.py` `IssueRelationChoices` and its unique constraint, `utils/issue_relation_mapper.py`, `apps/web/components/relations/`); no code was taken.
