# The planning context

Part of the project's guidance for agents; the index is [`CLAUDE.md`](../../CLAUDE.md). Read this document before changing code in `backend/app/services/planning/`.

- **Folder:** `backend/app/services/planning/`
- **Responsibility:** What is built and in which tasks: the specification and its check, the architecture and its check, their approval, the PO's sprint plan from a specification, the sprint planner and team, the project's stack discovery. It writes plans and documents; it never runs a task.
- **May import:** [contracts](contracts.md), [platform](platform.md), [tasks](tasks.md), [models](models.md), [evidence](evidence.md), [workspace](workspace.md), [tools](tools.md) (`docs/architecture/contexts.json`, checked by `scripts/check_architecture.py`).
- **Modules:** `arch_author`, `arch_check`, `discovery_service`, `discovery_team`, `document_approval`, `spec_author`, `spec_check`, `spec_diff`, `spec_impact`, `spec_planning`, `sprint_context`, `sprint_fallbacks`, `sprint_planner`, `sprint_prompts`, `sprint_team`, `stack_detection`, `wstg_plan`, and the `project_docs` package (`texts`, `texts_wstg_en`, `texts_wstg_es`, `refs`, `sanitize`, `layout`, `c4`, `scope_docs`, `control_docs`, `log_docs`, `checks`, `wstg_status`, `security_docs`, `collect`, `pack`).

## Components

### The specification

**`backend/app/services/planning/spec_check.py`** / **`spec_author.py`** / **`spec_planning.py`** — The specification (`models/specification.py`, `routers/specifications.py`): what the company's agents build from, as data. `spec_check.normalize` assigns the ids (`REQ-1`, `REQ-1.2`, `NFR-1`) in order, never a model or a request; `spec_check.check` is the deterministic gate: blocking (a requirement without a criterion, a criterion with an empty given/when/then, a quality target without a number, an unanswered question) and warnings (a promise without a number: "fast", "easy", "rápido"…). `spec_author.draft` asks the PO for a draft in a fixed JSON shape from a person's brief, with the questions it could not decide; a person answers (`POST /v1/specifications/{id}/questions/{i}`), asks for a revision (the answers go into the prompt) or edits, and only a Manager approves (`/approve`, 409 while the check blocks); an approved version is never edited, `/revise` opens a new draft that supersedes it. `spec_planning.plan` has the PO split an approved specification into tasks that name the criteria they cover (`POST /v1/plan_sprint` with `specification_id`; `uncovered` lists what no task covers; without a usable answer, one task per requirement), `POST /v1/start_sprint` keeps `specification_id` on the sprint and `covers` on each task (422 for an unknown id), the task prompt and QA's review prompt carry only the requirements the task covers (`requirements_context`), and `coverage` reads the boards: per criterion, done, blocked, planned or uncovered.

### The architecture

**`backend/app/services/planning/arch_check.py`** / **`arch_author.py`** — The architecture (`models/architecture.py`, `routers/architectures.py`) of an approved specification, as data: modules (responsibility, place in the repository, `depends_on`, the requirements they `cover`), interfaces (kind, the module that provides it, a contract, consumers), decisions (ADRs) and conventions, plus the Architect's open questions. `arch_check.normalize` assigns the ids (`MOD-1`, `IF-1`, `ADR-1`) and maps a draft's names onto them; `arch_check.check` blocks approval on a module without a responsibility, a reference to a module or requirement that does not exist, a dependency cycle (`find_cycle`), a decision without its decision or an unanswered question, and warns on a requirement no module covers, a module without a path, an interface without a contract, no decision. `arch_author.draft` asks the Architect, from the specification, the detected stack and the project's root files, in a fixed JSON shape, or revises from the answers; only a Manager approves (`/approve`, 409 while the check blocks), `/revise` opens the next version. Once approved, the PO's planning prompt carries it (`planning_context`), each task's prompt and QA's review carry the modules its requirements map to with their interfaces, and the decisions and conventions every task follows (`context_for`, appended by `spec_planning.requirements_for`), and `POST /v1/architectures/{id}/write` sends it as `docs/ARCHITECTURE.md` through the daemon (`workspace.generate`), keeping the sha256 the daemon read back (`written_sha256`) as an observation; `GET .../document` is the same Markdown.

### A sprint's team

**`backend/app/services/planning/sprint_team.py`** / **`routers/sprint_planning.py`** — A sprint's team (`Sprint.team`, `team_source`; `Company.team_selection`; migration `0019`): the roles its tasks may go to, so a documentation sprint does not hand work to the Developer. `POST /v1/plan_sprint` asks the PO for a `team` and `team_reasons` beside the tasks in the plan's JSON (`prompt_section`, both planners: `spec_planning.plan_from` and `sprint_planner._plan_with_po`, which the execution and self-improvement planners share); `suggested` reads it within the hired roles, adds every role a planned task goes to, and an unusable answer means every hired role. The answer carries `suggested_team`, `team_reasons`, `hired_roles` and `team_selection`. With a `team`, planning uses only those roles (the roster, the assignee list, `fit_tasks` for the fallback, and no QA test-writing tasks when QA is left out). The company's `team_selection` (`GET`/`PUT /v1/companies/{id}/team_selection`, Viewer / Manager) is `suggested` (default: the form pre-ticks the suggestion and a Manager adjusts it) or `automatic` (the form shows the team, the Manager does not confirm it); a person never picks a team from scratch. The suggestion travels with the plan: the form sends `suggested_team` back unchanged to `POST /v1/start_sprint`, which takes `team` (hired roles only, an unknown one a 422) and `suggested_team`, and `decide` records the team and `team_source`: `suggested` (the suggestion confirmed), `person` (a Manager changed it), `automatic` (no team sent in automatic mode: the suggestion) or `all` (no team: every hired role, as before). A backlog item or a carried task assigned outside the team is a 422. A sprint the system plans on its own (the autonomy-3 follow-up and the tasks it carries) takes the automatic path whatever the setting (`automatic_team`). The worker never runs a task outside its sprint's team (`refuse_off_team` in `_load_task_context` blocks one still to start for a person, `manual triage` in the System's note, so the sprint can close around it), and `PATCH /v1/backlog` refuses an assignee outside it. The team decides who gets tasks, not who judges them: QA's review and the Verifier still look at every delivery. `GET /v1/sprints` and the board return `team` and `team_source`; the "Plan a sprint" form (`components/QuickLaunch.tsx`, `components/SprintTeam.tsx`, `lib/sprintTeam.ts`) shows the picker or the automatic team, holds the launch while a task's role is off the team until it is planned again (sent with `team`), and the sprint page shows the team and who chose it.

### The sprint planner and the stack discovery

**`backend/app/services/planning/sprint_planner.py`** / **`sprint_prompts.py`** / **`sprint_context.py`** / **`sprint_fallbacks.py`** — The PO's plans: the foundation sprint of a new company (`plan_foundation_sprint`), an execution sprint from an objective and a self-improvement sprint (`plan_execution_sprint`, `plan_self_improvement_sprint`, both through `_plan_with_po` and its proxy client `_client`, which stay in `sprint_planner`). `sprint_prompts` holds the three prompt templates, `sprint_context` the roster, stack summary, root-file listing, the PO's choice among the agents and `build_self_improvement_objective`, and `sprint_fallbacks` the deterministic plans used when no model answers usably. `sprint_planner` re-exports every name, so its callers and tests import them there (issue #511).

**`backend/app/services/planning/discovery_service.py`** / **`stack_detection.py`** / **`discovery_team.py`** / **`routers/enterprise.py`** (`POST /v1/discover_team`) — The project's stack discovery: `stack_detection` reads the stack from the files alone (languages, frameworks, databases, infrastructure, complexity; no model, no network), `discovery_team` holds the rule-based team (`_build_team`) and the prompt and model catalogue the model is asked with, and `DiscoveryService.discover_project_team` with `_ai_suggest_team` (which the tests replace) stays in `discovery_service`, which re-exports the other names (issue #511).

### The documentation pack

**`backend/app/services/planning/project_docs/`** / **`routers/documentation.py`** / **`models/documentation.py`** (migration `0023`) — A project's management documentation compiled from its records (issue #530; design and threat model: [`docs/design/PROJECT_DOCUMENTATION.md`](../design/PROJECT_DOCUMENTATION.md)). `collect.snapshot` reads the company's records into plain data without personal data (roles and counts, never names): the newest approved specification and its architecture, the stack discovery, the sprints and tasks, the task events (blocked, escalated, decided, risk hold, carry-over) with their chain hash, the Verifier's verdict and risk tier per delivery, every specification and architecture version, the roster and members counted, the retrospectives, the procedures and the integrations. The pure builders turn it into Markdown placed after the PMBOK Guide, 8th edition (PMI, 2025), by performance domain and focus area (`layout.PLACEMENT`): charter, scope statement, WBS, requirements traceability matrix (requirement, task, verification, integration commit), schedule and milestones, RACI, risk register, issue log, change log, lessons learned register, check results per domain (`checks.CHECKS`, met / not met / measured / not computable / person), and the C4 context, container and component diagrams (`c4`: data the page draws plus Mermaid source), with an index. Every statement cites a record with a digest the backend computed or observed (`refs`); a section with no record says so (`missing`); sections only a person can decide (business case, benefits, budget, sponsor, risk appetite) are templates no agent fills (`persons`); record text cannot become Markdown or Mermaid structure (`sanitize`). The one model call is the charter's background, asked of the TechWriter and quoted as a claim (`pack.write_prose`). A pack is written in the project's documentation language (`Company.doc_language`, `en` or `es`, `GET`/`PUT /v1/companies/{id}/doc_language`, Viewer / Manager, set from the creator's interface language at `POST /v1/init_company`): every fixed string comes from `texts.TEXTS` in both languages, record text, ids, citations and digests stay as recorded, the prose is asked in that language, and the lint blocks a pack whose language is no longer the project's. Each document keeps the digest of exactly what it read; `pack.lint` recomputes it, so drift blocks approval. Routes: `GET`/`POST /v1/companies/{id}/documentation` (Viewer lists, Manager compiles a draft and supersedes older drafts), `GET /v1/documentation/{id}` with its lint, `GET …/documents/{key}` as Markdown, `POST …/approve` (Owner, `document_approval.approve_pack`, 409 while the lint blocks) and `POST …/write` (Manager, an approved pack to `docs/project/` through `workspace.generate`, the daemon's sha256 per file kept in `written_files`).

### The security test plan (OWASP WSTG)

**`backend/app/services/planning/wstg_plan.py`** / **`project_docs/wstg_status.py`** / **`project_docs/security_docs.py`** / **`routers/security_tests.py`** / **`models/security_review.py`** (migration `0099`) — Which web security tests apply to a project and which ran (issue #539; design in [`docs/design/PROJECT_DOCUMENTATION.md`](../design/PROJECT_DOCUMENTATION.md#security-test-plan-and-checklist-owasp-wstg-issue-539)). The tests come from the versioned catalogue of the OWASP Web Security Testing Guide (`services/platform/wstg_catalogue.py` over `app/data/wstg/catalogue.json`, CC BY-SA 4.0), each with the identifier the security probe uses (`WSTG-v42-CONF-06`, or `WSTG-87cf4a4-CONF-12` where release 4.2 lacks the test). `wstg_plan.plan` is a deterministic rule table (`RULES`): a signal read from the specification, the architecture and the detected stack (an HTTP surface, a browser client, sign-in, roles, an API, an API behind sign-in, uploads, a database, outbound fetches, payments, OAuth, SAML, GraphQL, WebSockets, JWT; English and Spanish words, interface kinds, frameworks, databases), cited by where it was found, selects tests, each `auto` (the daemon's `security_probe`, or a `qa_test` QA names `test_wstg_<cat>_<nn>_…`) or `manual` (a person), with its reason; a test no rule selects is not applicable with the signals that would bring it in. A model may only propose additions (`proposals`), shown as claims. `wstg_status.rows` sets each row from an observation (a WSTG item of a Verifier check, cited with the verification, the run, the run's artifact digest and the tool) or a person's recorded review, the newest winning: observed-pass / observed-fail / not-run / needs-manual / not-applicable. `security_docs` adds two documents to the pack, the WSTG checklist and a security test report after the guide's chapter 5, both with the CC BY-SA 4.0 footer, and `checks` measures the applicable tests observed passing against the specification's security target (STD-PO-1). `security_test_tasks` shapes QA's test-writing tasks, one per `qa_test` row; the sprint planner does not add them yet (see the design). Routes: `GET /v1/companies/{id}/security/wstg` (Viewer: signals, rows, statuses, counts), `GET`/`POST /v1/companies/{id}/security/wstg/reviews` (Viewer lists; a Manager records who reviewed, the date, the artifact and the result, `not_applicable` only with a note; the backend computes `record_sha256`; audited as `wstg_review_recorded`).
