## Components

### The specification

**`backend/app/services/planning/spec_check.py`** / **`spec_author.py`** / **`spec_planning.py`** — The specification (`models/specification.py`, `routers/specifications.py`): what the company's agents build from, as data. `spec_check.normalize` assigns the ids (`REQ-1`, `REQ-1.2`, `NFR-1`) in order, never a model or a request; `spec_check.check` is the deterministic gate: blocking (a requirement without a criterion, a criterion with an empty given/when/then, a quality target without a number, an unanswered question) and warnings (a promise without a number: "fast", "easy", "rápido"…). `spec_author.draft` asks the PO for a draft in a fixed JSON shape from a person's brief, with the questions it could not decide; a person answers (`POST /v1/specifications/{id}/questions/{i}`), asks for a revision (the answers go into the prompt) or edits, and only a Manager approves (`/approve`, 409 while the check blocks); an approved version is never edited, `/revise` opens a new draft that supersedes it. `spec_planning.plan` has the PO split an approved specification into tasks that name the criteria they cover (`POST /v1/plan_sprint` with `specification_id`; `uncovered` lists what no task covers; without a usable answer, one task per requirement), `POST /v1/start_sprint` keeps `specification_id` on the sprint and `covers` on each task (422 for an unknown id), the task prompt and QA's review prompt carry only the requirements the task covers (`requirements_context`), and `coverage` reads the boards: per criterion, done, blocked, planned or uncovered.

### The architecture

**`backend/app/services/planning/arch_check.py`** / **`arch_author.py`** / **`arch_versions.py`** — The company's architecture (`models/architecture.py`, `routers/architectures.py`, `routers/company_architecture.py`), versioned, as data: modules (responsibility, place in the repository, `depends_on`, the requirements they `cover`), interfaces (kind, the module that provides it, a contract, consumers), decisions (ADRs) and conventions, plus the Architect's open questions. `arch_check.normalize` assigns the ids (`MOD-1`, `IF-1`, `ADR-1`) and maps a draft's names onto them; `arch_check.check` blocks approval on a module without a responsibility, a reference to a module or requirement that does not exist, a dependency cycle (`find_cycle`), a decision without its decision or an unanswered question, and warns on a requirement no module covers, a module without a path, an interface without a contract, no decision. `arch_author.draft` asks the Architect, from the specification, the detected stack and the project's root files, in a fixed JSON shape, or revises from the answers; only a Manager approves (`/approve`, 409 while the check blocks), `/revise` opens the next version. Once approved, the PO's planning prompt carries it (`planning_context`), each task's prompt and QA's review carry the modules its requirements map to with their interfaces, and the decisions and conventions every task follows (`context_for`, appended by `spec_planning.requirements_for`), and `POST /v1/architectures/{id}/write` sends it as `docs/ARCHITECTURE.md` and one ADR file per decision through the daemon, in a single `workspace.generate` request, keeping the sha256 the daemon read back per file as an observation (`written_files`, plus `written_path`/`written_sha256` for the document); `GET .../document` is the same Markdown. `adr_docs.adr_documents` renders each decision as its own ADR file (`docs/adr/NNNN-<slug>.md`: Status, Context, Decision, Consequences): the write first lists the repository's `docs/adr` (`workspace.list`), so a decision whose file is already there keeps its number and slug and a new one takes the repository's first free number (`adr_files`, `first_free_number`); a decision may record its `slug`, the `date` it was accepted, and the decision that supersedes it (`superseded_by`, `ADR-7`, rendered by its file number: "Superseded by ADR 0018") — all three a person's record: `arch_author.parse_draft` drops a date or a supersession the Architect wrote — and without a date the architecture's approval date is its status; `GET .../adrs?first_number=` serves them (issue #329, F4). La Fabrique's own `docs/ARCHITECTURE.md` and `docs/adr/0012` onwards are this rendering of `docs/architecture/architecture.json` (`scripts/self_host/render_docs.py`, kept in step by `tests/test_self_hosting.py`).

**One architecture per company, versioned** (issue #329, finding F3 of [the self-hosting retrospective](../retrospectives/2026-11-self-hosting.md); migration `0038`). A company has one architecture and each `Architecture` row is a version of it: `version` counts the company's versions, approving one (`document_approval.approve_architecture`) supersedes every other approved version of the company, so `arch_versions.current` is the newest approved one, and the earlier versions stay readable. A version names the specification it was drafted for (`specification_id`); a module's `covers` are that specification's requirements and its `earlier_covers` (`{"<specification id>": ["REQ-1"]}`, kept by `arch_check.normalize`) what it covers in the earlier specifications the architecture serves, since `REQ-1` of one specification is not `REQ-1` of another. The revision for a new specification is the next version of the same architecture (`arch_versions.start_revision`, through `POST /v1/companies/{id}/architecture/revisions` or `POST /v1/architectures/{id}/revise` with a `specification_id`, Manager; and `POST /v1/architectures` or `/draft` for a specification the current version does not cover): `rebase` moves the own covers under `earlier_covers` and takes back what the version had for the target or a version it supersedes, and `carry` keeps a module's earlier covers when an edit or the Architect's answer rewrites the modules without naming them (the Architect is told which earlier specifications the modules serve, and its prompt omits their covers). The version number is taken under a lock of the company row, after the Architect's call. `arch_check.check` takes the earlier specifications too (`arch_versions.earlier_specifications`: a requirement a specification does not have, or a specification of another company, blocks; a requirement of an approved one no module covers warns), and `arch_versions.coverage` lists, per specification the version covers, each requirement with its modules. The prompts read the version that holds for their sprint's specification (`arch_author.approved_for`: the current version when it covers it, else the newest approved or superseded one that does, so a specification of a company whose versions predate F3 keeps its own) with that specification's covers (`content_for`, `arch_versions.view_for`; also the routing, related-code and sprint-note readers of the loop). A specification names the version it was planned against (`Specification.architecture_id`, set when the version drafted for it is approved and when `POST /v1/start_sprint` starts a sprint from it; `GET /v1/specifications/{id}` adds `architecture_version`). `GET /v1/companies/{id}/architecture` (the current version with its check and coverage, the open draft and the history), `…/architecture/versions` and `…/architecture/versions/{version}` read it (Viewer); `GET /v1/architectures?specification_id=` lists the versions that cover a specification. The document names the earlier specifications a version covers and each module's covers in them; a version that covers one specification renders exactly as before. Taken from Kiro's spec-driven flow (requirements, then one design per project revised for each new spec, then tasks), design only.

### A sprint's team

**`backend/app/services/planning/sprint_team.py`** / **`routers/sprint_planning.py`** — A sprint's team (`Sprint.team`, `team_source`; `Company.team_selection`; migration `0019`): the roles its tasks may go to, so a documentation sprint does not hand work to the Developer. `POST /v1/plan_sprint` asks the PO for a `team` and `team_reasons` beside the tasks in the plan's JSON (`prompt_section`, both planners: `spec_planning.plan_from` and `sprint_planner._plan_with_po`, which the execution and self-improvement planners share); `suggested` reads it within the hired roles, adds every role a planned task goes to, and an unusable answer means every hired role. The answer carries `suggested_team`, `team_reasons`, `hired_roles` and `team_selection`. With a `team`, planning uses only those roles (the roster, the assignee list, `fit_tasks` for the fallback, and no QA test-writing tasks when QA is left out). The company's `team_selection` (`GET`/`PUT /v1/companies/{id}/team_selection`, Viewer / Manager) is `suggested` (default: the form pre-ticks the suggestion and a Manager adjusts it) or `automatic` (the form shows the team, the Manager does not confirm it); a person never picks a team from scratch. The suggestion travels with the plan: the form sends `suggested_team` back unchanged to `POST /v1/start_sprint`, which takes `team` (hired roles only, an unknown one a 422) and `suggested_team`, and `decide` records the team and `team_source`: `suggested` (the suggestion confirmed), `person` (a Manager changed it), `automatic` (no team sent in automatic mode: the suggestion) or `all` (no team: every hired role, as before). A backlog item or a carried task assigned outside the team is a 422. A sprint the system plans on its own (the autonomy-3 follow-up and the tasks it carries) takes the automatic path whatever the setting (`automatic_team`). The worker never runs a task outside its sprint's team (`refuse_off_team` in `_load_task_context` blocks one still to start for a person, `manual triage` in the System's note, so the sprint can close around it), and `PATCH /v1/backlog` refuses an assignee outside it. The team decides who gets tasks, not who judges them: QA's review and the Verifier still look at every delivery. `GET /v1/sprints` and the board return `team` and `team_source`; the "Plan a sprint" form (`components/QuickLaunch.tsx`, `components/SprintTeam.tsx`, `lib/sprintTeam.ts`) shows the picker or the automatic team, holds the launch while a task's role is off the team until it is planned again (sent with `team`), and the sprint page shows the team and who chose it.

### The intake queue

**`backend/app/services/planning/intake_queue.py`** / **`intake_records.py`** / **`routers/intake.py`** / **`models/intake.py`** (migration `0035`) — The requests that reach a company, until a person decides them (issue #532; after Plane's intake, `db/models/intake.py`, `app/views/intake/base.py`, `bgtasks/issue_automation_task.py`, AGPL-3.0, design only). An `IntakeItem` is company-scoped and keeps the sender's words (`title`, `body`), the `source` the backend observed (`ticket` from `POST /v1/support/report_bug` with a `company_id` the sender is a member of, `source_ref` the ticket number; `brief` from a person signed in on `POST /v1/companies/{id}/intake`, and the client's brief that `POST /v1/specifications/draft` turns into a new draft, recorded accepted and linked to it by `record_brief`; `webhook` from an API-token caller on the same route, `source_ref` `api_token:<id>`; `chat` from `request <text>` in Slack or Teams, see [integrations](integrations.md#approvals-in-slack-and-teams)), never a field the sender fills. The status is one of `pending`, `accepted`, `declined`, `duplicate`, `snoozed`; the moves a person may make are `services/contracts/intake_rules.TRANSITIONS` (accepted is final; declined and duplicate may be reopened; snoozed may be decided or reopened). Only a Manager decides (`POST /v1/intake/{intake_id}/accept|decline|duplicate|snooze|reopen`, the row locked for the decision); a Viewer reads and sends. The routes are declared in `docs/architecture/authorization.json` and the bodies are `schemas.RequestModel`s. Accepting creates what the request became and keeps both links: a task in an open sprint of the company (the assignee on the sprint's team, the task's thread opening with a `note` event naming the request, queued through the outbox only in an active sprint), or a specification revision (the draft named, else the open revision of the approved one, else a new revision, version + 1; the request is added as an open question, so `spec_check` blocks approval until a person answers it; the approved version is never edited). Declining needs a reason; a duplicate names one intake item or one task of the company. The Support agent's suggestion (`suggested_*`, a claim; [management](management.md)) and a person's decision (`decided_*`, `decision_reason`, `decided_by`, `decided_at`) are separate fields, and nothing in the web form is filled in from the suggestion. Every move is one audit row naming its actor (`human:<email>`, or `system:intake-janitor`) under `intake:<company>:<item>`, with `from` and `to`; `intake_records.history` reads the item's history back from the company's hash chain. The intake janitor loop (`run_intake_janitor`, started by `lifecycle`, every five minutes under `locks.INTAKE_WAKE`) moves a snoozed request back to `pending` once `snoozed_until` passes (`wake_due`); it runs in the backend rather than the janitor container because only the backend seals audit rows. `GET /v1/companies/{id}/intake-record` is the queue's numbers, counted by `intake_rules.measures` from the items: the share of requests closed with what they led to recorded (the task or revision, the duplicate's link, the decline's reason), the median time from received to a final decision, and, per category, how often the agent's suggested status matched the person's decided status (and the category itself where both named one). The inbox counts the pending requests (`intake_pending`, in `total`); the Review page lists them (`components/IntakeQueue.tsx`, [frontend](frontend.md)).

### The sprint planner and the stack discovery

**`backend/app/services/planning/sprint_planner.py`** / **`sprint_prompts.py`** / **`sprint_context.py`** / **`sprint_fallbacks.py`** — The PO's plans: the foundation sprint of a new company (`plan_foundation_sprint`), an execution sprint from an objective and a self-improvement sprint (`plan_execution_sprint`, `plan_self_improvement_sprint`, both through `_plan_with_po` and its proxy client `_client`, which stay in `sprint_planner`). `sprint_prompts` holds the three prompt templates, `sprint_context` the roster, stack summary, root-file listing, the PO's choice among the agents and `build_self_improvement_objective`, and `sprint_fallbacks` the deterministic plans used when no model answers usably. `sprint_planner` re-exports every name, so its callers and tests import them there (issue #511).

**`backend/app/services/planning/objective_text.py`** / **`planner_fallback.py`** — The objective a person wrote is never cut, and a plan made without the planner's model is visible (issue #752; ISO/IEC 27001:2022 A.8.32, and the positioning's rule that a claim and an observation never share a field). `_plan_with_po` returns `objective` (what the person wrote, whole) apart from the model's `goal` (bounded to one line; without one, the objective whole), and `planner_fallback`: None when the model answered usably, else `{reason, detail}` as the backend observed it (`no_model`, `model_error` with the proxy's error, `unparseable` with the parse failure, `too_few_tasks`, `unexpected_error`); `spec_planning.plan_from` does the same for its one-task-per-requirement fallback, and the person's note reaches the PO whole. `_build_execution_fallback` makes the goal the objective whole and has the PO's task cite it whole; `objective_items` reads the objective's explicit items without a model (the shallowest Markdown heading level that occurs twice, else numbered list items at the start of a line; never inside a code fence), and each becomes a Developer task whose description is the item's text as written, after the PO's task, up to the scope; the rest are named in `unplanned_items`. `display_name` shortens a label (the sprint's name, a task's title) with an ellipsis, for display only. `planner_fallback` records the fallback in the audit log, by the backend: `record_plan` under `plan:<company>:<plan_id>` when `POST /v1/plan_sprint` (or the self-improvement planner) falls back, the response carrying `plan_id`; `carry_to_sprint` when `POST /v1/start_sprint` names that `plan_id`, reading the backend's own row back and writing `sprint:<id>:planning` with the reason copied from it (an unknown `plan_id`, or another company's, records nothing); `record_sprint` for the follow-up sprint the platform opens at close. The board returns `objective` and `planner_fallback` (`of_sprint`); the row records no work, so `sprint_archive.evidence_of` leaves it out. The frontend's `components/PlannerFallback.tsx` shows the note (reason, detail, the items left out) on the plan preview with "Retry planning" (plan again) and on the board, where a Manager's "Retry planning" opens the planner on the Sprints page with the objective; `ObjectiveText` shows the objective whole on demand.

**`backend/app/services/planning/discovery_service.py`** / **`stack_detection.py`** / **`discovery_team.py`** / **`routers/enterprise.py`** (`POST /v1/discover_team`) — The project's stack discovery: `stack_detection` reads the stack from the files alone (languages, frameworks, databases, infrastructure, complexity; no model, no network), and its `has_code_files` answers whether a list of file paths holds source code — what the loop's foundation-sprint decision reads from the daemon's snapshot of a folder ([loop](loop.md), retrospective F8); `discovery_team` holds the rule-based team (`_build_team`) and the prompt the model is asked with (roles, seniority, specialty, system prompt and reasoning; no model catalogue), and sets every suggested agent's `model` to its role's default through `model_factory` (`model_for_discovery_role`: PO→PO, SM→ScrumMaster, Architect→Architect, Dev→Developer, QA→QA, DevOps→DevOps, Security→SecOps, Data→DataEngineer), whichever path suggested the team, and `DiscoveryService.discover_project_team` with `_ai_suggest_team` (which the tests replace) stays in `discovery_service`, which re-exports the other names (issue #511).

### The documentation pack

**`backend/app/services/planning/project_docs/`** / **`routers/documentation.py`** / **`models/documentation.py`** (migration `0023`) — A project's management documentation compiled from its records (issue #530; design and threat model: [`docs/design/PROJECT_DOCUMENTATION.md`](../design/PROJECT_DOCUMENTATION.md)). `collect.snapshot` reads the company's records into plain data without personal data (roles and counts, never names): the newest approved specification, every approved specification (`specifications`, oldest first, with the ids of their versions) and the company's current architecture, the stack discovery, the sprints and tasks, the task events (blocked, escalated, decided, risk hold, carry-over) with their chain hash, the Verifier's verdict and risk tier per delivery, every specification and architecture version, the roster and members counted, the retrospectives, the procedures and the integrations. The pure builders turn it into Markdown placed after the PMBOK Guide, 8th edition (PMI, 2025), by performance domain and focus area (`layout.PLACEMENT`): charter, scope statement, WBS, requirements traceability matrix (requirement, task, verification, integration commit), schedule and milestones, RACI, risk register, issue log, change log, lessons learned register, check results per domain (`checks.CHECKS`, met / not met / measured / not computable / person), and the C4 context, container and component diagrams (`c4`: data the page draws plus Mermaid source), with an index. With several approved specifications (issue #329, F3) the scope statement, WBS, traceability matrix, schedule and index have a section (or a milestone, or an entry) per specification, the requirements-covered check counts them all, and a requirement's tasks are those of its own specification's sprints (`specs`); with one, a document reads as before and its inputs do not name `specifications`, so its digest is unchanged. Every statement cites a record with a digest the backend computed or observed (`refs`); a section with no record says so (`missing`); sections only a person can decide (business case, benefits, budget, sponsor, risk appetite) are templates no agent fills (`persons`); record text cannot become Markdown or Mermaid structure (`sanitize`). The one model call is the charter's background, asked of the TechWriter and quoted as a claim (`pack.write_prose`). A pack is written in the project's documentation language (`Company.doc_language`, `en` or `es`, `GET`/`PUT /v1/companies/{id}/doc_language`, Viewer / Manager, set from the creator's interface language at `POST /v1/init_company`): every fixed string comes from `texts.TEXTS` in both languages, record text, ids, citations and digests stay as recorded, the prose is asked in that language, and the lint blocks a pack whose language is no longer the project's. Each document keeps the digest of exactly what it read; `pack.lint` recomputes it, so drift blocks approval. Routes: `GET`/`POST /v1/companies/{id}/documentation` (Viewer lists, Manager compiles a draft and supersedes older drafts), `GET /v1/documentation/{id}` with its lint, `GET …/documents/{key}` as Markdown, `POST …/approve` (Owner, `document_approval.approve_pack`, 409 while the lint blocks) and `POST …/write` (Manager, an approved pack to `docs/project/` through `workspace.generate`, the daemon's sha256 per file kept in `written_files`).

### Importing a company's standards

**`backend/app/services/planning/company_standards_import.py`** (issue #700; [`docs/design/COMPANY_STANDARDS.md`](../design/COMPANY_STANDARDS.md), §4) — `POST /v1/companies/{id}/standards/import` (a Manager; `202`): the daemon reads `.fabrique/standards.toml` at the head of the company's default branch (`workspace.git.read_at`: the base branch, else `origin/HEAD`, `main`, `master`; never a task branch or the checkout), the backend hashes the bytes it received, `contracts.company_standards.parse` validates them, and at the same commit every guard's files (folders recursively, sorted, symbolic links refused, `exclude` applied) are hashed here (`guard_hashes`) and each `baseline` read (`read_baselines`); the in-backend kinds are then dry-run against that commit's tree as if every file had been delivered (`dry_run`, through the evidence's `company_standards_check`) and the draft stored with its refusals by `platform.company_standards_setting`. `command` standards are `not_run` in the dry run: they execute in a delivery's sandbox. No daemon, no project folder or no file is `ImportUnavailable` (a 409) and no draft. `tests/test_company_standards_import.py` drives it over real git in `tmp_path` through the daemon's handler.

### The security test plan (OWASP WSTG)

**`backend/app/services/planning/wstg_plan.py`** / **`project_docs/wstg_status.py`** / **`project_docs/security_docs.py`** / **`routers/security_tests.py`** / **`models/security_review.py`** (migration `0034`) — Which web security tests apply to a project and which ran (issue #539; design in [`docs/design/PROJECT_DOCUMENTATION.md`](../design/PROJECT_DOCUMENTATION.md#security-test-plan-and-checklist-owasp-wstg-issue-539)). The tests come from the versioned catalogue of the OWASP Web Security Testing Guide (`services/platform/wstg_catalogue.py` over `app/data/wstg/catalogue.json`, CC BY-SA 4.0), each with the identifier the security probe uses (`WSTG-v42-CONF-06`, or `WSTG-87cf4a4-CONF-12` where release 4.2 lacks the test). `wstg_plan.plan` is a deterministic rule table (`RULES`): a signal read from the specification, the architecture and the detected stack (an HTTP surface, a browser client, sign-in, roles, an API, an API behind sign-in, uploads, a database, outbound fetches, payments, OAuth, SAML, GraphQL, WebSockets, JWT; English and Spanish words, interface kinds, frameworks, databases), cited by where it was found, selects tests, each `auto` (the daemon's `security_probe`, or a `qa_test` QA names `test_wstg_<cat>_<nn>_…`) or `manual` (a person), with its reason; a test no rule selects is not applicable with the signals that would bring it in. A model may only propose additions (`proposals`), shown as claims. `wstg_status.rows` sets each row from an observation (a WSTG item of a Verifier check, cited with the verification, the run, the run's artifact digest and the tool) or a person's recorded review, the newest winning: observed-pass / observed-fail / not-run / needs-manual / not-applicable. `security_docs` adds two documents to the pack, the WSTG checklist and a security test report after the guide's chapter 5, both with the CC BY-SA 4.0 footer, and `checks` measures the applicable tests observed passing against the specification's security target (STD-PO-1). `security_test_tasks` shapes QA's test-writing tasks, one per `qa_test` row; the sprint planner does not add them yet (see the design). Routes: `GET /v1/companies/{id}/security/wstg` (Viewer: signals, rows, statuses, counts), `GET`/`POST /v1/companies/{id}/security/wstg/reviews` (Viewer lists; a Manager records who reviewed, the date, the artifact and the result, `not_applicable` only with a note; the backend computes `record_sha256`; audited as `wstg_review_recorded`). The routes are declared in `docs/architecture/authorization.json`; `ReviewRequest` is a `schemas.RequestModel`, so an undeclared privileged field is refused.

### Other modules

- `spec_diff` (`diff_specs`): the deterministic diff between two versions of a specification, by requirement and criterion id (ids are positional, so a reorder shows as an add and a remove).
- `spec_impact` (`impact`): which tasks and modules a specification revision affects. It changes nothing; turning the list into a sprint is a Manager's step.
- `project_docs/scope_docs` (charter, scope statement, WBS), `project_docs/control_docs` (schedule, RACI, risk register, lessons learned) and `project_docs/log_docs` (traceability matrix, issue log, change log): the pack's pure builders, from the snapshot alone; no model writes them.
- `project_docs/statements` / `routers/person_sections.py` / `models/person_statement.py` (migration `0047`): the sections only a person can write (issue #530, phase 2): the charter's business case, benefits, budget and sponsor, the risk appetite and the checks a person judges (`statements.SECTIONS`). An Owner or a Manager writes or withdraws one (`GET …/documentation/person-sections` and `…/{section}/history`, Viewer; `PUT`/`DELETE …/{section}`, Manager, audited); rows are append-only and the backend computes `statement_sha256`. A statement is a claim, never an observation: it has its own snapshot key per document, is quoted with the author's company role and time and cited as a claim, is sanitized like record text, and makes a compiled pack stale when it changes.
- `project_docs/performance`, `project_docs/status_docs`, `project_docs/collect_status` (issue #530, phase 2): the status and work performance report. `collect_status` reads two snapshot keys, `effort` (per task, the latest `effort_observed` event the backend wrote, actor `system` and `observed_by` `backend`; any other is a claim and is not read) and `costs` (each sprint's reported model usage and price, `services/models/run_cost.sprint_costs`); `performance` counts the figures per sprint and in total from those and the sprints, events and verifications; `status_docs.report` renders them with a source per figure and the forecast as a person's section (`status_report.forecast`). Its inputs name no retrospective or message. `checks` adds carry-over and first-pass (measured), spend known and effort observed for every completed sprint (met / not met). Strings in `project_docs/texts_status_en` and `texts_status_es`.
- `project_docs/iterations`, `project_docs/release_docs`, `project_docs/collect_release` (issue #530, phase 2): the release and iteration plan. `collect_release` reads three snapshot keys: `iteration_plans` (each sprint's `scope_size` and `team_source`), `carries` (each `carried_over` task event leaving a sprint that the platform wrote, actor `system`, with the task and sprint it went to and its chain hash; any other actor is a claim and is not read) and `releases` (each sprint integration published as one request: the daemon's commit, how it was published, and the time and chain hash of the audit row; the publisher's name and the request's address are left out); `iterations` counts the iterations, the requirements carried and delivered (a covering task done on the board) and the completed iterations released; `release_docs.plan` renders the iteration plan, the requirements by iteration, the carry-over and the releases with a source per figure, and target dates and scope ahead as a person's section (`release_plan.targets`). Its inputs name no retrospective or message. `checks` adds requirements delivered and iterations released (both measured). Strings in `project_docs/texts_release_en` and `texts_release_es`.
- `project_docs/closure`, `project_docs/final_docs` (issue #530, phase 2): the final report. No new snapshot key: `closure` reads the specifications, sprints, events, verifications, `carries` and `releases` and counts each requirement as delivered (a covering task done) or not delivered (planned or not planned) with the Verifier's latest reading of each done task, the holds left open (a `blocked` or `risk_hold` event whose task is still blocked, an `escalated` one with no later `decided`, on a task neither done nor carried by the platform) and the high-risk readings of tasks neither done nor carried, and the sprints still open (the report is then interim); `final_docs.report` renders those with the status report's measured outcomes (`performance`, `status_docs.spend_total`) and the releases cut, a source per figure, a pointer to the lessons learned register, and three person sections (`final_report.acceptance`, `.benefits`, `.handover`). Its inputs name no retrospective, procedure or message. `checks` adds nothing left on hold at closure (Risk: met / not met once every sprint is closed, measured while one runs). Strings in `project_docs/texts_final_en` and `texts_final_es`.
- `project_docs/collect_plans`, `project_docs/quality_docs`, `project_docs/comms_docs`, `project_docs/plan_checks` (issue #530, phase 2): the quality and communications management plans. `collect_plans` reads two snapshot keys: `quality_basis` (no database: the standards catalogue, `standards.QUALITY_AREAS`, the gate's refuting checks from `evidence/delivery_gate` and the tier `risk.classify` gives one path per area, each entry with the digest the backend computed) and `communications` (the company's `CompanyWebhook`, `ChatConnection`s with their linked-account count, the `ManagerPolicy` row with the deployment's Manager agent and mail settings, and `AuditAnchorSettings`, each hashed, never an address, secret, credential, workspace or name; delivery counters are left out). `quality_docs.plan` renders the standards, the specification's quality targets and the areas without one (STD-PO-1), the gate, the risk tiers and the status report's quality figures, with the objectives and thresholds as a person's section (`quality_plan.objectives`); `comms_docs.plan` renders who is in the company and each channel the platform has (board, review inbox, documentation pack, webhook, Slack, Teams, brief by mail, audit anchors, audit log) with its state from its record, and the external stakeholders and cadence as person sections (`communications_plan.stakeholders`, `communications_plan.cadence`). Neither reads a retrospective or message. `plan_checks` adds verified readings (Scope, measured), quality targets for every area (Scope, met / not met) and channels on (Stakeholders, measured) to `checks.CHECKS`. Strings in `project_docs/texts_plans_en` and `texts_plans_es`.
- `project_docs/collect_stakeholders`, `project_docs/stakeholder_docs` (issue #691): the stakeholder register. `collect_stakeholders` reads one snapshot key, `stakeholders`: the company's teams (the role each grants and its members who are company members, counted; never a name, description or author) and each approved specification and architecture version with who approved it reduced to a code (the approving account's effective role now, `agent`, `no_sign_in` or `former`; the address is matched there and never leaves the module; the pack's own approvals are not read), each hashed. `stakeholder_docs.register` renders the company roles with their people counted (`members`) and what each receives and decides, citing the routes that enforce it, the teams by number, the approvals counted by who gave them with each approval cited, the agent roles hired (`roles`), and the external stakeholders as a person section (`stakeholder_register.external`). It reads no retrospective or message. `stakeholder_docs.approvals_check` adds who gave the approvals (Stakeholders, measured) to `checks.CHECKS`. Strings in `project_docs/texts_stakeholders_en` and `texts_stakeholders_es`.
- `project_docs/collect_checks`, `project_docs/domain_checks` (issue #692): more computed checks per domain. `collect_checks` reads one snapshot key, `check_basis`: each sprint's `duration_days`, the tasks accepted into a sprint from an intake request (the `note` task event `intake_queue` writes under the actor `system`, with its chain hash; the same payload under another actor is a claim and is not read) and each business unit's token quota and use, hashed, without the unit's name. `domain_checks` adds work starts on an approved plan (Governance, met / not met), tasks that joined a sprint after planning (Scope, measured), sprints closed by their planned end (Schedule, measured), usage against the configured quota (Finance, measured) and tasks on their sprint's team (Resources, met / not met) to `checks.CHECKS`; each is not computable with its reason when the records cannot decide. Strings in `project_docs/texts_checks_en` and `texts_checks_es`.
- `project_docs/collect_transition`, `project_docs/transition`, `project_docs/transition_docs` (issue #696): the ITIL transition set (`transition.md`; Governance, Executing). `collect_transition` reads one snapshot key, `transition`: per release (a sprint integration published as a request or merged locally into the base), the done tasks as the integration recorded them with the criteria they cover, the daemon's suite run, the publication and the local merge with their audit rows, the integration's latest decision review (commit, `diff_sha256`, segregation of duties, audit row; never its words), the Verifier's reading of each delivery recorded at integration, the `run_delivery_undone` audit rows of its runs, and the sprint's hold events up to the release with the task's status then (`TaskEvent.task_status`); who approved or merged is the account's effective company role now, `former` or `no_account`, never a name or address, and each part carries the digest the backend computed. `transition` derives what each release delivered and its known errors (a refuted, unverifiable or high-risk reading of a delivery it carries, or a hold open in its sprint at release time: still blocked, or escalated with no decision, not delivered and not carried by the platform); `transition_docs.document` renders a change record per release, release notes, the known errors and a person section, `transition.handover`. It reads the release context's tables directly, since planning may not import release (`run_delivery_undone` is repeated as a constant). Strings in `project_docs/texts_transition_en` and `texts_transition_es`.
- `project_docs/collect_code`, `project_docs/c4_code` (issue #693): the C4 code level of `c4.md`. `collect_code` reads, through the tools interface (`services/tools/code_level`), the stored code graph (issue #438) of the folder the task worker stores it for (the newest discovered project, else `AGENT_WORKSPACE_ROOT`) and gives the snapshot two keys: `code_graph` (`status`, `claims`: each module's `implements` edge to its path, the architecture's claim; `observed`: the stored files under those paths with the sha256 the daemon reported, the names they define and the references among them, or None when nothing is stored) and `code_graph_observed_at` (shown, not hashed). The folder itself is not put in the snapshot. `c4_code` renders, per component, a **Claim.** line citing the module as a claim and an **Observed.** table citing each file with its sha256, then the references between the components' files; without a stored graph the section says "not observed" and is listed in `missing`. `code_graph` is an input of `c4.md`'s digest (`c4.DOCUMENT_INPUTS`) and not of the diagrams' (`C4_INPUTS`), so a cited file whose sha256 changes makes the document stale and leaves the diagrams current. The pack never asks the daemon.
- `project_docs/pack_manifest` / `routers/documentation_manifest.py` (issue #694, phase 4): the pack's signed manifest. `build` lists every file the pack writes to `docs/project/` with the sha256 and size the backend computed over those bytes, the inputs digest and the compile time (UTC, to the second); `sign` uses the deployment's audit signing key (`audit_signing.sign_audit_payload`: `hmac-sha256:` with `AUDIT_SIGNING_KEY`, `unsigned:` without); `verify` refuses a tampered, missing or unexpected file, a signature that does not match, and a keyed signature checked without the key (`unverifiable`). Compiling a pack enters the manifest's digest in the company's audit chain (`record`, action `documentation_pack_compiled`), so a pack rewritten in the database afterwards no longer matches it (`audit_record`). `GET /v1/documentation/{id}/manifest` (Viewer) downloads the manifest, its digest, signature and that audit record. No table: the manifest is derived from the stored pack and the chain keeps its digest.
- `project_docs/texts_en`, `project_docs/texts_es`: the English and Spanish fixed strings of the documentation pack, read through `project_docs/texts`; `project_docs/texts_wstg_en`, `project_docs/texts_wstg_es`: the same for the pack's security documents (`security_docs`, issue #539).
