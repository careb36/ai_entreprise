# The platform context

Part of the project's guidance for agents; the index is [`CLAUDE.md`](../../CLAUDE.md). Read this document before changing code in `backend/app/services/platform/`.

- **Folder:** `backend/app/services/platform/`
- **Responsibility:** The infrastructure every context may use: the audit writes (AgentService), the advisory locks across replicas, idempotency claims, the Glassroom publisher, the KPI turn records, token usage, API tokens, run secrets, the health check, the knowledge graph reader and, after the migration, the engram processor from backend/memory. It knows nothing of tasks, runs or companies' decisions.
- **May import:** [contracts](contracts.md) (`docs/architecture/contexts.json`, checked by `scripts/check_architecture.py`).
- **Interface** (`public` in `docs/architecture/contexts.json`, ADR 0018, checked by `scripts/check_architecture.py`): `agent_service`, `audit_anchors`, `egress`, `engram_processor`, `forge_policy_setting`, `glassroom`, `hooks`, `locks`, `memory_graph`, `orchestration_metrics`, `protected_paths_setting`, `rework_mentions`, `rfc3161`, `sod`, `teams`, `wstg_catalogue`. Another context imports only these modules and the package; the rest are internal.
- **Modules:** `access_review`, `agent_service`, `api_tokens`, `audit_anchors`, `dns_client`, `egress`, `engram_processor`, `forge_policy_setting`, `glassroom`, `healthcheck`, `hooks`, `idempotency`, `invitations`, `locks`, `login_throttle`, `memory_graph`, `oidc`, `oidc_client`, `orchestration_metrics`, `protected_paths_setting`, `rework_mentions`, `rfc3161`, `run_secrets`, `service_accounts`, `sessions`, `sod`, `sso_connections`, `sso_domains`, `sso_flow`, `sso_group_approvals`, `sso_group_config`, `sso_group_review`, `sso_group_sync`, `sso_groups`, `sso_link`, `sso_metrics`, `sso_team_control`, `teams`, `token_usage`, `wstg_catalogue`
- **HTTP adapters** (`http_adapters` in `docs/architecture/contexts.json`, checked by `scripts/check_architecture.py`, issue #511): `healthcheck` (the LLM proxy's probe). Only these modules of the context may import an HTTP library; each returns data and raises named errors, and the rest of the context calls it.

## Components

### The FastAPI app and its routers

**`backend/app/main.py`** — The FastAPI app: lifespan (workers, JetStream, schema backfills), middleware and the routers it includes. The routes live in `backend/app/routers/` (`sprint`, `sprint_planning` (included by `sprint`), `sprint_crud`, `board_moves`, `agents`, `agent_runs`, `costs`, `inbox`, `messages`, `procedures`, `support`, `workspace`, `github`, `auth`, `enterprise` (with `enterprise_analytics` and `enterprise_agents`, registered beside it and re-exported by it), `providers`, `model_settings`, `webhooks`, `chat_approvals`, `chat_interactions`, `console_producers`, `teams`, `invitations`, `usage`, `sod`, `protected_paths`, `access_review`).

### The schema's version (Alembic)

**`backend/app/migrations.py`** / **`backend/alembic/`** — The schema's version. Alembic owns it: `alembic.ini` and `alembic/env.py` (the models are the target metadata; the URL is the backend's `POSTGRES_*`, or `ALEMBIC_DATABASE_URL`), `alembic/versions/0001_baseline.py` (the baseline: creates each table the models define and the database lacks, adds each column a table lacks, and repeats the old startup's `ALTER TABLE` fixes, indexes and backfills on Postgres, so an empty database, one from `db/init-db/init.sql` and one patched by an older backend all converge). `database.prepare_database` (startup) runs `require_schema_at_head`: a database behind head stops the start with both versions in the error; `DB_AUTO_UPGRADE=true` runs `upgrade_to_head` first. `schema_differences` is what `alembic check` reports (`include_object` leaves `vector_memory` and init.sql's other tables out). The container's `CMD` runs `alembic upgrade head` before uvicorn; the e2e runs `upgrade head` then `check` on Postgres; `backend-tests.yml` runs both on a SQLite file. How to write a migration: `CONTRIBUTING.md` §5.

### The NATS client

**`backend/app/nats_client.py`** — `enable_jetstream()` declares the work-queue streams in `DURABLE_STREAMS` (`task.assign`, `workspace.deliver`, `workspace.delivered`); `publish()` stores durable subjects with a `Nats-Msg-Id`, `consume()` is a durable pull consumer with explicit acks. Without JetStream both fall back to core NATS with a warning. `connect()` takes its credentials and TLS from `nats_auth.connect_options` (`app/nats_auth.py`) and keeps `nats_auth.describe` (method and TLS, no secret); `/health` reports `nats` as `{state, connected, jetstream, authenticated, tls}` (and `jetstream` at the top level, as before).

### The janitor and backups

**`backend/janitor/main.py`** — Background maintenance container (runs daily, `JANITOR_INTERVAL_SECONDS`). Applies the retention settings (`janitor/retention.py`, plain SQL over psycopg2, tested on `sqlite3`) in transactions (each batch of superseded run versions locked `FOR UPDATE`, its guards checked again, and deleted with its verifications or rolled back whole), and rebuilds pgvector indices with `REINDEX CONCURRENTLY`, the one step in autocommit. `scripts/backup.sh` backs Postgres up under `umask 077` (`pg_dump -Fc`, checked, with a checksum; Neo4j through APOC only when enabled, decoded into plain Cypher; the outputs are in `.gitignore`) and restores it (`restore FILE --yes`: into a new database in one transaction, then swapped in by rename, the previous one kept as `<db>_pre_restore_<time>`); CI backs up and restores the e2e database.

### Locks and replicas

**`backend/app/services/platform/locks.py`** / **`replicas.py`** — Several backend replicas may run the workers against one database (issue #328, `docs/OPERATIONS.md`). `locks.held(engine, name, ident)` is a Postgres session-level advisory lock taken with `pg_try_advisory_lock` on a connection held for the work (never waits; a replica that does not get it skips; a dead replica's lock goes with its connection), a process-local table on SQLite. `replicas.claim_todo` claims a task with a conditional `UPDATE … WHERE status = 'todo'` (only the replica whose update matched runs it; the claim is the task's `claimed` event, written in the same transaction), the worker holds `task_lock` while it works on a task (the lock is its lease) and `recover_inflight` returns to `todo` only the `in_progress` tasks nobody holds (a `recovered` event, or `blocked` for a frozen task, through `task_events.record`); `recover_stale` runs it at the start of every review cycle, so a surviving replica dispatches a crashed one's task again within a cycle; `close_once` closes a sprint under its company's lock and `mark_completed` with a conditional update from `active` (one close, retrospective, procedure measurement, proposal round and follow-up), and `triage_slot` triages an escalation once (the `escalated` event is recorded inside it, once). The review cycle (`worker/review._review_cycle`, re-exported by `task_worker`) and the Support and Reviewer agents' cycles run under their own locks.

### Memory architecture

### Memory Architecture

- **pgvector (Postgres)** — RAG short-term semantic memory. Used for code snippet retrieval and context injection. API: `GET /v1/memory/search`, `POST /v1/memory/store`. It needs only Postgres with `vector_memory` (`db/init-db/init.sql`); without that table the memory routes answer 503 with the reason and `/v1/capabilities` says `memory: false`.
- **Neo4j** (optional, `NEO4J_ENABLED`, on by default) — Temporal knowledge graph. Immutable "Engram" nodes record every agent decision with timestamps. Used for file lineage and the graph half of the RAG context. Queried via APOC plugin. Off, nothing is written to it and its readers answer "not recorded" (`services/platform/memory_graph.py`); `MemoryClient(neo4j_driver=None)` works on pgvector alone and raises `GraphNotRecorded` on a graph read. Memory is prompt context, never evidence.

### Auth and multi-tenancy

### Auth & Multi-tenancy

- Company-scoped: all data (agents, sprints, memory, budgets) is namespaced by `company_id`
- RBAC covers both human roles (manager, developer) and AI agent roles (PO, Architect, etc.)
- Passwords hashed with bcrypt directly (`backend/app/passwords.py`); a password chosen at registration (or by any route that sets one, `passwords.check_new_password`) has at least `PASSWORD_MIN_LENGTH` characters (12) and at most bcrypt's 72 bytes, never checked at sign-in so an older short password still works, and login re-hashes a stored hash whose cost is below the current one. `POST /v1/auth/login` issues an HS256 JWT (`JWT_SECRET_KEY`, `ACCESS_TOKEN_EXPIRE_MINUTES`, 15 by default); `auth_deps.get_current_user` resolves it from `Authorization: Bearer` first (an API token or a Bearer access token, never CSRF-checked) and otherwise from the browser's session cookie. Browser sessions (issue #524; threat model and design in [`docs/design/SESSIONS.md`](../design/SESSIONS.md)): login (and the SSO exchange) starts a refresh-token family (`models/session.py`: `session_families`, `refresh_tokens`; migration `0023`; `services/platform/sessions.py`) and sets three cookies (`session_cookies.py`): `fabrique_session` (the access token with the family's `sid` and the CSRF digest, `HttpOnly; Secure; SameSite=Strict; Path=/`), `fabrique_refresh` (`HttpOnly`, `Path=/v1/auth`) and `fabrique_csrf` (readable); the body carries no token. Refresh tokens and the CSRF value are stored only as HMAC-SHA256 under `JWT_SECRET_KEY`. `POST /v1/auth/refresh` (rate-limited by `REFRESH_RATE_LIMIT`) rotates the token exactly once (a conditional update); a used token presented again revokes the family, except within `REFRESH_REUSE_GRACE_SECONDS` while its successor is unused (two tabs: 409, nothing issued); a family ends at `REFRESH_TOKEN_ABSOLUTE_DAYS`. `POST /v1/auth/logout` revokes the family and clears the cookies; `GET /v1/auth/csrf` echoes the CSRF cookie for a page on another host. An access token naming a family is refused once the family is revoked or expired, on every request. An unsafe request authenticated by the cookie needs `X-Fabrique-CSRF` equal to the CSRF cookie and to the digest in the token (403 with `X-Fabrique-CSRF: required` otherwise). A script logs in with `"token_delivery": "bearer"` to get a Bearer access token in the body (no family, no refresh); automation should prefer API tokens. Turning `require_sso` on revokes the password-started families of the members it would refuse (not break-glass Owners), and `DELETE /v1/company/{id}/members/{user_id}` (Owner; the last Owner stays; audited `member_removed`) revokes the removed person's families. CORS allows credentials only with explicit `CORS_ORIGINS` (`security.cors_allows_credentials`). Authentication enforcement is on by default; set `AUTH_REQUIRED=false` only for a local demo without a login. Configure `JWT_SECRET_KEY`, then register and log in through the frontend. Protected routes require a JWT and company roles follow Owner > Manager > Viewer. A company's agents (`/v1/agents`) and its token usage are read by its Viewers; only its Managers create, change or delete an agent, since its prompt, model and budget decide what it does (the agents page is read-only for a Viewer). Likewise only a Manager records the folder a company's agents write to (`POST /v1/discover_team` with a `company_id`; the New company wizard calls it without one), and `/v1/generate` bills only a business unit of the company itself; a sprint's token total counts only its own company's audit rows. Company initialization creates the caller's Owner membership; any other membership comes from an accepted invitation (below).
- Single sign-on over OpenID Connect (issue #512, phase 3; threat model and design in [`docs/design/SSO.md`](../design/SSO.md)). One connection per company (`models/sso.py`: `sso_connections`, `sso_identities`, `sso_flow_states`; migration `0022`), managed only by a signed-in human Owner (`routers/sso_admin.py`; API tokens refused): issuer (Google and Entra ID are presets, `services/platform/sso_connections.py`), client id, client secret encrypted with the Fernet key and never returned, allowed domains (no public mail provider), default role (Viewer or Manager), auto-join, enabled and require SSO; every change and the test (discovery and JWKS, recorded on the row as an observation) is audited without the secret. The flow (`routers/sso.py`, public, rate-limited by `SSO_RATE_LIMIT`): `GET /v1/auth/sso/{slug|email|domain}/start` stores a hashed one-time `state` with the PKCE verifier and nonce, sets an HttpOnly SameSite=Lax binding cookie and redirects; `GET /v1/auth/sso/callback` consumes the state once, checks the cookie, exchanges the code (`services/platform/oidc_client.py`, the HTTP adapter) and validates the ID token itself (`services/platform/oidc.py`: asymmetric signature against the cached JWKS, `iss`, `aud`/`azp`, `exp`/`iat` with skew, nonce, `email_verified` when sent); `services/platform/sso_flow.py` resolves the account by `(issuer, sub)`, links an existing account by email once, in an allowed domain and only when the account is a member of this company and of no other (any Owner can run a provider and assert any address, so an IdP is trusted only within its company; the linked account loses its password unless it is an Owner here), never adopts an existing account through auto-join, creates a new one only with auto-join, takes the role from the membership, and writes an `sso_sign_in` audit row with the observed claims and the outcome; the browser lands on the frontend's `/login/sso` with a 60-second one-time code that `POST /v1/auth/sso/exchange` trades for the same browser session `/v1/auth/login` starts (cookies, issue #524). Requiring SSO is refused until an Owner has signed in through the enabled connection; then `/v1/auth/login` refuses a member of that company (403, after the password check) unless the Owner is in `SSO_BREAK_GLASS_EMAILS` (audited `sso_break_glass_login`). Allowed domains are verified by DNS (`services/platform/sso_domains.py`; `models/sso.py`: `sso_domains`, `sso_domain_checks`; migration `0049`): saving the connection issues a random token per company and domain; the Owner publishes `la-fabrique-domain-verification=<token>` as a TXT record at `_la-fabrique-verify.<domain>` and asks for a check (`GET /v1/companies/{id}/sso/domains`, `POST …/sso/domains/{domain}/check`, `routers/sso_domains.py`, Owner, rate-limited by `SSO_RATE_LIMIT`), which `services/platform/dns_client.py` (the resolver adapter, dnspython) answers; every lookup is an `sso_domain_checks` row with the time, trigger, outcome and the strings seen, and each status change an audit row (`sso_domain_verified`, `sso_domain_unverified`). Only a verified domain, or a legacy one (listed before `0049`) during `SSO_LEGACY_DOMAIN_GRACE`, lets SSO create or link an account (`domain_unverified` otherwise); an identity already linked keeps signing in. A transient DNS failure changes nothing; the re-check (`run_rechecks`, every `SSO_DOMAIN_RECHECK_HOURS`, lock `sso-domain-recheck`) unverifies a record that is definitely gone. A domain another company verified cannot be listed (409), and a newer proof re-checks the older claim first. Each re-check, and each cycle of the loop, is counted for `/metrics` by outcome (`services/platform/sso_metrics.py`, issue #684; never by company, domain or person; `docs/OPERATIONS.md`). A signed-in person links their account to a company's provider themselves (`services/platform/sso_link.py`, `routers/sso_link.py`; the frontend's `/account`): `POST /v1/auth/sso/link/start` (browser session only, CSRF, a member of the company) stores a `link` state whose binding is the HttpOnly binding cookie joined to the session's public id, and the same callback finishes it only while that browser and a live session of the person match, the provider's email is the account's, its domain is verified by DNS (no legacy grace) and the subject is nobody else's; the password is kept, and each attempt is an `sso_identity_link` audit row. `DELETE /v1/auth/sso/identities/{id}` unlinks one's own identity only while another way to sign in remains (a password no SSO requirement refuses, or another identity); `GET`/`DELETE /v1/companies/{id}/sso/identities[/{id}]` (Owner) lists and unlinks the identities of the company's connection and ends the person's SSO-started sessions; each unlink is an `sso_identity_unlink` row, committed with the change it records; a unique index on `sso_identities (user_id, issuer)` (migration `0050`) holds one identity per account and provider, so a racing link ends as `identity_conflict`.
- Teams (issue #512, phase 5; design and threat model in [`docs/design/TEAMS_AND_USAGE.md`](../design/TEAMS_AND_USAGE.md)). A company's Owner groups its members in teams (`models/team.py`: `teams`, `team_members`; migration `0029`); a team has a name, a description and a role, Viewer or Manager, never Owner. A member's **effective role** is the higher of their own membership role and the roles of their teams in that company (`services/platform/teams.py`: `effective_role` is pure, `member_role` reads it); a team never makes anyone a member (no `company_members` row, no role) and never reaches another company (both rows' `company_id` checked), and a row holding any other role is ignored. `auth_policy.require_company_role` checks the effective role, so a team raises access on every company route and leaving it lowers it on the next request; the API token cap (`routers/api_tokens.py` when minted, and `api_tokens.verify` on every use: a token above its creator's current effective role, or whose creator left, is refused and audited `api_token_refused`; the creator is found by account id, `api_tokens.created_by_user_id` (migration `0048`), and only a row from before it that the migration could not match is found by email), the brief's recipients (`brief_mail.recipients`) and `/v1/auth/me` (`effective_role` beside `human_role`) read it too. `routers/teams.py` (`GET`/`POST /v1/companies/{id}/teams`, `PATCH`/`DELETE …/teams/{team_id}`, `PUT`/`DELETE …/teams/{team_id}/members/{user_id}`) answers only a signed-in human Owner (an API token is refused whatever its role) and audits every change (`team_created`, `team_updated` with what changed, `team_deleted`, `team_member_added`, `team_member_removed`) under `human:<email>`; only a member of the company joins a team. The usage report that reads teams is in [models](models.md).

- Segregation of duties, the access review and the service accounts (issue #543; design and threat model in [`docs/design/SEGREGATION_OF_DUTIES.md`](../design/SEGREGATION_OF_DUTIES.md)). `services/platform/sod.py` holds the rule (`decide`, pure: an approval by the account that asked for or wrote the work is refused, for the actions the company's mode holds: `high_risk` by default, `all` or `off`) and `enforce`, which the approval points call with the requesters they read from records (`services/loop/sod_requesters.py`; an approving review of a sprint's integration is one, `services/release/integration_review.py`); a refusal is a committed `sod_refused` audit row and a 403. An API token acts for its creator. The single-person exception is an Owner's explicit, audited grant with a reason, honoured only while exactly one member can approve (effective role Manager or Owner, teams counted); each use is `sod_exception_applied`. `routers/sod.py` (`GET`/`PUT /v1/companies/{id}/sod/policy`, `POST`/`DELETE …/sod/exception`: a signed-in human Owner only, every change audited; `GET …/sod/report`: Manager, from [management](management.md)). `services/platform/access_review.py` and `routers/access_review.py` (`GET`/`POST /v1/companies/{id}/access-review`, Owner only): every member with own, team-derived and effective role, SSO and chat links and observed last activity, and every working API token, each confirmed or removed; removals apply (membership and teams dropped, sessions ended, tokens revoked), the review is a row (`models/sod.py`: `access_reviews`, with `sod_policies`; migration `0036`) and `access_review_completed`; the schedule is pure (`scheduled`, `due` for 14 days, then `missed`; a late review is `on_time: false`), every `review_interval_days` (90). `services/platform/service_accounts.py` (`GET /v1/companies/{id}/service-accounts`, Owner only) lists API tokens, the webhook (host only), chat connections, the SSO client, model providers and GitHub webhooks with owner, scope and age, and the deployment's NATS method and LLM proxy token presence, never a value. The eight routes are declared in `docs/architecture/authorization.json` (Owner, the report Manager) and their bodies (`PolicyUpdate`, `ExceptionGrant`, `ReviewCompletion`) are `schemas.RequestModel`s.
- Always public: `/health`, registration/login, refresh, logout and the CSRF echo (each checks the session cookie itself), the SSO start, callback and exchange, the HMAC-signed GitHub webhook, the Slack and Teams inbound endpoints (`/v1/integrations/{slack|teams}/{public_id}/…`, each request verified by the platform's HMAC and acting only for a linked account with its role here; [integrations](integrations.md)), support bug reporting/chat, `/v1/models`, `/v1/capabilities` (feature flags only, no company data), and the retired `/v1/approve_task` (410). Glassroom SSE cannot take an Authorization header (EventSource sends none): with `AUTH_REQUIRED` it takes a five-minute `ticket` for one sprint from `POST /v1/sprints/{id}/stream_ticket` (Viewer), and checks the holder's membership again when it is used; the frontend asks for a new one on every connection. `/v1/auth/me` always requires a JWT. Audit writes and memory stores resolve company ownership from authorized membership and existing interactions, never payload metadata; callers with multiple memberships should select a `company_id` query parameter. Audit verification, memory search, and lineage use column-backed Viewer scoping. Legacy NULL-company evidence is flagged and included only without a company filter (authenticated when `AUTH_REQUIRED=true`). Startup backfills historical company metadata into the audit/vector columns and Neo4j properties. Help-desk tickets are not company data: support admins (`SUPPORT_ADMIN_EMAILS`) see and update all of them and download the logs; other authenticated users see only their own (matched by account email, 403 for another reporter, 404 for another's ticket). With `AUTH_REQUIRED=false` and no token, the desk stays open as in a local demo. When `SUPPORT_AGENT_ENABLED`, the Support agent triages open tickets first (`suggested_severity`, `suggested_category`, `agent_reply`, `triaged_by`), and a support admin decides.
- Who may call each route is data, `docs/architecture/authorization.json` (issue #541): public, signed, authenticated, support admin or the minimum company role, checked by `backend/tests/test_authorization_matrix.py`, which fails on an undeclared route. Password login is limited per address (`LOGIN_RATE_LIMIT`) and per account with a doubling backoff (`services/platform/login_throttle.py`; making room in its bounded record drops an unlocked record first, so failures at other addresses cannot evict a lock); registration answers alike for a new and a taken email. Access tokens carry `iss` and `aud` (`JWT_ISSUER`, `JWT_AUDIENCE`), required when checked. A URL a company chose (the notification webhook, an OIDC issuer, a research fetch) is reached through `services/platform/egress.py`: resolved once, refused unless every address is public (mapped, NAT64, 6to4 and Teredo forms included), and connected to by that address with the host in `Host` and TLS SNI, so DNS rebinding cannot steer it (`backend/tests/test_ssrf_vectors.py`).

- Invitations (WSTG-v42-IDNT-04; `models/invitation.py`: `company_invitations`, migration `0046`; `services/platform/invitations.py`; `routers/invitations.py`). `POST /v1/company/invite` (a signed-in person, Manager or above, never an API token) answers 202 with the same body whether or not the address has an account or is already a member, and adds nobody: it records a pending invitation (the company, the normalised address, the role, the inviter, an expiry of `INVITATION_TTL_HOURS`, and a single-use token stored only as its sha256 and shown once in the answer for a link). A Manager invites Viewers and Managers; only an Owner invites an Owner. A new invitation of the same address revokes the pending one. The invitee sees theirs at `GET /v1/invitations` once signed in and accepts (`POST /v1/invitations/{id}/accept`, or `POST /v1/invitations/accept` with the token, which works only for the invited address) or declines (`.../decline`); accepting, declining and revoking (`DELETE /v1/companies/{id}/invitations/{invitation_id}`, Manager, up to their role) are conditional updates on `status = 'pending'`, so an invitation is used once; an expired one answers 410; one that is not the caller's, 404. Only acceptance creates the `company_members` row. Audited: `invitation_created`, `invitation_accepted`, `invitation_declined`, `invitation_revoked` (never the token). `GET /v1/companies/{id}/invitations` lists the pending ones for Managers.
- Email addresses are compared by one rule, `services/contracts/emails.py` (strip, lower-case): registration, sign-in, invitations and lookups use it, so `Ana@x` and `ana@x` are one account. Migration `0045` normalised the stored addresses and added the unique index `ux_users_email_lower` on `lower(email)`; it stops, naming the colliding ids, when two accounts would share an address (`docs/OPERATIONS.md`). Registration attempts the insert for a taken address too (the unique index refuses it), so both paths do one bcrypt hash and one insert and answer alike.
- The client's address behind a reverse proxy: `security.TrustedProxyMiddleware` (outermost) replaces `request.client` with the right-most `X-Forwarded-For` address that is not a listed proxy, only when the connection comes from one in `TRUSTED_PROXY_IPS` (addresses or networks; empty, the default, trusts none and ignores the header; a malformed entry stops startup). The per-address limits (`get_remote_address`) then key on the real client. The image runs uvicorn with `--no-proxy-headers`, so the app's rule is the only one (`docs/OPERATIONS.md`, Behind a reverse proxy).

### Other modules

- `agent_service` (`AgentService`): publishes `workspace.generate` to NATS and writes the audit entries, to the JSONL file and the `audit_log` table.
- `idempotency` (`claim_event`, `prune_expired`): one claim per NATS event in `processed_events`, so a redelivered message is skipped; a database failure lets the work proceed.
- `orchestration_metrics`: writes each agent turn in the shape `GET /v1/analytics/orchestration_health` reads (QA rework rate, Developer tokens, Architect consults). It also counts the deliveries the gate before QA sent back, by the problem `delivery_gate` named (`count_gate_refutations`, issue #549), parsed from the Verifier's `NEEDS WORK: <problem> —` text since platform may not import the evidence; `tests/test_gate_refutations.py` pins that text to what the loop writes, and `GET /v1/analytics/gate_refutations` serves the count, which the Sprints page shows per problem and per week as an observation (`components/GateRefutations.tsx`, `services/gateRefutations.ts`). It never mixes with `count_qa_rework_requests`.
- `rework_mentions`: the rework requests whose text names a missing module, package or import (issue #549), the before/after measure of the grounded check: which task events are rework requests (`rework_request_source`: a `reviewed` needs-work verdict, a person's review, a person's or the Manager agent's send-back; never the system's notes), by source (`gate`, `person`, `agent_reviewer`), and the matching rule (`MISSING_MODULE_RULES`, tested in `tests/test_rework_mentions.py`). The text is a reviewer's claim, so the counts say what reviewers wrote, not what was missing; `GET /v1/analytics/missing_module_mentions` splits them at a cutoff, by default #503's merge (`GROUNDED_CHECK_SHIPPED_AT`).
- `run_secrets`: values that live only for one task run (issue #357), stored encrypted and handed to the run's environment (`env_for_task`); the routes are `routers/run_secrets.py`.
- `egress` (`pin`): where an outgoing request may go. It resolves a company-chosen URL's host once and refuses a private address (SSRF); the webhook, the OIDC client and the research fetches use it.
- `sessions`: browser sessions as refresh-token families, each token rotated exactly once (issue #524, `docs/design/SESSIONS.md`).
- `oidc`, `oidc_client`, `sso_connections`, `sso_flow`, `sso_link`, `sso_domains`, `dns_client`: single sign-on, described under Auth and multi-tenancy above; `oidc_client` is the HTTP adapter, `oidc` validates the ID token, `sso_domains` verifies the allowed domains by DNS, `sso_metrics` counts its re-checks for `/metrics`, and `dns_client` is its resolver adapter (returns data, raises `DnsNameNotFound` or `DnsUnavailable`; not in `http_adapters`, whose checker knows only HTTP libraries).
- `sso_groups`, `sso_group_sync`, `sso_group_config`, `sso_group_approvals`, `sso_team_control`, `sso_group_review`: identity-provider groups mapped to teams (issue #703; design and threat model in [`docs/design/SSO_GROUP_MAPPING.md`](../design/SSO_GROUP_MAPPING.md); `models/sso_groups.py`, migration `0054`). Per SSO connection the Owner turns the mapping on, names the ID token claim (`groups`; `roles`, Entra's app roles, proposed for the `entra` preset), sets a cap (`Viewer` by default, `Manager` at most, a check constraint keeps `Owner` out) and writes `(group value, team)` pairs (`GET`/`PUT /v1/companies/{id}/sso/group-mappings`, `routers/sso_groups.py`). A team is `owner`- or `sso`-managed (`teams.membership_source`); only SSO-managed teams of the company, at or under the cap, are mapped; Google is refused until a Directory sync exists (#716); Entra group values are GUIDs, lower-cased. `sso_groups` is pure: it classifies the claim (`present`, `empty`, `absent`, `overage` from `_claim_names` or `hasgroups`, `malformed` past 1000 values or 256 characters) and evaluates the adds, removals and skips; an absent, overage or malformed claim changes nothing, only a present empty list removes. `sso_group_sync.apply_sign_in` runs in `sso_flow.finish_login` under the transaction lock `sso-groups` (`locks.in_transaction`) and writes an append-only `sso_group_observations` row (matched values, count, the backend's sha256, never an unmatched value), the `team_members` rows, the periods (`sso-mapping:<id>`, `started_observation_id`/`ended_observation_id`) and a signed `sso_group_sync` audit row, all committed with the `sso_sign_in` row (`audit_interaction(commit=False)`); a token older than the last applied one is `stale_token`; nothing is fetched for an overage. `sso_group_config` saves the configuration and removes, with a pair, the memberships it alone justified; a pair to a Manager team is a pending `sso_manager_approvals` row that `sso_group_approvals` lets a second Owner approve (self-approval is a 403 and a `sod_refused` row; the backend's `proposal_sha256` and a 7-day expiry bind it), or the only Owner confirm alone (no Owner removed or demoted in 30 days, the team's name typed back, a reason). `sso_team_control` (`routers/team_sso.py`, `routers/teams.py`): the conversion preview and the switch (`preview_stale`; members kept as `sso_manual_exceptions`), the member routes on an SSO-managed team (`team_managed_by_sso`, `use_break_glass`), the break-glass exclusion (`sso_team_exclusions`, the person removed at once, every other Owner notified through the outbox on `company.owner_notice`, lifted by any Owner with a reason) and the refusal to raise a mapped team's role (`team_mapped`). `sso_group_review` adds exclusions, manual exceptions and single-Owner Manager pairs to the access review. Every route is a signed-in human Owner's (API tokens refused) and declared in `docs/architecture/authorization.json`.

## Audit anchors

**`services/platform/audit_anchors.py`**, **`services/platform/rfc3161.py`**, `models/audit_anchor.py` (issue #542; [`docs/design/AUDIT_ANCHORS.md`](../design/AUDIT_ANCHORS.md); migration `0032`). The chain (`audit_chain.py`) is keyed by the factory's own `AUDIT_SIGNING_KEY`; an anchor (`audit_anchors`: company, `kind` `webhook`/`tsa`/`customer_key`, `chain_seq`, `chain_hash`, `anchored_at`, `reason`, `status` `pending`/`delivered`/`verified`/`failed`, `external_ref`, `key_fingerprint`, `receipt`) records the head outside the factory. Every kind covers one pinned `statement` (company, seq, chain hash, time to the second). `rfc3161` builds the `TimeStampReq` and checks a token with a small DER reader (no indefinite lengths, high tags or trailing bytes; 64 KiB) and `cryptography`: signature by the pinned certificate's key over the signed attributes, imprint, nonce, `genTime` within the certificate, time-stamping EKU, ESS signing certificate. `record_customer_signature` stores a head the customer signed with an active Ed25519 key from `audit_anchor_settings.customer_keys`, once the head matches the chain. `coverage` re-checks every anchor against the chain as it is now (`row_missing`, `hash_mismatch`, `token_invalid`, `signature_invalid`, `key_unknown`) and reports the covered segments (`verified` or `claim`), `verified_through`, `covered_through`, the `uncovered` tail and a status; `GET /v1/audit/chain` carries it as `anchors`. The chain's own rows are not changed. Taking and sending anchors: [integrations](integrations.md#audit-anchors).
