# The workspace context

Part of the project's guidance for agents; the index is [`CLAUDE.md`](../../CLAUDE.md). Read this document before changing code in `backend/app/services/workspace/`.

- **Folder:** `backend/app/services/workspace/`
- **Responsibility:** The client of the workspace daemon over NATS: requests and their errors, the delivery test run, the project inspection and snapshot, the sandbox modes, the stack profiles and the Git workflow's delivery spec. It sends and returns observations; it never judges them.
- **May import:** [contracts](contracts.md), [platform](platform.md) (`docs/architecture/contexts.json`, checked by `scripts/check_architecture.py`).
- **Interface** (`public` in `docs/architecture/contexts.json`, ADR 0018, checked by `scripts/check_architecture.py`): `daemon_liveness`, `delivery_commands`, `git_workflow`, `project_profile`, `sandbox`, `workspace_daemon`. Another context imports only these modules and the package; the rest are internal. Nothing is allowlisted: the loop's delivery checks reach the install, the test run, the folders' commands and the application check through `delivery_commands`, the one entry point for a delivery's daemon commands.
- **Modules:** `browser_images`, `daemon_abilities`, `daemon_liveness`, `delivery_commands`, `dependency_install`, `folder_commands`, `git_workflow`, `project_profile`, `run_log_reader`, `run_logs`, `sandbox`, `sandbox_http`, `sandbox_manager`, `stack_profiles`, `stack_roots`, `workspace_daemon`, `workspace_snapshot`.
- **HTTP adapters** (`http_adapters` in `docs/architecture/contexts.json`, checked by `scripts/check_architecture.py`, issue #511): `sandbox_http` (the pre-QA sandbox's health and validate endpoints, raising `SandboxUnreachable`; `sandbox_manager` calls it). Only these modules of the context may import an HTTP library; each returns data and raises named errors, and the rest of the context calls it.

## Components

### The workspace daemon

**`vscode-daemon/daemon.py`** — The workspace daemon: a Python process that runs natively on the user's macOS, Linux or Windows machine (started by `scripts/start-daemon.*`, reconnects to NATS on its own). It answers `workspace.generate` (write files, reply with the sha256 read back from disk and the diff against the bytes that were there, `file_diff.py`; with a `git` spec, as a commit on the task's branch in a worktree, `git_workspace.py`, delivered with a snapshot instead and `git_workflow_skipped: "not a repository"` when the folder is not a repository; without one, with a `snapshot` that undoes it, `delivery_snapshot.py`; `delivery.py` picks the two and adds the project's paths, `workspace_read.project_files`, for the Verifier's import check), `workspace.execute` (run a command the command policy accepts, `command_policy.py`, where the sandbox's rules put it, `shell_exec.py` and `sandbox.py`: a request without `sandbox` reads as `host`, so `FABRIQUE_SANDBOX_REQUIRED` raises it to its mode, `forced_by_daemon`, or refuses it when that mode cannot run, never the host; without the floor its reply is unchanged, no `sandbox` key; purposes `test`, `install`, `check` and `assistant`; issue #525, `backend/tests/test_sandbox_floor.py`), `workspace.capabilities`, `workspace.status` (the machine, the daemon's version and protocol version, `daemon_status.py`), `workspace.browse` (folder picker) and `workspace.inspect` (canonical path, git remote/branch, file snapshot for stack detection; both `host_folders.py`), `workspace.hash` (the sha256 of named files as they are on disk, `file_hash.py`; the backend keeps QA's acceptance tests intact with it), `workspace.list` / `workspace.read` / `workspace.search` / `workspace.find` (the Developer's read-only tools on the project, bounded, `workspace_read.py`), `workspace.map` (the repository map: the project's definitions ranked by use, cached per file set, `repo_map.py`), `workspace.signatures` (the signatures of named module-level Python definitions, for the Verifier's symbol findings: at most 50 paths and 400 names a request, each file's sha256, each name `found` with its parameters (names and whether each has a default, never a value), `unknown` (decorated, an inherited constructor, bound twice) or `missing`, a file that does not parse said so; read with `repo_map`'s guards, never a secret, a symlink out or VCS metadata, `signatures.py`), `workspace.related` (the files around a task's seeds and the names that tie them, from the repository map's parse cache and edge rule, paths, names and sha256 only, never contents, `code_graph.py`; [tools](tools.md)), `workspace.edit` / `workspace.edit.finish` (the Developer's checked edits, a working copy per task, `workspace_edit.py`), `workspace.git.publish` (push a `fabrique/` task branch to `origin` with the person's credentials and open a draft pull or merge request with `gh` / `glab`, else the compare page), `workspace.git.merge` (merge a `fabrique/` branch into a base branch of the local repository, no remote, `local_merge.py`), `workspace.git.diff` (read-only: what a sprint's integration brings into its base, the files and hunks between the merge base and the pinned commit with each side's sha256, for a person's review of the integration, `git_diff.py`), `workspace.git.base_status` (whether the folder is a repository and how its base branch stands against its remote, fetched now, `git_base.py`; the settings page reads it), `workspace.git.reviews` (the comments people left on that request, read with `gh api` / `glab api`, `platform_reviews.py`), `workspace.app.check` (start the application in the sandbox, wait for its port, probe it, with `security_probe: true` send it the security probes and record the answers, `security_probe.py`, run an e2e command, stop it, `app_run.py`), `workspace.sandbox.reset` (remove a project's dependency cache volume, only the daemon's own by name and label, and lift its quarantine, `sandbox_cache.py`), `workspace.console.prepare` / `workspace.console.collect` (a console producer's worktree, then the files its CLI changed read back with their sha256 and the worktree put back, `console_run.py`), `workspace.git.integrate` (a sprint's task branches merged into `fabrique/sprint-<id>` in a worktree, `sprint_integration.py`), `workspace.undo` (undo a delivery made without a `git` spec from the snapshot `workspace.generate` kept, `delivery_snapshot.py`), and consumes the JetStream queue `workspace.deliver` for files queued while it was offline, reporting on `workspace.delivered`; it publishes `workspace.heartbeat` (below). Its dependencies are `nats-py` and `nkeys` (for a creds file or an nkey seed), declared in `requirements.in` and locked with every sha256 in `requirements.txt` (`uv pip compile --universal --generate-hashes`), which the Dockerfile and `scripts/start-daemon.*` install with `--require-hashes` and `pip-audit` reads in CI (issue #522). `nats_connect.py` connects it with the credentials and TLS the environment names, replies under `_INBOX.daemon` (passed explicitly to the pull consumer: nats-py 2.3.1, the image's earlier pin, ignored the connection's prefix there), and waits for the backend to create the delivery streams instead of creating them.

### The protocol, its version and the heartbeat

**`vscode-daemon/protocol/PROTOCOL.md`** / **`vscode-daemon/daemon_status.py`** / **`services/workspace/daemon_liveness.py`** — The wire between the backend and the daemon is versioned: [`vscode-daemon/protocol/PROTOCOL.md`](../../vscode-daemon/protocol/PROTOCOL.md) describes protocol version 1 (transport, every subject with its request and reply, the refusal codes and what the backend does with each, observed failures apart from refusals), with a JSON Schema per subject in `vscode-daemon/protocol/schemas/v1/` and recorded request/reply pairs in `vscode-daemon/protocol/fixtures/v1/` that both sides replay (`test_daemon_protocol.py`, `test_daemon_protocol_client.py`); a subject without a schema, or a schema without a subject, fails the tests. The design is taken from AixleHQ/flow's `runner/protocol/` (design only). The daemon reports `protocol_version` and `protocol_min` in `workspace.status` and publishes `workspace.heartbeat` every `FABRIQUE_HEARTBEAT_SECONDS` (≤25 s) with its `daemon_id`, protocol version and a monotonic `sequence`. The backend (`daemon_liveness`) subscribes, records when it *observed* each heartbeat on its own clock, and decides `online` / `stale` / `offline` (`DAEMON_HEARTBEAT_STALE_SECONDS`, `DAEMON_HEARTBEAT_OFFLINE_SECONDS`); without a heartbeat the request to `workspace.status` is the fallback. It serves a daemon whose range overlaps `SUPPORTED_PROTOCOL`; one outside it is `incompatible` with a reason naming the side to update (in `GET /v1/workspace/status`, as `DaemonIncompatible` from `daemon_request`, and as a delivery's evidence `reason`, never a generic timeout), and one that reports no version is an older daemon, served as before. What the daemon says about itself is kept under `reported_by_daemon`, apart from what the backend observed. **Abilities announced, not guessed** (#315, `PROTOCOL.md` §2.1): the daemon announces the subjects it serves and the optional fields it honours (`vscode-daemon/abilities.py`, `abilities` in `workspace.status` and every heartbeat, versioned by `abilities_version`); the backend keeps it per daemon under `reported_by_daemon.abilities` (`daemon_abilities.parse`, bounded) and `daemon_liveness.announces(subject, feature)` answers true, false or none (no daemon heard, an older one among them, or they disagree). `signature_lookup` and `delivery_checks.guard_test_files` do not ask daemons that announce no `workspace.signatures` / `workspace.hash`, and `run_logs.observe` words a reply without `full_log` from it; without an announcement each keeps its earlier guess. The announcement is a claim: it never stands in for what a run's reply shows. The folder picker and the project check moved from `daemon.py` to `vscode-daemon/host_folders.py`.

### The sandbox: which image ran, and the dependency cache

**`vscode-daemon/sandbox.py`** / **`sandbox_image.py`** / **`sandbox_cache.py`** / **`services/workspace/sandbox.py`** — Agent code runs in the mode the company asked for (`host`, `container`, `bwrap`) and the daemon reports what it applied. In container mode it also records **which image ran** (`sandbox_image.py`): before the run it asks the runtime (`image inspect`, Docker or Podman) for the image's content ID and registry digest and starts the container from that ID; an image the run itself pulled is observed after it (`observed: after_run`); host and bwrap say why there is no image (`image_identity.reason`), never an empty success. With `cache` in the request (`DELIVERY_SANDBOX_CACHE`), a named volume per project, `fabrique-cache-<key>` labelled `dev.fabrique.sandbox-cache=<key>`, holds the package managers' caches at `/fabrique-cache` (`sandbox_cache.py`): kept after a run, removed after a failed install (the backend's install request says `purpose: install`), quarantined after three failed installs in a row with the reason in each report and in `workspace.status`, until `POST /v1/companies/{id}/sandbox/cache/reset` (Manager, audited, `sandbox.reset_cache`) removes it through `workspace.sandbox.reset`; a same-named volume without the label is never used or removed. `GET /v1/workspace/status` relays the daemon's `sandbox_cache` (allowed, and the projects quarantined). **The environment volume** (#315): with `environment` and `scope` in the request (`DELIVERY_SANDBOX_ENV`; the backend's scope is `company:<id>`, `sandbox.scope_for`), a second volume, `fabrique-env-<key>` labelled `dev.fabrique.sandbox-env=<key>` and `dev.fabrique.sandbox-env.project=<project key>`, keeps what an install leaves outside the worktree at `/fabrique-env`: `PYTHONUSERBASE` (pip's user installation), `POETRY_VIRTUALENVS_PATH`, `WORKON_HOME`, `GOPATH`, `GOMODCACHE` and, for an install, `GOCACHE`, its `bin` folders appended to `PATH` after the image's (`sandbox_cache.prepare_env`). Its key is the project as for the cache, the company's scope, the image asked for and the sha256 of the Python and Go manifests in the run's folder and its direct folders, so no two companies, projects, images or manifest sets share one. Only `purpose: install` mounts it read-write (and creates it); a test run, the application check and an assistant mount it read-only, and not at all before an install filled it (`state: absent`). A failed install removes it, three in a row quarantine the project for that company, and the cache's reset (same endpoint, `workspace.sandbox.reset` with `scope`) removes every environment of the project and company and, once they are gone, drops the company's `container:` install records so the next delivery installs again; at most three are kept per project and company. Reported as `sandbox.environment`, phrased by `sandbox_report.check_sandbox`; `GET /v1/workspace/status` relays `sandbox_environment`. `FABRIQUE_SANDBOX_ENV=off` on the daemon's machine refuses it. Tests: `vscode-daemon/tests/test_sandbox_env.py`. The design and what was taken from AixleHQ/flow: [`docs/design/EXECUTION_ENVIRONMENT.md`](../design/EXECUTION_ENVIRONMENT.md).

**`vscode-daemon/images/browser/`** / **`browser_probe.py`** / **`run_logs.py`** / **`services/workspace/run_logs.py`** (#315) — **The browser sandbox image**: Node, the Playwright of its `package-lock.json` (installed with `npm ci`, each package checked against its integrity hash) and the Chrome Headless Shell build that Playwright launches headless, downloaded from the Playwright CDN and checked against a sha256 pinned per architecture (`TARGETARCH`, amd64 and arm64), the base image pinned by digest, run as a non-root user, nothing downloaded at run time. With `DELIVERY_BROWSER_IMAGE` naming it, the application check runs a browser e2e command (QA's smoke suite, or the e2e command of a `web` profile) in that image in container mode; the run records its content ID and digest like every container run. `images.yml` publishes it on every `v*` tag for `linux/amd64` only (#529), and operators pin `DELIVERY_BROWSER_IMAGE` to the digest the run prints, never a tag (`docs/OPERATIONS.md`, Releasing); `browser-image-probe.yml` (manual) is where an arm64 variant is built under QEMU and probed before it is ever published. **The browser probe**: with `browser_probe: true` on `workspace.app.check`, before the e2e command the daemon runs `probe-browser.js` with `node -e` where the command runs (the project's folder, or inside the container) and replies `browser_probe` (`available`, `from: image` when it used the image's own pinned Playwright, `from: project` when the project's, the versions or the reason, `observed_by: daemon`). **Full logs**: with `full_log: {bucket, name}` on `workspace.execute` or `workspace.app.check` (sent by the install, the tests and the application check when `DELIVERY_FULL_LOGS` is on and the bucket exists), the daemon keeps each stream whole up to `FABRIQUE_FULL_LOG_MAX_MB` (50 MiB) in a temporary file while the command runs, uploads it as `<name>/<stream>` to the JetStream object store `FABRIQUE_RUN_LOGS` (namespaced; created by the backend with JetStream, `nats_client.run_log_bucket`, objects expiring after `FULL_LOG_RETENTION_DAYS`, the oldest dropped beyond `FULL_LOG_BUCKET_MAX_MB`), and replies with the objects and their byte counts, never a hash. The backend reads each object back, computes its size and sha256 (`run_logs.observe`) and records `full_log` on the record beside the tail; a daemon from before full logs, the setting off or no JetStream give `full_log: {observed: false, reason}`. The broker lets the daemon's user write to that one bucket and read an object's metadata, never purge or delete (`scripts/nats_config.py`). **Reading a full log back** (`run_log_reader.py`, `routers/run_logs.py`): `GET /v1/agent_runs/{id}/logs` lists the `full_log` objects a run's verifications recorded; `GET .../logs/{log_id}` (Viewer) reads one again from the backend's own bucket, only by a name of the shape `run_logs` asks for, into a spool, computes its size and sha256 over exactly the bytes it then streams and compares them with the recorded sha256: `X-Log-Integrity: matched | mismatched` with both hashes and `X-Log-Observed-By: backend`, a 410 `missing` when the store no longer holds it, a 503 `unavailable` when it cannot be read; no hash from the daemon, the client or the store's metadata. The run page's `RunLogViewer` shows it. **Install state per sandbox mode**: `Company.dependency_installs` is keyed by folder for `host` (the key records had before) and `<mode>:<folder>` for `container` and `bwrap` (`dependency_install.install_key`), so a company that moves from host to container mode installs again. **The security probe** (#540): with `security_probe: true` on `workspace.app.check` (the loop always asks, `services/loop/delivery_checks.py`), once the application listens the daemon sends it a fixed set of requests and replies `security_probe` (`vscode-daemon/security_probe.py`, standard library only): the probe path's headers and parsed cookies (a value only as its length), the answers to a foreign `Origin` with and without a cookie and to a preflight, OPTIONS and TRACE, a missing path and a malformed body (the head of each body), `/.git/HEAD` and `/.env` (the names it assigns only); in host mode from the daemon's own process, in container mode with `python3 -c` inside the application's container, read back and bounded again (an image without `python3` is `observed: false` with the reason). It records, the evidence judges ([evidence](evidence.md), the security probe); the fields are in `PROTOCOL.md` §5.1.1. **The cache in the application check**: with `cache` in the request, the application check's container mounts the project's dependency cache volume as a test run does (`after: kept`).

JetStream's object store has no byte-range read, so `read_range` lists the object's chunks headers only (an ordered consumer with `headers_only`, which gives each chunk's size and stream sequence) and fetches by sequence only the chunks the range overlaps, into a spool of the range's size: the whole object is never read or held for a range. The logs live only in the backend's object store (the daemon keeps none once uploaded), so that is the one store ranges are served from. The run page's `RunLogViewer` shows it; a log over 256 KiB opens in `RunLogPieces`, from its tail with earlier pieces on demand, and offers the full read to verify it. **Install state per sandbox mode**: `Company.dependency_installs` is keyed by folder for `host` (the key records had before) and `<mode>:<folder>` for `container` and `bwrap` (`dependency_install.install_key`), so a company that moves from host to container mode installs again. **The security probe** (#540): with `security_probe: true` on `workspace.app.check` (the loop always asks, `services/loop/delivery_checks.py`), once the application listens the daemon sends it a fixed set of requests and replies `security_probe` (`vscode-daemon/security_probe.py`, standard library only): the probe path's headers and parsed cookies (a value only as its length), the answers to a foreign `Origin` with and without a cookie and to a preflight, OPTIONS and TRACE, a missing path and a malformed body (the head of each body), `/.git/HEAD` and `/.env` (the names it assigns only); in host mode from the daemon's own process, in container mode with `python3 -c` inside the application's container, read back and bounded again (an image without `python3` is `observed: false` with the reason). It records, the evidence judges ([evidence](evidence.md), the security probe); the fields are in `PROTOCOL.md` §5.1.1. **The cache in the application check**: with `cache` in the request, the application check's container mounts the project's dependency cache volume as a test run does (`after: kept`).

**Grading in the sandbox** (`scripts/bench/sandbox_grading.py`, rsi-loop PR 12; threat model [`docs/design/SANDBOX_GRADING_THREAT_MODEL.md`](../design/SANDBOX_GRADING_THREAT_MODEL.md)) — The self-improvement runner's target measure (`scripts/self_host/spec_source.run_measure`) and the bench's acceptance tests (`scripts/bench/bench_grade.grade`) import code the factory produced, so they run in this sandbox, reused as it is: `normalize`, `container_runtime`, `container_command`, `run_bounded`, `report` and `sandbox_image.pinned`, called by the runner on its own machine (not through NATS; the backend is not involved). Grading adds its own floor: container mode only (`bwrap` has no CPU or memory limit and is refused), network off, `--read-only` root, the candidate's tree at `/candidate` and the graders from the pinned commit at `/graders`, both read-only, a 256 MB tmpfs at `/workspace` (`container_command(scratch_mb=...)`, no bind mount of the host) and the `/tmp` tmpfs the only writable places (either filled up is `unmeasured`), no variable of the runner's environment, an image already on the machine run from its content ID (`--pull=never`), and a timeout. The verdict is the runtime's exit status and pytest's JUnit report, printed by the runner's wrapper after pytest exited and after every other process in the container was killed; no file the candidate could write is read. A run the sandbox cannot give is `unmeasured` with its reason, never passed. With `run.sh --graders <B>` the grader loads these modules from B's git objects, hash-checked (`graders.py daemon`, `FABRIQUE_DAEMON_SHA256`), never from the candidate's checkout. `vscode-daemon/sandbox.py`, `sandbox_image.py`, `sandbox_cache.py` and `run_logs.py` are protected paths for that reason (`services/contracts/protected_paths.py`). Tests: `backend/tests/test_sandbox_grading.py`.

### The workspace routes and the daemon client

**`backend/app/routers/workspace.py`** / **`services/workspace/workspace_daemon.py`** — `GET /v1/workspace/{status,browse,inspect}` relay the picker and project check to the daemon (503 with start instructions when none is connected, or with the reason when it is incompatible). `status` reports `state`: `connected`, `absent` (NATS says nothing listens), `unknown` (NATS unreachable, no answer in time, or an error reply) or `incompatible` (a protocol outside the backend's range), with a `reason`; unknown is never shown as stopped. It adds `protocol`, `heartbeat`, `liveness` and `reported_by_daemon` (above). `POST /v1/discover_team` inspects the folder through the daemon and runs stack detection on its file snapshot (`materialized_snapshot`), recording the host path; with a `company_id` the company's Git workflow is set from what was observed there (`services/release/git_setup.py`: on only for a repository).

### The Git workflow, the local merge and publishing

**`backend/app/services/workspace/git_workflow.py`** — The company's Git workflow (`Company.git_workflow`, `git_base_branch`; `GET|PUT /v1/companies/{id}/git`, Viewer/Manager): the task worker asks the daemon to deliver on `fabrique/task-<id>` (`delivery_spec`), the daemon commits in a worktree under `<git dir>/fabrique-worktrees/` and answers with the branch, commit and parent (`vscode-daemon/git_workspace.py`, real git, no shell), and `record_reply` keeps that on the evidence as `git` and points the delivery tests at the worktree. The person's checkout is never touched by a delivery. **Where a branch starts** (`vscode-daemon/git_base.py`): before a new task branch (also a console producer's, `console_run.py`) or a sprint's integration branch starts, the daemon fetches the base's one branch from its upstream (or `origin`'s, or the one remote's, same name) with the person's credentials, no shell, at most `FETCH_TIMEOUT_SECONDS` (30): a local base behind by a fast-forward starts the branch from the remote tip (the person's branch, index and files do not move, and the remote tip holds every local commit), a base only ahead or equal starts where it is, a diverged one is refused naming both counts (no side can be chosen without dropping commits), a repository with no remote starts from the local base as before, and a fetch that fails starts from the local base with `remote_unreachable` (never blocking). The `git` evidence carries `base_commit`, `base_ref`, `base_remote`, `base_remote_commit`, `started_from` and `base_behind_remote` when the local copy was behind; a branch that already exists keeps its start (the first delivery's evidence says it). **Only under the company's forge policy** (issue #727, `vscode-daemon/forge_gate.py`, [platform](platform.md)): the backend sends `forge_policy` with the delivery's `git` spec (`delivery_spec`), with every `workspace.git.*` request and with a console producer's `workspace.console.prepare`; with `none` (a new company's default, and what the daemon reads when the field is missing or unknown) the daemon fetches nothing and starts from the local base, the evidence saying `remote_contacted: false`, `forge_policy` and `base_remote_not_contacted`; with `fetch` or `publish` it fetches as above. `workspace.git.publish` and `workspace.git.reviews` are refused before anything runs unless the policy is `publish` (409, `code: forge_disabled`), and the daemon's own `FORGE_POLICY_MAX` caps whatever the backend asks for, so a compromised or outdated backend cannot widen contact (`vscode-daemon/protocol/PROTOCOL.md` §5.3). **A folder that is not a repository** with the workflow on is delivered with a snapshot, as without the workflow; the reply's `git_workflow_skipped` is kept on the evidence and the delivery's System note says so (`git_workflow.skipped_note`). When a company is created (`POST /v1/init_company`, which asks `workspace.inspect` itself and takes the wizard's `git_workflow` and `git_base_branch`; since F8 the file snapshot of that one inspection also feeds the foundation-sprint decision, [loop](loop.md)) or its folder recorded (`discover_team` with a `company_id`), `services/release/git_setup.py` sets the workflow from that observation: on only for a repository, off when the folder is not one or nobody could observe it, and a person's `git_workflow: false` turns it off; the request never makes a folder a repository. `Company.git_workflow` keeps its default (`True`, PR #446) for rows made elsewhere; the delivery fallback keeps them working. `GET /v1/companies/{id}/git?check=true` adds `base_status` (`state: observed` with the daemon's `workspace.git.base_status`, or `unknown` with the reason). The workflow is set on the company's Models page (`components/GitWorkflowPanel.tsx`, beside the console producers that need it: the switch, the base branch, whether the folder is a repository and a warning naming how far the local base is behind its remote; a Viewer reads it) and in the New company wizard's review step (`GitSetupChoice`, pre-set from the inspection with the checked-out branch as base), as well as on the sprint's Board tab. Pushing is never a step the loop requires: a company may keep its code only in a local repository. `services/release/local_merge.py` merges a run's branch into a base branch of that repository (`POST /v1/agent_runs/{id}/merge`, Manager; `POST /v1/sprints/{id}/integration/merge` for a sprint's integration, refused at a conflict or a failing suite): the daemon (`vscode-daemon/local_merge.py`, `workspace.git.merge`) computes the merge in a worktree of its own detached at the base's tip, aborts a conflict naming its files with nothing changed, and moves the base with `git update-ref` against the old tip, or with `git merge --ff-only` in the checkout that has it, only while that checkout has no uncommitted changes to tracked files; nothing is pushed and no remote is needed. The answer (base, tip before and after, the branch's commit) is an observation kept as a `RunPublication` with `how == "local"` (a run) or under the integration's `details["local_merge"]`, audited. Publishing is the optional other way out: `services/release/git_publish.py` publishes a run's branch (`POST /v1/agent_runs/{id}/publish`, Manager; `GET .../publications`, Viewer): the request's description is the evidence the Verifier observed, the producer's claims labelled apart, with a `Fabrique-Run:` trailer; the daemon's answer is kept as a `RunPublication` and audited. The Files changed tab offers it (`components/PublishBranch.tsx`). `services/release/review_sync.py` brings the request's comments back (`POST /v1/agent_runs/{id}/publications/{pid}/sync`, Manager): each becomes a `ReviewComment` with its `source`, `external_id`, page and, for a review, its state there; reading again updates one still waiting and never duplicates; the next review a Manager submits carries them, and its `NEEDS WORK:` names who wrote each and on which platform. A review submitted on the platform decides nothing here.

**Bringing the person's local copy up to date** (issue #745, `vscode-daemon/git_sync.py`, `workspace.git.sync_base`; PROTOCOL.md §5.4). Sprint branches already start from the remote's base, but the person's own checkout, and what a new company reads from it, may be weeks behind. On the Owner's request (the New company form's "Bring my local copy up to date", the company's Git settings, or the board of a sprint that has not started; [release](release.md), `base_sync`) the daemon fast-forwards the local base branch and nothing else: `git fetch` of that one branch into a temporary ref (`--refmap=`, so no remote-tracking branch moves on a refusal; deleted at once), then `git update-ref refs/heads/<base> <new> <old>` when no worktree has the base checked out, or `git merge --ff-only` in the checkout that has it; no merge commit, rebase or reset, no shell, no prompt, bounded (`SYNC_FETCH_TIMEOUT_SECONDS`, 20). It refuses with `ok: false`, an `outcome` and a `reason`, leaving refs and index as they were: under a forge policy below `fetch` (`forge_disabled`, nothing contacted, `forge_gate`), a rebase, merge, cherry-pick or revert unfinished (`operation_in_progress`) or uncommitted changes to tracked files in the base's checkout (`dirty`), both read before the remote is contacted, a remote that cannot be read (`remote_unreachable`), and both sides moved (`diverged`, with both counts). `updated` names `before` and `after`; `up_to_date` and `ahead` move nothing. **Never a prompt** (`vscode-daemon/git_env.py`): every git command the daemon runs (`git_workspace.run_git`) has `GIT_TERMINAL_PROMPT=0`, an empty `GIT_ASKPASS` and `GCM_INTERACTIVE=never`, and one that can reach a remote (`fetch`, `push`, `pull`, `ls-remote`, `clone`; the sync, the base's fetch before a branch, the check before publishing, the push) also `GIT_SSH_COMMAND` ending in `-o BatchMode=yes`, appended to the person's own command (`GIT_SSH_COMMAND`, else `core.sshCommand`, else `GIT_SSH`, else `ssh`). A remote that wants a passphrase, a password or an unknown host key fails at once: `remote_needs_interaction` (the sync's outcome; on the base's observation `remote_needs_interaction: true` and the reason prefixed with it). `vscode-daemon/git_local.py` reads the checkout locally (`current_branch`, `clean`, `operation_in_progress`, `remote_url` without credentials), which `workspace.git.base_status` now adds to its answer under every policy, so the New company form shows them before anything is contacted.

### A stack profile per folder

**`backend/app/services/workspace/delivery_commands.py`** (ADR 0018) — The workspace's one entry point for a delivery's daemon commands, called by `loop/delivery_checks` and `loop/delivery_suites`: `install_dependencies` (`dependency_install.install_if_needed`), `run_tests` (the test command through `workspace.execute` in the company's sandbox, recorded by `workspace_daemon.record_test_run` with its full log from `run_logs`; returns the output, or `None` when nothing ran), `folders_to_run` (`stack_roots.selected` over the daemon's write report), `sandbox_box` and `run_in_folder` (`folder_commands`), and `check_app` with `app_record` (the `workspace.app.check` request bounded by the daemon's own phases: launch, security probe, browser probe, full log upload). It composes requests and returns replies; the loop chooses the commands and the evidence reads the output.

**`backend/app/services/workspace/stack_roots.py`** / **`folder_commands.py`** (self-hosting retrospective, F5) — A repository with several projects (La Fabrique's `backend/`, `frontend/`, `llm-proxy/`) has a profile per folder: `detect_folders` finds each sub-folder with its own manifest, up to two deep (dependencies, build output, `fixtures/` and `examples/` skipped; a folder found is not searched further), each detected as `stack_profiles.detect` detects a root. Folders are searched for only when the root has neither a stack nor a test command a person named, so a single-root project runs as before; the folders a company names in `Company.stack_profile["folders"]` (`{folder: {stack, install, test}}`, an empty command turning that step off) always count, and `every_delivery` lists the commands every delivery runs. The rest of the stored profile is the root's, so a profile in the old shape is one root. `selected` says which folders' suites a delivery runs, from the daemon's report of the files it wrote (`changed_paths`, `workspace_writes`, never the agent's list): a folder it wrote in runs; a file in no folder is the root's suite's when the root has one, every folder's otherwise; no report (a sprint's integration) runs every one. `folder_commands.execute` sends `cd <folder> && <command>` through `workspace.execute` in the company's sandbox (the folder name is checked so it needs no quoting; an allow-list command policy must list `cd`) and keeps the reply with the sha256 of the output computed by the backend. A manifest in a folder is installed by that folder's install (`dependency_install._install_folders`), recorded per folder as the root's is. Configuration and observations only: `services/evidence/command_runs.py` judges them.
