# The workspace context

Part of the project's guidance for agents; the index is [`CLAUDE.md`](../../CLAUDE.md). Read this document before changing code in `backend/app/services/workspace/`.

- **Folder:** `backend/app/services/workspace/`
- **Responsibility:** The client of the workspace daemon over NATS: requests and their errors, the delivery test run, the project inspection and snapshot, the sandbox modes, the stack profiles and the Git workflow's delivery spec. It sends and returns observations; it never judges them.
- **May import:** [contracts](contracts.md), [platform](platform.md) (`docs/architecture/contexts.json`, checked by `scripts/check_architecture.py`).
- **Modules:** `dependency_install`, `git_workflow`, `project_profile`, `sandbox`, `sandbox_manager`, `stack_profiles`, `workspace_daemon`, `workspace_snapshot`.

## Components

### The workspace daemon

**`vscode-daemon/daemon.py`** — The workspace daemon: a Python process that runs natively on the user's macOS, Linux or Windows machine (started by `scripts/start-daemon.*`, reconnects to NATS on its own). It answers `workspace.generate` (write files, reply with the sha256 read back from disk and the diff against the bytes that were there, `file_diff.py`; with a `git` spec, as a commit on the task's branch in a worktree, `git_workspace.py`, delivered with a snapshot instead and `git_workflow_skipped: "not a repository"` when the folder is not a repository; without one, with a `snapshot` that undoes it, `delivery_snapshot.py`; `delivery.py` picks the two and adds the project's paths, `workspace_read.project_files`, for the Verifier's import check), `workspace.execute` (run a command the command policy accepts, `command_policy.py`), `workspace.capabilities`, `workspace.status`, `workspace.browse` (folder picker) and `workspace.inspect` (canonical path, git remote/branch, file snapshot for stack detection), `workspace.hash` (the sha256 of named files as they are on disk, `file_hash.py`; the backend keeps QA's acceptance tests intact with it), `workspace.list` / `workspace.read` / `workspace.search` / `workspace.find` (the Developer's read-only tools on the project, bounded, `workspace_read.py`), `workspace.map` (the repository map: the project's definitions ranked by use, cached per file set, `repo_map.py`), `workspace.signatures` (the signatures of named module-level Python definitions, for the Verifier's symbol findings: at most 50 paths and 400 names a request, each file's sha256, each name `found` with its parameters (names and whether each has a default, never a value), `unknown` (decorated, an inherited constructor, bound twice) or `missing`, a file that does not parse said so; read with `repo_map`'s guards, never a secret, a symlink out or VCS metadata, `signatures.py`), `workspace.related` (the files around a task's seeds and the names that tie them, from the repository map's parse cache and edge rule, paths, names and sha256 only, never contents, `code_graph.py`; [tools](tools.md)), `workspace.edit` / `workspace.edit.finish` (the Developer's checked edits, a working copy per task, `workspace_edit.py`), `workspace.git.publish` (push a `fabrique/` task branch to `origin` with the person's credentials and open a draft pull or merge request with `gh` / `glab`, else the compare page), `workspace.git.merge` (merge a `fabrique/` branch into a base branch of the local repository, no remote, `local_merge.py`), `workspace.git.base_status` (whether the folder is a repository and how its base branch stands against its remote, fetched now, `git_base.py`; the settings page reads it), `workspace.git.reviews` (the comments people left on that request, read with `gh api` / `glab api`, `platform_reviews.py`), `workspace.app.check` (start the application in the sandbox, wait for its port, probe it, run an e2e command, stop it, `app_run.py`), `workspace.sandbox.reset` (remove a project's dependency cache volume, only the daemon's own by name and label, and lift its quarantine, `sandbox_cache.py`), `workspace.console.prepare` / `workspace.console.collect` (a console producer's worktree, then the files its CLI changed read back with their sha256 and the worktree put back, `console_run.py`), `workspace.git.integrate` (a sprint's task branches merged into `fabrique/sprint-<id>` in a worktree, `sprint_integration.py`), `workspace.undo` (undo a delivery made without a `git` spec from the snapshot `workspace.generate` kept, `delivery_snapshot.py`), and consumes the JetStream queue `workspace.deliver` for files queued while it was offline, reporting on `workspace.delivered`. Its `requirements.txt` is `nats-py` only (`nkeys` is added for a creds file or an nkey seed). `nats_connect.py` connects it with the credentials and TLS the environment names, replies under `_INBOX.daemon` (passed explicitly to the pull consumer: nats-py 2.3.1, the image's pin, ignores the connection's prefix there), and waits for the backend to create the delivery streams instead of creating them.

### The sandbox: which image ran, and the dependency cache

**`vscode-daemon/sandbox.py`** / **`sandbox_image.py`** / **`sandbox_cache.py`** / **`services/workspace/sandbox.py`** — Agent code runs in the mode the company asked for (`host`, `container`, `bwrap`) and the daemon reports what it applied. In container mode it also records **which image ran** (`sandbox_image.py`): before the run it asks the runtime (`image inspect`, Docker or Podman) for the image's content ID and registry digest and starts the container from that ID; an image the run itself pulled is observed after it (`observed: after_run`); host and bwrap say why there is no image (`image_identity.reason`), never an empty success. With `cache` in the request (`DELIVERY_SANDBOX_CACHE`), a named volume per project, `fabrique-cache-<key>` labelled `dev.fabrique.sandbox-cache=<key>`, holds the package managers' caches at `/fabrique-cache` (`sandbox_cache.py`): kept after a run, removed after a failed install (the backend's install request says `purpose: install`), quarantined after three failed installs in a row with the reason in each report and in `workspace.status`, until `POST /v1/companies/{id}/sandbox/cache/reset` (Manager, audited, `sandbox.reset_cache`) removes it through `workspace.sandbox.reset`; a same-named volume without the label is never used or removed. `GET /v1/workspace/status` relays the daemon's `sandbox_cache` (allowed, and the projects quarantined). The design and what was taken from AixleHQ/flow: [`docs/design/EXECUTION_ENVIRONMENT.md`](../design/EXECUTION_ENVIRONMENT.md).

### The workspace routes and the daemon client

**`backend/app/routers/workspace.py`** / **`services/workspace/workspace_daemon.py`** — `GET /v1/workspace/{status,browse,inspect}` relay the picker and project check to the daemon (503 with start instructions when none is connected). `status` reports `state`: `connected`, `absent` (NATS says nothing listens) or `unknown` (NATS unreachable, no answer in time, or an error reply), with a `reason`; unknown is never shown as stopped. `POST /v1/discover_team` inspects the folder through the daemon and runs stack detection on its file snapshot (`materialized_snapshot`), recording the host path; with a `company_id` the company's Git workflow is set from what was observed there (`services/release/git_setup.py`: on only for a repository).

### The Git workflow, the local merge and publishing

**`backend/app/services/workspace/git_workflow.py`** — The company's Git workflow (`Company.git_workflow`, `git_base_branch`; `GET|PUT /v1/companies/{id}/git`, Viewer/Manager): the task worker asks the daemon to deliver on `fabrique/task-<id>` (`delivery_spec`), the daemon commits in a worktree under `<git dir>/fabrique-worktrees/` and answers with the branch, commit and parent (`vscode-daemon/git_workspace.py`, real git, no shell), and `record_reply` keeps that on the evidence as `git` and points the delivery tests at the worktree. The person's checkout is never touched by a delivery. **Where a branch starts** (`vscode-daemon/git_base.py`): before a new task branch (also a console producer's, `console_run.py`) or a sprint's integration branch starts, the daemon fetches the base's one branch from its upstream (or `origin`'s, or the one remote's, same name) with the person's credentials, no shell, at most `FETCH_TIMEOUT_SECONDS` (30): a local base behind by a fast-forward starts the branch from the remote tip (the person's branch, index and files do not move, and the remote tip holds every local commit), a base only ahead or equal starts where it is, a diverged one is refused naming both counts (no side can be chosen without dropping commits), a repository with no remote starts from the local base as before, and a fetch that fails starts from the local base with `remote_unreachable` (never blocking). The `git` evidence carries `base_commit`, `base_ref`, `base_remote`, `base_remote_commit`, `started_from` and `base_behind_remote` when the local copy was behind; a branch that already exists keeps its start (the first delivery's evidence says it). **A folder that is not a repository** with the workflow on is delivered with a snapshot, as without the workflow; the reply's `git_workflow_skipped` is kept on the evidence and the delivery's System note says so (`git_workflow.skipped_note`). When a company is created (`POST /v1/init_company`, which asks `workspace.inspect` itself, and takes the wizard's `git_workflow` and `git_base_branch`) or its folder recorded (`discover_team` with a `company_id`), `services/release/git_setup.py` sets the workflow from that observation: on only for a repository, off when the folder is not one or nobody could observe it, and a person's `git_workflow: false` turns it off; the request never makes a folder a repository. `Company.git_workflow` keeps its default (`True`, PR #446) for rows made elsewhere; the delivery fallback keeps them working. `GET /v1/companies/{id}/git?check=true` adds `base_status` (`state: observed` with the daemon's `workspace.git.base_status`, or `unknown` with the reason). The workflow is set on the company's Models page (`components/GitWorkflowPanel.tsx`, beside the console producers that need it: the switch, the base branch, whether the folder is a repository and a warning naming how far the local base is behind its remote; a Viewer reads it) and in the New company wizard's review step (`GitSetupChoice`, pre-set from the inspection with the checked-out branch as base), as well as on the sprint's Board tab. Pushing is never a step the loop requires: a company may keep its code only in a local repository. `services/release/local_merge.py` merges a run's branch into a base branch of that repository (`POST /v1/agent_runs/{id}/merge`, Manager; `POST /v1/sprints/{id}/integration/merge` for a sprint's integration, refused at a conflict or a failing suite): the daemon (`vscode-daemon/local_merge.py`, `workspace.git.merge`) computes the merge in a worktree of its own detached at the base's tip, aborts a conflict naming its files with nothing changed, and moves the base with `git update-ref` against the old tip, or with `git merge --ff-only` in the checkout that has it, only while that checkout has no uncommitted changes to tracked files; nothing is pushed and no remote is needed. The answer (base, tip before and after, the branch's commit) is an observation kept as a `RunPublication` with `how == "local"` (a run) or under the integration's `details["local_merge"]`, audited. Publishing is the optional other way out: `services/release/git_publish.py` publishes a run's branch (`POST /v1/agent_runs/{id}/publish`, Manager; `GET .../publications`, Viewer): the request's description is the evidence the Verifier observed, the producer's claims labelled apart, with a `Fabrique-Run:` trailer; the daemon's answer is kept as a `RunPublication` and audited. The Files changed tab offers it (`components/PublishBranch.tsx`). `services/release/review_sync.py` brings the request's comments back (`POST /v1/agent_runs/{id}/publications/{pid}/sync`, Manager): each becomes a `ReviewComment` with its `source`, `external_id`, page and, for a review, its state there; reading again updates one still waiting and never duplicates; the next review a Manager submits carries them, and its `NEEDS WORK:` names who wrote each and on which platform. A review submitted on the platform decides nothing here.
