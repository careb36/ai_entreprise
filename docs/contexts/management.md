# The management context

Part of the project's guidance for agents; the index is [`CLAUDE.md`](../../CLAUDE.md). Read this document before changing code in `backend/app/services/management/`.

- **Folder:** `backend/app/services/management/`
- **Responsibility:** The owner as a client: the Manager agent with its inbox, policy, rules, observations, actions and record, the client's brief and its mail, the Reviewer agent and the Support agent. It may read and act through every other context; no other context imports it.
- **May import:** [contracts](contracts.md), [platform](platform.md), [tasks](tasks.md), [models](models.md), [evidence](evidence.md), [workspace](workspace.md), [tools](tools.md), [learning](learning.md), [planning](planning.md), [producers](producers.md), [loop](loop.md), [release](release.md), [integrations](integrations.md) (`docs/architecture/contexts.json`, checked by `scripts/check_architecture.py`).
- **Interface** (`public` in `docs/architecture/contexts.json`, ADR 0018, checked by `scripts/check_architecture.py`): none: no other context imports it, and the rule keeps it so.
- **Modules:** `brief_mail`, `intake_triage`, `manager_actions`, `manager_actions_extra`, `manager_agent`, `manager_brief`, `manager_inbox`, `manager_inbox_extra`, `manager_observe`, `manager_policy`, `manager_record`, `manager_record_extra`, `manager_rules`, `reviewer_agent`, `sod_report`, `support_agent`.

## Components

### The Manager agent

**`backend/app/services/management/manager_agent.py`** / **`manager_inbox.py`** / **`manager_inbox_extra.py`** / **`manager_policy.py`** / **`manager_rules.py`** / **`manager_observe.py`** / **`manager_actions.py`** / **`manager_actions_extra.py`** / **`manager_record.py`** / **`manager_record_extra.py`** / **`manager_brief.py`** / **`routers/manager.py`** — The Manager agent (issue #331, `MANAGER_AGENT_ENABLED`): the owner acts as a client and decides only the big things. `manager_inbox.inbox_items` gathers what waits for a person with the facts the platform observed (`run_facts`: the latest verification's verdict, the `risk_tier` check, the distinct files declared, imported (`subject.changed_files`) or written, unknown when none says, which no limit lets through; whether an operator froze the task; the criteria a task covers; whether a hold is only autonomy level 1's; the autonomy level; a procedure reverted for the role; `over_budget` from the business units' quotas) and gives each a category the platform decides (`accept_delivery`, `accept_high_risk`, `blocked_task`, `adopt_procedure`, `approve_run`); `parse_suggestion` takes only `DECISION … CATEGORY … REASON … END` with a decision the category allows and the item's own category. The prompt carries the standards (`standards.prompt_section`) and the company's active procedures for the role `Manager`; each call is billed to the company's business unit (`bu_id`) and its tokens audited as `manager_agent_call`; a cycle makes at most `ITEMS_PER_CYCLE` calls across companies, failures included. The situation key (`item_state`) holds the latest run and verification ids, so new evidence is looked at afresh. A suggestion row keeps its `action_state` (`pending`, `done`, `not_allowed`, `stale`, `unusable`) and, when it settles `not_allowed` or `stale`, `refusal_reason` (migration `0040`): the platform's sentence, a field of its own so `suggested_*` stays the model's claim, written by `decide` through `refusal_reason(verdict)` as the rule's name and its check's or the policy's `why` (a rule that does not hold, a flagged rule, no rule named for the item, a suggestion that is not the rule's decision, over budget, overridden before, a probe that left a fact unknown when the row still ends refused), or `LEFT_THE_INBOX` / `SITUATION_CHANGED` for a stale row; a row waiting for a probe has none yet, and `track_record` never reads it: after the call `decide` reads the item, policy, record and overrides again and acts only while the situation is the one it asked about, the acceptance being one conditional update on the task as it was read (a task that moved without a new situation stays `pending` and is read again); a row a stopped replica left `pending` is decided on the next cycle without another call. Across replicas the loop runs under `locks.MANAGER_AGENT` and each item under its own `locks.MANAGER_ITEM` lock, held from the check that its situation is new through the model call to the decision, so two replicas never ask about or decide the same item; one `ManagerDecision` row per situation (`item_state`, unique) stays as the invariant behind the lock. `manager_policy` holds the rules a Manager may enable, every one off until named (issue #394: every action a Manager takes in the product is a rule), with the checks in `manager_rules` (`CHECKS`, one per rule, reading only observed facts; an unknown fact never lets one hold): `accept_delivery` (an autonomy-1 hold, verified, tier low or medium, within `max_files`/`max_criteria`), `adopt_procedure` (autonomy 3, no reverted procedure for the role), `approve_run` (verified, low or medium, within `max_files`), `merge_local` (a done task's branch QA approved, verified, low or medium, within `max_files`, not merged at that commit; or a sprint's integration at `tests_passed`, approved when the company asks for a review, and, for a company that hosts the factory, with every protected path the merge guard last matched in its diff acknowledged by an Owner: `manager_inbox_extra` reads the guard's check kept on the integration as `protected_paths` and `protected_paths_acked`, unknown until a merge attempt read the diff, and suffixes the item's state `:protected_unchecked`, `:protected_none`, `:protected_awaiting_ack` or `:protected_acked`, so a refusal and the Owner's acknowledgement each ask the agent again, [release](release.md), `docs/design/rsi-loop.md` REQ-13), `undo_delivery` (the latest verification refuted, no Git branch, a snapshot not undone, no person's note since), `send_back_blocked` and `carry_over` (both on the `blocked_task` category: a triage that chose another attempt with a brief and an open sprint; or not carried, not a second attempt, not left for a person by the triage), `answer_question` (a draft's open question an approved specification or architecture already answers, word for word after case, spacing and closing punctuation: an answered question or a decision's title), `publish` (as `merge_local` for a task branch, with the policy's `publish_enabled` and a remote the daemon reads), `resume_after_credit` (a sprint paused for credit once a one-token call through the proxy passes, at most every `CREDIT_PROBE_INTERVAL`), and the strict ones: `approve_specification` (no blocking finding, no open question, criteria on every requirement), `approve_architecture` (no blocking finding, no open question, its specification approved, every requirement covered), `accept_high_risk` (verified, every criterion the task covers passing in `criteria_tests`, the `standards` check without a secret, within `max_files_high_risk`, 3 by default; migration `0018` adds it and `publish_enabled`; and no protected path: for a company that hosts the factory, `run_facts` reads the matches of the Verifier's `protected_paths` check and `protected_touched` matches the run's declared and observed paths again against the running backend's list, so a delivery verified before an Owner turned the flag on is held too; a match is refused naming the paths, by `accept_delivery` too and whatever the recorded tier, and the item is categorised `accept_high_risk`; a person reviews it through the normal review, `docs/design/rsi-loop.md` REQ-11; the item's text lists them). The confirmation set no policy unlocks is `ALWAYS_ESCALATE`: cancel or delete a sprint, change autonomy, spend above budget, change the protected paths (`change_protected_paths`, a signed-in Owner's, [platform](platform.md)) (a policy naming one is a 422). `manager_inbox_extra` gathers the items behind them with their facts: draft specifications and architectures (for approval, or their open questions), credit-paused sprints, and, only when the policy names the rule, done tasks' branches and integrations to merge, branches to publish and refuted deliveries to undo. `manager_observe` probes what nothing stored (the credit call, the remote) only when the rule is named and suggested, leaves the row `pending` while a probe could not answer, and makes the daemon requests (`workspace.git.merge`, `workspace.undo`, `workspace.git.publish`) from the agent's thread on the backend's loop (`bind`, from `lifecycle`). `evaluate` allows a decision alone only when a rule holds on the facts *and* the suggestion is that rule's decision, never over budget, after an override on the item, or under a flagged rule. `manager_actions.act` takes it as a person would (the task marked done with an `Accepted by the Manager agent` note, its `moved` event through `task_events.record` after the conditional claim, also for `accept_high_risk`, `procedures.adopt`, `run_review.record_approval`; the rest in `manager_actions_extra`: the daemon's merge, undo or publication recorded with the agent as actor, a send-back authored by the agent with the triage's brief that `board.is_send_back` and the projection count as a send-back, a carry-over mark (`carry_over.CARRY_MARK_PREFIX`) the inbox reports as `marked_for_carry_over` so the "Plan a sprint" form ticks it, the answers with `answered_by`, `/resume`'s steps, `document_approval` shared with the approve routes), audited `manager_agent_<category>` with `decided_by`, the rule and the action's facts; `override` undoes it (the task back to waiting for a person, the procedure retired and the one it superseded restored, a rejection recorded, a send-back or a mark taken back, the agent's answers cleared, the sprint paused again, a document back to draft with what it superseded restored only while nothing was planned from it; a local merge and an undo are recorded and counted but nothing is undone, with a note saying the person reverts it in git or redelivers; a publication is a 409, closed on the platform) and is audited as the person's; it runs once (a lock on the decision and a conditional claim: a second request is a 409) and only while the agent's decision is still the latest on the item (a later acceptance, approval or retirement is a 409). `manager_record.track_record` reads the client's decision from what they did (a send-back or acceptance note after the agent looked, a carry-over, the procedure's status and who decided it, the run's latest approval by someone else) and counts suggested, decided, agreed, unusable, taken alone, overridden and the override rate by category; `flagged_rules` (two or more overrides among a rule's last five decisions since the policy was saved, at a higher rate than before) stops the agent applying a rule until a Manager saves the policy again, never widening it. `GET /v1/companies/{id}/brief` (`manager_brief`) is the client's brief, deterministic: tasks done since `since` (a day by default, dated by their closing comment, never by `updated_at`), suggestions, decisions and overrides each by its own moment, what the agent decided and why, what waits for the client (blocked tasks, holds, proposals, runs, integrations, specification and architecture drafts) and the tokens from the audit log beside the quotas; `agent.refused` and `agent.refusals` list the suggestions of the window the policy did not let the agent take alone, each with its `refusal_reason` beside the model's reason. `GET /v1/manager_decisions` and the inbox's `suggestion` carry `refusal_reason`, and the Review page shows it under the suggestion (`ManagerSuggestion`) and in the brief (`ClientBriefCard`). The inbox carries each item's latest `suggestion` and the agent's `agent_decisions`. `history_check.py` lets an autonomy-1 hold close on the agent's acceptance (and dates the task's closing by it for its dependants) and still refuses one on a high-risk hold, unless the acceptance names the strict rule `accept_high_risk`. The client's request box on the Review page (`components/ClientRequestBox.tsx`, Managers) is the PO's `POST /v1/specifications/draft`, linking to the draft the client approves; the policy is edited beside it (`components/ManagerPolicyPanel.tsx`: every rule off until ticked, the strict ones apart, the limits and the publishing switch; read-only for a Viewer); the Sprints page shows the record beside the other numbers (`components/ManagerRecordCard.tsx`) once the agent has decisions.

### The segregation-of-duties report

**`backend/app/services/management/sod_report.py`** / **`routers/sod.py`** — `GET /v1/companies/{id}/sod/report` (Manager, `no-store`; issue #543, [`docs/design/SEGREGATION_OF_DUTIES.md`](../design/SEGREGATION_OF_DUTIES.md)): every approval recorded (held deliveries accepted and runs approved from `run_reviews`, specifications and architectures from `approved_by`, run and integration merges) beside its requesters, as `separated`, `exception` (matched to its `sod_exception_applied` row), `violation`, `unattributed` or `not_a_person`; the `sod_refused` rows; and the matrix of duties (request, plan, deliver, verify, approve, release) per member with their effective role, per role and per agent role, flagging a member who both requests and approves. Computed from records only; `approver_name` is never read.

### The Support agent on the intake queue

**`backend/app/services/management/intake_triage.py`** — In the Support agent's loop (`SUPPORT_AGENT_ENABLED`, after the tickets, under `locks.SUPPORT_AGENT`), up to five pending requests nobody has triaged get a suggestion (issue #532): `DECISION … CATEGORY … DUPLICATE_OF … REASON … END`, with a decision among `accepted`, `declined`, `duplicate`, `snoozed`, a category among `bug`, `feature`, `question`, `incident`, and for a duplicate one reference from the candidates the prompt lists (the company's other requests and open tasks), checked by `parse_suggestion`; any other answer marks the request triaged without a suggestion, and a failed call leaves it for the next cycle. The request's text is treated as data and the agent has no tools. The suggestion is stored in `suggested_*` and never moves the request; a Manager decides ([planning](planning.md#the-intake-queue)), and `GET /v1/companies/{id}/intake-record` compares the two per category.
