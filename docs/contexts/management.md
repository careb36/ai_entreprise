# The management context

Part of the project's guidance for agents; the index is [`CLAUDE.md`](../../CLAUDE.md). Read this document before changing code in `backend/app/services/management/`.

- **Folder:** `backend/app/services/management/`
- **Responsibility:** The owner as a client: the Manager agent with its inbox, policy, rules, observations, actions and record, the client's brief and its mail, the Reviewer agent and the Support agent. It may read and act through every other context; no other context imports it.
- **May import:** [contracts](contracts.md), [platform](platform.md), [tasks](tasks.md), [models](models.md), [evidence](evidence.md), [workspace](workspace.md), [tools](tools.md), [learning](learning.md), [planning](planning.md), [producers](producers.md), [loop](loop.md), [release](release.md), [integrations](integrations.md) (`docs/architecture/contexts.json`, checked by `scripts/check_architecture.py`).
- **Interface** (`public` in `docs/architecture/contexts.json`, ADR 0018, checked by `scripts/check_architecture.py`): none: no other context imports it, and the rule keeps it so.
- **Modules:** `brief_mail`, `intake_triage`, `manager_actions`, `manager_actions_extra`, `manager_agent`, `manager_brief`, `manager_inbox`, `manager_inbox_extra`, `manager_observe`, `manager_policy`, `manager_record`, `manager_record_extra`, `manager_rules`, `reviewer_agent`, `rsi_cycle`, `rsi_cycle_import`, `rsi_cycle_steps`, `rsi_cycle_view`, `sod_report`, `support_agent`.

## Components

### The Manager agent

**`backend/app/services/management/manager_agent.py`** / **`manager_inbox.py`** / **`manager_inbox_extra.py`** / **`manager_policy.py`** / **`manager_rules.py`** / **`manager_observe.py`** / **`manager_actions.py`** / **`manager_actions_extra.py`** / **`manager_record.py`** / **`manager_record_extra.py`** / **`manager_brief.py`** / **`routers/manager.py`** — The Manager agent (issue #331, `MANAGER_AGENT_ENABLED`): the owner acts as a client and decides only the big things. `manager_inbox.inbox_items` gathers what waits for a person with the facts the platform observed (`run_facts`: the latest verification's verdict, the `risk_tier` check, the distinct files declared, imported (`subject.changed_files`) or written, unknown when none says, which no limit lets through; whether an operator froze the task; the criteria a task covers; whether a hold is only autonomy level 1's; the autonomy level; a procedure reverted for the role; `over_budget` from the business units' quotas) and gives each a category the platform decides (`accept_delivery`, `accept_high_risk`, `blocked_task`, `adopt_procedure`, `approve_run`); `parse_suggestion` takes only `DECISION … CATEGORY … REASON … END` with a decision the category allows and the item's own category. The prompt carries the standards (`standards.prompt_section`) and the company's active procedures for the role `Manager`; each call is billed to the company's business unit (`bu_id`) and its tokens audited as `manager_agent_call`; a cycle makes at most `ITEMS_PER_CYCLE` calls across companies, failures included. The situation key (`item_state`) holds the latest run and verification ids, so new evidence is looked at afresh. A suggestion row keeps its `action_state` (`pending`, `done`, `not_allowed`, `stale`, `unusable`) and, when it settles `not_allowed` or `stale`, `refusal_reason` (migration `0040`): the platform's sentence, a field of its own so `suggested_*` stays the model's claim, written by `decide` through `refusal_reason(verdict)` as the rule's name and its check's or the policy's `why` (a rule that does not hold, a flagged rule, no rule named for the item, a suggestion that is not the rule's decision, over budget, overridden before, a probe that left a fact unknown when the row still ends refused), or `LEFT_THE_INBOX` / `SITUATION_CHANGED` for a stale row; a row waiting for a probe has none yet, and `track_record` never reads it: after the call `decide` reads the item, policy, record and overrides again and acts only while the situation is the one it asked about, the acceptance being one conditional update on the task as it was read (a task that moved without a new situation stays `pending` and is read again); a row a stopped replica left `pending` is decided on the next cycle without another call. Across replicas the loop runs under `locks.MANAGER_AGENT` and each item under its own `locks.MANAGER_ITEM` lock, held from the check that its situation is new through the model call to the decision, so two replicas never ask about or decide the same item; one `ManagerDecision` row per situation (`item_state`, unique) stays as the invariant behind the lock. `manager_policy` holds the rules a Manager may enable, every one off until named (issue #394: every action a Manager takes in the product is a rule), with the checks in `manager_rules` (`CHECKS`, one per rule, reading only observed facts; an unknown fact never lets one hold): `accept_delivery` (an autonomy-1 hold, verified, tier low or medium, within `max_files`/`max_criteria`), `adopt_procedure` (autonomy 3, no reverted procedure for the role), `approve_run` (verified, low or medium, within `max_files`), `merge_local` (a done task's branch QA approved, verified, low or medium, within `max_files`, not merged at that commit; or a sprint's integration at `tests_passed`, approved when the company asks for a review, and, for a company that hosts the factory, with every protected path the merge guard last matched in its diff acknowledged by an Owner: `manager_inbox_extra` reads the guard's check kept on the integration as `protected_paths` and `protected_paths_acked`, unknown until a merge attempt read the diff, and suffixes the item's state `:protected_unchecked`, `:protected_none`, `:protected_awaiting_ack` or `:protected_acked`, followed by the observed diff's hash and the approving review's id, so a refusal, the Owner's acknowledgement and a new acknowledgement of a changed diff each ask the agent again, [release](release.md), `docs/design/rsi-loop.md` REQ-13), `undo_delivery` (the latest verification refuted, no Git branch, a snapshot not undone, no person's note since), `send_back_blocked` and `carry_over` (both on the `blocked_task` category: a triage that chose another attempt with a brief and an open sprint; or not carried, not a second attempt, not left for a person by the triage), `answer_question` (a draft's open question an approved specification or architecture already answers, word for word after case, spacing and closing punctuation: an answered question or a decision's title), `publish` (as `merge_local` for a task branch, with the policy's `publish_enabled` and a remote the daemon reads), `resume_after_credit` (a sprint paused for credit once a one-token call through the proxy passes, at most every `CREDIT_PROBE_INTERVAL`), and the strict ones: `approve_specification` (no blocking finding, no open question, criteria on every requirement), `approve_architecture` (no blocking finding, no open question, its specification approved, every requirement covered), `accept_high_risk` (verified, every criterion the task covers passing in `criteria_tests`, the `standards` check without a secret, within `max_files_high_risk`, 3 by default; migration `0018` adds it and `publish_enabled`; and no protected path: for a company that hosts the factory, `run_facts` reads the matches of the Verifier's `protected_paths` check and `protected_touched` matches the run's paths again with `protected_check.touched` (the daemon's observations, `subject.changed_files` and the same declared paths as the Verifier: `claims.files`, the claims' prose, the edit tool's files; without the shipped list the reason stands in for a path, so the item is refused), so a delivery verified before an Owner turned the flag on is held too; a match is refused naming the paths, by `accept_delivery` too and whatever the recorded tier, and the item is categorised `accept_high_risk`; a person reviews it through the normal review, `docs/design/rsi-loop.md` REQ-11; the item's text lists them). The confirmation set no policy unlocks is `ALWAYS_ESCALATE`: cancel or delete a sprint, change autonomy, spend above budget, change the protected paths (`change_protected_paths`, a signed-in Owner's, [platform](platform.md)), merge a kept self-improvement change (`merge_self_change`, below) (a policy naming one is a 422). `manager_inbox_extra` gathers the items behind them with their facts: draft specifications and architectures (for approval, or their open questions), credit-paused sprints, and, only when the policy names the rule, done tasks' branches and integrations to merge, branches to publish and refuted deliveries to undo. `manager_observe` probes what nothing stored (the credit call, the remote) only when the rule is named and suggested, leaves the row `pending` while a probe could not answer, and makes the daemon requests (`workspace.git.merge`, `workspace.undo`, `workspace.git.publish`) from the agent's thread on the backend's loop (`bind`, from `lifecycle`). `evaluate` allows a decision alone only when a rule holds on the facts *and* the suggestion is that rule's decision, never over budget, after an override on the item, or under a flagged rule. `manager_actions.act` takes it as a person would (the task marked done with an `Accepted by the Manager agent` note, its `moved` event through `task_events.record` after the conditional claim, also for `accept_high_risk`, `procedures.adopt`, `run_review.record_approval`; the rest in `manager_actions_extra`: the daemon's merge, undo or publication recorded with the agent as actor, a send-back authored by the agent with the triage's brief that `board.is_send_back` and the projection count as a send-back, a carry-over mark (`carry_over.CARRY_MARK_PREFIX`) the inbox reports as `marked_for_carry_over` so the "Plan a sprint" form ticks it, the answers with `answered_by`, `/resume`'s steps, `document_approval` shared with the approve routes), audited `manager_agent_<category>` with `decided_by`, the rule and the action's facts; `override` undoes it (the task back to waiting for a person, the procedure retired and the one it superseded restored, a rejection recorded, a send-back or a mark taken back, the agent's answers cleared, the sprint paused again, a document back to draft with what it superseded restored only while nothing was planned from it; a local merge and an undo are recorded and counted but nothing is undone, with a note saying the person reverts it in git or redelivers; a publication is a 409, closed on the platform) and is audited as the person's; it runs once (a lock on the decision and a conditional claim: a second request is a 409) and only while the agent's decision is still the latest on the item (a later acceptance, approval or retirement is a 409). `manager_record.track_record` reads the client's decision from what they did (a send-back or acceptance note after the agent looked, a carry-over, the procedure's status and who decided it, the run's latest approval by someone else) and counts suggested, decided, agreed, unusable, taken alone, overridden and the override rate by category; `flagged_rules` (two or more overrides among a rule's last five decisions since the policy was saved, at a higher rate than before) stops the agent applying a rule until a Manager saves the policy again, never widening it. `GET /v1/companies/{id}/brief` (`manager_brief`) is the client's brief, deterministic: tasks done since `since` (a day by default, dated by their closing comment, never by `updated_at`), suggestions, decisions and overrides each by its own moment, what the agent decided and why, what waits for the client (blocked tasks, holds, proposals, runs, integrations, specification and architecture drafts) and the tokens from the audit log beside the quotas; `agent.refused` and `agent.refusals` list the suggestions of the window the policy did not let the agent take alone, each with its `refusal_reason` beside the model's reason. `GET /v1/manager_decisions` and the inbox's `suggestion` carry `refusal_reason`, and the Review page shows it under the suggestion (`ManagerSuggestion`) and in the brief (`ClientBriefCard`). The inbox carries each item's latest `suggestion` and the agent's `agent_decisions`. `history_check.py` lets an autonomy-1 hold close on the agent's acceptance (and dates the task's closing by it for its dependants) and still refuses one on a high-risk hold, unless the acceptance names the strict rule `accept_high_risk`. The client's request box on the Review page (`components/ClientRequestBox.tsx`, Managers) is the PO's `POST /v1/specifications/draft`, linking to the draft the client approves; the policy is edited beside it (`components/ManagerPolicyPanel.tsx`: every rule off until ticked, the strict ones apart, the limits and the publishing switch; read-only for a Viewer); the Sprints page shows the record beside the other numbers (`components/ManagerRecordCard.tsx`) once the agent has decisions.

### The self-improvement cycle

**`backend/app/services/management/rsi_cycle.py`** / **`rsi_cycle_steps.py`** / **`rsi_cycle_view.py`** / **`rsi_cycle_import.py`** / **`models/rsi_cycle.py`** / **`routers/rsi_cycles.py`** — The cycle record and its limits in the backend ([`docs/design/rsi-loop.md`](../design/rsi-loop.md), PR 10 of §8; REQ-22 to REQ-26; decisions 1, 3, 4, 7). `rsi_cycles` (migration `0044`) holds one row per cycle a company runs for a finding: its name (`cycle_key`, branch-safe, unique per company), B and C, `status` (`running`, `awaiting_merge`, `awaiting_person`, `merged`, `reverted`, `unmeasured`, `budget_exceeded`, `stopped`), the fitness decision with its reasons and metrics (from `services/evidence/fitness.decide`, never a model), the diff's files and lines the daemon observed, the token budget and the reported tokens, the kept files (`sha256_observed`, computed by the backend, beside `sha256_claimed`, the runner's), the runner's record as received, who merged and when, and who resumed the loop past a cycle. `rsi_cycle.start` refuses, each with a reason code audited `rsi_cycle_refused`: `rsi_disabled` (`RSI_ENABLED` off), `not_self_hosting` (the company is not marked by its Owner as hosting the factory: `companies.protected_paths_enabled` is that flag, decision 3 and REQ-3, so no second flag was added), `stopped` (N = `RSI_STOP_AFTER_CYCLES_WITHOUT_KEEP` cycles in a row ended without a keep, REQ-23), `cycle_running`, `daily_limit` (`RSI_CYCLES_PER_DAY` per UTC day), `budget_unknown` (`RSI_FIRST_SPRINT_TOKENS` unknown: the budget is `RSI_CYCLE_TOKEN_BUDGET` capped at twice it, decision 7), and a finding of another company, without a target measure or whose reverted specification `findings.may_start` refuses (REQ-2, REQ-20). `rsi_cycle_steps` holds the steps of a running cycle, each a boundary that stops the cycle and its sprint (`sprint_control.stop`) when a kill switch went off (REQ-24, audited `rsi_cycle_stopped`): `record_sprint`, `record_candidate` (C, the integration and the pull request), `account_tokens` (the sprint's reported tokens through `models/run_cost`, now part of that context's interface, plus the bench runner's; over the budget the cycle ends `budget_exceeded`, its sprint stops and nothing is kept, REQ-22), `read_size`/`observe_size` (the integration's diff from the workspace daemon, `integration_review.read_diff`; over `RSI_MAX_DIFF_FILES`/`RSI_MAX_DIFF_LINES`, or a diff the daemon cut short or did not list in full, the cycle is `unmeasured` and `awaiting_person`, REQ-25) and `record_decision` (a keep without C, an observed size within the cap or a known budget is recorded `unmeasured`; the finding's outcome is written by the platform, `findings.record_outcome`). A kept cycle waits in the Manager inbox (`rsi_cycle_view.inbox_items`, from `manager_inbox_extra`) as `merge_self_change`, which is in `ALWAYS_ESCALATE`: a policy naming it is a `PolicyError`, and the agent's `merge` suggestion is recorded and refused at every autonomy (decision 1: the first five kept changes are merged by a person; the automation after them is not built). A signed-in Owner records the merge, pinned to C's sha (`record_person_merge`, REQ-17; another sha is a 409 `not_pinned`), and resumes the loop after the stop (`resume`); a Manager, an API token, the Manager agent or nobody gets `not_an_owner`. `rsi_cycle_import.import_record` reads a record `scripts/rsi/cycle.py` wrote: it validates it with the script's rules (`services/contracts/rsi_cycle_record.validate` with `fitness.GUARDED`, kept in step by `test_rsi_cycle_record_parity.py`) and `kept_files`, reads `kept_files` as `cycle.py` writes it (`{path, sha256}`, relative to the cycle's work folder), hashes every kept file it can read under `RSI_FILES_ROOT/<cycle_id>/` (or `RSI_FILES_ROOT`) and refuses a record whose claimed sha256 differs; an absolute path is never read (`rsi_cycle_import_refused`, every problem named); a file it cannot read keeps its hash as a claim only. A `candidate_sha` must be a sha and a `decision` keep; a record of a cycle the backend ran must be of the same B and C (`merged_sha` may be the merge commit holding C); otherwise an `imported`, merged cycle is created with no person named. Every change is audited `rsi_cycle_<step>` (`started`, `sprint`, `candidate`, `tokens`, `budget_exceeded`, `size`, `size_refused`, `decided`, `merged`, `resumed`, `stopped`, `imported`) in the company's chain. Routes: `GET /v1/companies/{id}/rsi/cycles` (the state and the cycles) and `GET …/rsi/cycles/{rsi_cycle_id}` (Viewer); `POST …/rsi/resume`, `POST …/rsi/cycles/{rsi_cycle_id}/merge` and `POST …/rsi/cycles/import` (a signed-in Owner, never a token). No route starts a cycle or records a decision. After the review of PR #632, every step fails closed: `start` runs its checks, the creation and the commit under the company's `locks.RSI_CYCLE_START` (a start that finds it taken is refused `start_in_progress`); `record_sprint` refuses a missing or another company's sprint (`bad_sprint`); the size is read only from the integration of the cycle's sprint whose commit is C, and only when the parsed diff agrees with the daemon's inventory (`protected_merge.inventory_problem`), else `size_unobserved`, and a new C or integration clears the stored size; `read_size` checks the kill switches before asking the daemon; a keep re-reads the usage, every turn of the sprint reported and the bench's count recorded (`bench_tokens`), or it is unmeasured (`sprint_usage_missing`, `sprint_usage_incomplete`, `bench_usage_missing`), and over the budget it ends `budget_exceeded`; a decision whose `baseline` and `candidate` are not this cycle's B and C is refused (`decision_not_this_cycle`); the metric rows `fitness.decide` returns are kept as a list; the import leaves `sha256_observed` empty for a file it cannot read. A cycle's integration and its sprint's task branches are not offered as `merge_local`, and their merge is held for a signed-in Owner at the merge itself (`release/self_change.py`, [release](release.md)).

### The segregation-of-duties report

**`backend/app/services/management/sod_report.py`** / **`routers/sod.py`** — `GET /v1/companies/{id}/sod/report` (Manager, `no-store`; issue #543, [`docs/design/SEGREGATION_OF_DUTIES.md`](../design/SEGREGATION_OF_DUTIES.md)): every approval recorded (held deliveries accepted and runs approved from `run_reviews`, specifications and architectures from `approved_by`, run and integration merges) beside its requesters, as `separated`, `exception` (matched to its `sod_exception_applied` row), `violation`, `unattributed` or `not_a_person`; the `sod_refused` rows; and the matrix of duties (request, plan, deliver, verify, approve, release) per member with their effective role, per role and per agent role, flagging a member who both requests and approves. Computed from records only; `approver_name` is never read.

### The Support agent on the intake queue

**`backend/app/services/management/intake_triage.py`** — In the Support agent's loop (`SUPPORT_AGENT_ENABLED`, after the tickets, under `locks.SUPPORT_AGENT`), up to five pending requests nobody has triaged get a suggestion (issue #532): `DECISION … CATEGORY … DUPLICATE_OF … REASON … END`, with a decision among `accepted`, `declined`, `duplicate`, `snoozed`, a category among `bug`, `feature`, `question`, `incident`, and for a duplicate one reference from the candidates the prompt lists (the company's other requests and open tasks), checked by `parse_suggestion`; any other answer marks the request triaged without a suggestion, and a failed call leaves it for the next cycle. The request's text is treated as data and the agent has no tools. The suggestion is stored in `suggested_*` and never moves the request; a Manager decides ([planning](planning.md#the-intake-queue)), and `GET /v1/companies/{id}/intake-record` compares the two per category.
