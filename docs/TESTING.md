# Testing

The test suites, the end-to-end run, the bench and what CI runs. Moved whole from `CLAUDE.md`, whose index is [here](../CLAUDE.md). The i18n rule that `npm run lint` enforces is in that index (Frontend i18n).

## One command: `scripts/check.sh`

`scripts/check.sh quick` runs the checks a change can break, while working. It reads the files changed against `CHECK_BASE` (default `origin/main`, then `main`, then `HEAD`: committed since the merge base, staged, unstaged and untracked) and runs:

- for a change outside `frontend/`, the backend tests it can break (`scripts/affected_tests.py --run -- -n 0`, below) and `ruff check` and `ruff format --check` on the changed Python files of `backend/app` and `backend/tests`;
- for a change under `frontend/`, `npm run test:changed` (vitest's `--changed` against the same base; with no such ref, the uncommitted changes only), eslint on the changed files of `frontend/src` and `npx tsc --noEmit`;
- for a change to `.github/workflows/`, actionlint when it is installed;
- always, being fast, `check_architecture.py`, `check_frontend_architecture.py`, `check_file_sizes.py` and `check_changelog.py` (the changelog fragments, below).

`scripts/check.sh full` runs everything CI runs, once before pushing: the whole backend suite in parallel (`-n $CHECK_BACKEND_WORKERS`, default `auto`), ruff on `app` and `tests`, the LLM proxy's tests, the whole frontend (tsc, lint, `test:run`, build), actionlint and the four rule checks.

Both end with a summary of each step's status and time and exit non-zero when one failed. Neither reinstalls what is current: `frontend/node_modules` keeps the hash of the `package-lock.json` it was installed from, and the Poetry venvs of `backend/` and `llm-proxy/` the hash of their lock files (`.check-lock-sha256`); `npm ci` or `poetry install` runs only when one is missing or differs. `CHECK_PYTHON` and `CHECK_PROXY_PYTHON` name an interpreter instead of the Poetry venv, `CHECK_FILES` lists the changed files instead of asking git, and `CHECK_DRY_RUN=1` prints the steps without running them (`backend/tests/test_check_script.py`). `CHECK_REPORT=<file>` also writes each step to that file, one per line as `name<TAB>state<TAB>seconds`, which `scripts/land.sh` copies into its record.

### Landing: `scripts/land.sh`

`scripts/land.sh <branch>` is the gate into `main` (issue #728; `CONTRIBUTING.md`, Branches). In one worktree it keeps under `.git/fabrique/worktree`, reset and cleaned before each run (only `frontend/node_modules` survives, and `check.sh` reinstalls it when its lock hash differs), it merges `main` and the branch, runs `scripts/check.sh full` on that merge commit (`LAND_CHECK_CMD` names another command), and fast-forwards `main` only when it exits 0. The record (`.git/fabrique/verifications/<sha>.json` and the note of `<sha>` under `refs/notes/verification`) holds the commit, its tree and parents, the command, each step's status and seconds from `CHECK_REPORT`, the overall status and duration, the SHA-256 of the full log (kept under `.git/fabrique/logs/`), the tool versions, the host and the account. `scripts/land.sh --verify <sha>` runs the same command on `<sha>` in a clean worktree and compares the status and the steps with the record; durations are expected to differ and are not compared. What each option and exit status means is in `docs/OPERATIONS.md`, Landing locally.

`backend/tests/test_land_script.py` drives the script against a temporary repository with a bare remote, a fake `scripts/check.sh` and the real protected list: a passing branch moves `main` and writes the record and note, a failing or conflicting one leaves `main`, the checks run on the merge rather than the branch, a `main` that moves during the checks is merged and checked again, a diverged `main` is refused, `--push` mirrors `main` and the notes and refuses a tip without a record, `--verify` reproduces a record on a second clone and reports one that differs, a protected path is refused without `LAND_OWNER=1` and judged by `main`'s list rather than the branch's, and the lock holds against a live landing and is taken over from a dead one. It also runs shellcheck on the script when shellcheck is installed.

## Test Suite

The backend has a pytest test suite under `backend/tests/`.  No external services (Postgres, NATS, Neo4j, LLM proxy) are required — every boundary is stubbed with an in-memory SQLite engine or `unittest.mock`.

```bash
# Run all backend tests (fast, DB-free)
cd backend && PYTHONPATH=.:app python3 -m pytest tests -q
```

The suite runs in parallel with pytest-xdist (dev group): `tests/conftest.py` applies `-n auto --dist loadgroup` when the command names no `-n` (a hook rather than `addopts`, so `-p no:xdist` and an environment without xdist still work); `-n 0` or `--pdb` runs in one process, which is also quicker for a handful of tests (starting the workers costs about 3 s). Each worker has its own in-memory SQLite database, and `sqlite_session` empties it after every test, so no test reads rows another left behind. Emptied tables hand out their ids again, so what the process keeps by an id goes too: `conftest.PROCESS_STATE` lists each module-level container that can leak (by task, sprint, company or daemon id, a fake provider's issuer, a test's NATS client and loop), with its reason, and the autouse `forget_process_state` empties those of the modules the test loaded after every test; `test_process_state.py` fails on an empty container or an `lru_cache` at the top level of a `services` module that is neither there nor in its short list of safe ones. An autouse fixture acts on a module only once the test has loaded it (`when_loaded`: now, or right after a later import during the test), so a test loads only what it uses: the ScrumMaster's and the wiki's proxy are faked, the rate limiter reset and release's `sprint.closed` handler installed in the modules a test loads, the last through a stand-in that loads `integration_jobs` when a sprint first closes. The tests that time themselves (`xdist_group("wall_clock")`) share one worker, warm up first and keep the best of their timings. CI runs `-n 4`, since the self-hosted runners share one machine. On a 4-core machine the whole suite took 557 s in one process before (`--durations` showed single tests at 49 s and 39 s, paying for the rows of earlier tests, which the review cycle read again); now it takes about 370 s in one process and about 105 s with `-n auto`.

### Only the tests a change can break

Every `backend/tests/test_*.py` has a context, as data: `tests` in
`docs/architecture/contexts.json` maps each file to the contexts it exercises
(the top of what it imports and of the routes it calls; `repo` for a test that
reads repository files such as scripts, workflows or the frontend), and lists
the few that always run, each with its reason. `scripts/check_architecture.py`
fails when a test file has no entry, an entry names an unknown context or a
missing file, or a rule is unknown; a new test's entry starts from
`python3 scripts/affected_tests.py --suggest backend/tests/<file>`.

`scripts/affected_tests.py` prints the tests a set of changed files can break
(by default `git diff origin/main...HEAD` plus the working tree; `--files a b`,
`--base <ref>`). It has two ways to select, `--by module` (the default) and
`--by context`, and both fall back to the whole suite, and say why, for
`conftest.py`, the lock files, `backend/app/models`, `main.py`, the migrations,
`contexts.json` itself or a path no rule knows. `--run` runs pytest on the
selection from `backend/` with `PYTHONPATH=.:app` and the interpreter that runs
the script, passing what follows `--` through:

```bash
python3 scripts/affected_tests.py --files backend/app/services/loop/task_worker.py
python3 scripts/affected_tests.py --explain           # why each test is selected
<backend venv>/bin/python scripts/affected_tests.py --run -- -q
```

**By module** (`scripts/affected_graph.py`, `scripts/affected_modules.py`).
Every Python file of `backend/app`, `vscode-daemon`, `bench` and
`backend/tests` is a node of an import graph read with `ast`: plain, `from`,
relative and function-level imports, a package's re-exports
(`from package import name` is the module the package's `__init__` binds
`name` from), and in the
tests a dotted string that names a module (`mock.patch("services.x.y")`,
`importlib` by name), a `*.py` path string (a module loaded by path) and an
f-string's dotted head (`f"services.loop.{name}"`). Edges no import shows are
added: a module that calls `hooks.emit` uses every module that registers with
`hooks.on`, and a module whose top level changes another module's object uses
that module the other way. The routers are counted by URL: `main.py` mounts
them all, so a test that builds the app (`test_client`, `from app.main import
app`) does not reach a router through `main`; it reaches the routers whose
routes its URL strings match (`/v1/companies/{id}/webhook`, or a leading part
such as `"/v1/sprints"` that a path is added to), and every router when it
walks `app.routes` or `app.openapi()`. A changed module is then read by its
changed lines:

- inside function bodies only: the tests that use it, directly or through
  other modules (the reverse transitive closure). `conftest.py` and `main.py`
  are wiring, crossed only when they import the changed module themselves:
  `conftest`'s autouse fixtures patch, reset or install what they import, and
  `main` installs handlers, so a change to `lifecycle.py` selects every test
  that builds the app, and a change to a module `lifecycle` imports does not,
  through it;
- anywhere else (an import, a constant, a decorator, a default, a class body),
  or with no line information (`--files` without a diff; `--assume body|top`
  overrides): every test that loads it, by any edge, through `conftest`'s
  fixtures and the routers `main.py` mounts too. A raise at import fails
  exactly those tests. A module a `conftest` fixture names in `when_loaded`
  is no edge (the fixture acts on it only once the test has loaded it), and
  neither `services/__init__.py` nor `routers/__init__.py` imports anything,
  so a test that imports one module does not load the rest. For a top-level
  change, of the 229 test files `evidence/verification.py` selects 165 (all
  228 before), `tasks/task_events.py` 171 (228), `platform/agent_service.py`
  184 (228), `management/manager_agent.py` 127 (128) and `routers/webhooks.py`
  121 (123); most of the rest build the app (`test_client`), which loads
  every router. A raise injected at import into `evidence/verification.py`,
  `tasks/task_events.py` or `platform/agent_service.py` failed no test
  outside the selection.

Added to both: the changed tests and the tests that import them (a test file
is a node), the tests that walk a folder (`rglob`, `glob`, `os.walk`) and name
one of the changed file's folders, and the always-run set. A path that is not
a Python module of the graph (a script, a workflow, a document, a data file),
a deleted module, a bench file (read as data too), or any change while an app
module imports a module by a computed name, goes to the context rules below,
with the reason. `--explain` prints each selected test with the chain that
reaches the change (`test_webhooks.py -> routers/webhooks.py (calls
/v1/companies/{}/webhook)`).

**By context**, the tests of each changed module's context and of every
context that may import it (the dependency rule reversed: a change in platform
reaches loop), the changed test files and the tests that import them, the files
a rule in `tests.sources` names (a router or an app module stands for the
contexts it imports; a script, workflow or document for the tests that name
it), and the always-run set. A change low in the rule (contracts, platform)
selects nearly every test; one high in it (loop, release, management, a router)
selects far fewer. The context selection misses the tests that walk every
route when a router changes, and the tests that build the app when a router's
top level changes; the module selection does not.

Run the whole suite once before pushing.

Set up data with `tests/factories.py`, not through loop or management (not
`CompanyService`, the sprint or run routes, or a helper borrowed from another
test file): `company`, `user`, `member`, `headers`, `member_headers`, `sprint`,
`task`, `run` (with `task=`, the task worker's run of it) and `verification`
insert the rows directly, and the `enforcement` fixture turns authentication on
with a key made for the test. The module imports only the models, `auth_tokens`
and `config`, so it ties a test to no context; a test's entry in the map is
what the test itself calls, and a change to the factories runs every test that
imports them. `--suggest` reads the helper modules a test imports (not other
test files) with it.

plan; the optional row fields `difficulty_band`, `cost_cents` and
`cost_unknown` are checked when present and a card without them still reads. Schema v3 adds the weight of the prompts the backend sent
(`prompt`, `scripts/bench/prompt_weight.py`): each task's latest run's

per section, the prompts with sections cut and with related code, a run
without a measure counted apart; `compare.py` shows it before → after and
judges the mean per task only with `--prompt-tokens`.

#438): `sections_off`, the prompt sections a run turned off

per section, the criteria passed by the person-written tests, the rework

baseline's and their difference, over the specifications both ran in full.
`compare.py` prints that table, never judging it.

A change under `.github/workflows/` or to `.github/actionlint.yaml` runs every
job, and so does every push to `main`, every schedule and every manual run;
the bench is the exception (only its own two workflows start it).
The backend list is everything the backend suite reads outside `backend/`:
`backend/tests/test_ci_paths.py` fails when a test reads a path the filter
leaves out. So a docs-only pull request (`README.md`, `docs/TESTING.md`, a
design document) runs the security scans and nothing else, while
`CHANGELOG.md`, `docs/OPERATIONS.md` and `docs/STANDARDS.md` start the backend
tests (`test_release_notes.py`, `test_supply_chain.py` and `test_standards.py`
read them). A frontend-only change runs the frontend build, the file sizes and
the frontend image; a change under `backend/app` runs the backend tests, the
e2e, the file sizes and the backend image.

No workflow uses `on.pull_request.paths`: a workflow path filtering does not
start reports nothing, and a required check then waits forever. A job skipped
by its `if:` reports "skipped", which a required check accepts. The two matrix
jobs cannot be skipped that way (a skipped matrix job reports once under its
bare name, so `build (backend)` or `e2e (host)` would wait), so they start and
skip their steps, ending in seconds as a success. When the `changes` job
itself fails, every gated job runs. `test_ci_paths.py` holds all of this.

**The bench on a pull request** (`bench-pr.yml`, issue #316) is the nightly
fake-model run of `bench.yml` on a pull request that changes the bench
itself (`bench/`, `scripts/bench/`, either bench workflow; a backend change
alone does not start it, since the runners are one machine and the nightly
run covers the backend): the same steps (held equal by `test_ci_paths.py`), the same
comparison with the newest card in `bench/scorecards/` and the same
thresholds, so a regression fails the check. Its filter is its own `changes`
job (the same `scripts/changed_paths.py`), not an output of `changes.yml`,
whose backend filter also holds `CHANGELOG.md` and would start the bench on
nearly every pull request. It leaves out the nightly extras (the strict
performance budgets, the regression issue), holds no secret and no token that
writes, and takes an e2e slot once `E2E_RUNS_ON` names the label. The
real-model job, the watch and the revert stay in `bench.yml`, which a pull
request never starts.

The `changes` job runs only steps GitHub provides and `git`: this repository's
Actions policy allows GitHub-owned and Marketplace-verified actions only, and a
called workflow that uses anything else fails at startup before a job is
created, which takes every caller with it. The same policy refuses a
`docker://` step, so `workflows.yml` installs actionlint from a pinned,
checksummed release instead of running its image. Keep it that way, or widen
the policy deliberately in Settings → Actions → General.

**At most two e2e jobs at once, once turned on.** By default an e2e job takes
any runner, as before. Setting the repository variable `E2E_RUNS_ON` to
`["self-hosted","linux","x64","lafabrique","e2e"]` makes an e2e job that runs
the loop ask for the runner label `e2e` besides `lafabrique`; with only two of
the seven runners carrying it, GitHub queues any further e2e job until one of
the two is free, across every pull request, without cancelling anything. Label
the runners first, then set the variable (`docs/OPERATIONS.md`, Runner
capacity). A concurrency group cannot do this: it holds one running and one
pending run per group, and a third arrival cancels the pending one, a failed
check. An e2e job with nothing to run takes any runner. Each workflow's
own group (`<workflow>-${{ github.ref }}`, `cancel-in-progress: true`, #559)
still cancels the older run of a pull request when it gets a new push.
