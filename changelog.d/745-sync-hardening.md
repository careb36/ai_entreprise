Security

* **The base sync hardened: no git prompt, a guarded folder check, the stack read after the sync (issue #745, follows #747).** Every git command of the workspace daemon runs with `GIT_TERMINAL_PROMPT=0`, an empty `GIT_ASKPASS` and `GCM_INTERACTIVE=never`, and one that can reach a remote with `GIT_SSH_COMMAND` ending in `-o BatchMode=yes`, appended to the person's own (`GIT_SSH_COMMAND`, `core.sshCommand` or `GIT_SSH`; `vscode-daemon/git_env.py`): a remote that wants a passphrase, a password or an unknown host key fails at once as `remote_needs_interaction` instead of waiting out its time limit (the sync, the base's fetch before a branch, the check before publishing). `POST /v1/workspace/git_check` is held, past authentication, to a role rule (with several accounts, only an account with a company role or the deployment's first account), a per-account limit (`GIT_CHECK_RATE_LIMIT`, default `10/minute`), an audit row per "Check remote" (`folder_remote_checked`, with the account and the folder, never a URL) and an answer limited to branch names, flags and counts (no commit ids, an unreadable remote as a code); `SECURITY.md` documents the rule and no longer lists it as a known gap. When "Bring my local copy up to date" moved the base, `POST /v1/init_company` reads the stack again from the updated folder (`detect_stack`), so the stack recorded is the one the agents read. The test engine's shared SQLite connection no longer lets a read on one thread see rows another thread has not committed (`tests/shared_sqlite.py`), which made `test_code_graph_store` fail about once in 40 runs under `-n 8`.
