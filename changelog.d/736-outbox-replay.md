* **Operators can replay a failed or stuck outbox event without hand-editing the database or the NATS stream.** `POST /v1/admin/outbox-events/{event_id}/replay` (support admin only, `SUPPORT_ADMIN_EMAILS`) returns a `failed` or stuck `pending` outbox event to `pending` under `SELECT ... FOR UPDATE` and returns its id. The committed payload and correlation id are untouched, so the running `process_outbox` poller republishes the same message with the same `Nats-Msg-Id`. A replay never re-runs the domain logic that created the event, so no second sprint task or backlog row is produced. A `completed` row, or a `pending` row that is already due, is refused with `409`; a missing row is `404`. The publish path is factored into `outbox_service.dispatch_event`, shared by the poller and the replay, so both deliver through one code path.
