* **A self-hosting run can hold itself to the container sandbox (issue #701).** `scripts/self_host/self_host.py` gains `--container-mode` (`scripts/self_host/sandbox_mode.py`, `add_arguments` and `apply`): it sets the company's sandbox to `container`, one root command run with the sandbox image's own `python` (`--profile sprint-tests`, `python -m pytest -q -p no:cacheprovider tests`; `--profile` and `--test-command` still override), and the `sandbox` step after `wait`. The `sandbox` step reads, from the daemon's reply to each of the sprint's test runs (`evidence.test_run.sandbox`), the mode the replies report — `container`, `host`, `bwrap`, `mixed`, or `not observed` — and keeps it apart from `asked`, the mode the harness configured, in the report's `sandbox` (`asked`/`observed`/`observed_by: daemon`, `container_mode`, `modes`, `images`, `container_mode_asked`); the daemon's announced abilities are a claim and never label a run. A `--container-mode` run whose replies are anything but `container` — `host`, `bwrap`, a mode reported `(not isolated)`, `mixed`, or `not observed` — is never labelled container mode: the harness exits with status 5 and adds the reason to `notes`. `backend/tests/test_self_host_sandbox_mode.py` proves the flag reaches the sandbox setting and that a non-container observation fails the run, against replies in the daemon's own fixture shape. `scripts/self_host/README.md` documents the flag, the observed/asked split, and the stack-side settings an owner must set, as the e2e's `container` job does.
