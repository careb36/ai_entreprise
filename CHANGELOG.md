## [Unreleased]

### Security

* **The janitor no longer connects with the `.env.example` placeholder password (found while documenting the configuration, PR #675).** With `POSTGRES_PASSWORD` unset or blank, `backend/janitor/main.py` fell back to `your_secure_password_here`; it now logs `Janitor refused to start: POSTGRES_PASSWORD is not set` and exits with status 1 before the daily loop. Configuration defects fixed with it: `docker-compose.yml` passes all 13 `AGENT_MODEL_<ROLE>` variables to the backend (it passed 8, so the backend, frontend, DevOps, Designer and data engineer roles could not be set from `.env`); `AGENT_GRAPH_ENABLED` defaults to `false` in compose as in `config.py` and `.env.example` (the compose stack had the LangGraph producer on unless `.env` turned it off); compose no longer sets `PROXY_PORT` on the proxy (the image binds gunicorn to 5100; `python llm-proxy/app.py` still reads it) nor `OTEL_EXPORTER_OTLP_ENDPOINT` on the daemon, which has no telemetry; `OPENPROJECT_TOKEN_DEV` stays declared in `config.py`, marked as never read, so a `.env` that still sets it keeps the backend starting (the settings refuse unknown keys from that file).

* **Link your SSO identity from inside a signed-in session, and unlink it (issue #512; `docs/design/SSO.md`, T25–T32).** A new Account page (`/account`) lists your identities and the companies whose provider you can link; Link starts an authorisation (`POST /v1/auth/sso/link/start`, browser session and CSRF only) whose one-time state is bound to the browser and to your live session, with PKCE and a nonce. The provider's verified email must be your account's, in a domain the company verified by DNS (a legacy domain's grace does not count), and a subject linked to someone else is refused; your password is kept. This lets a person in several companies link, which the sign-in's email linking refuses. You may unlink yourself only while another way to sign in remains; an Owner can list and unlink the identities of the company's connection (`GET`/`DELETE /v1/companies/{id}/sso/identities[/{id}]`), which ends the person's SSO-started sessions. Every link attempt and unlink is audited (`sso_identity_link`, `sso_identity_unlink`), in the same transaction as the change, so a failed audit write leaves nothing changed. **Upgrade:** migration `0050` adds a unique index so an account holds at most one identity per provider (two racing links end as `identity_conflict`); if an account already holds two, it stops and changes nothing (`docs/OPERATIONS.md`, The SSO identity migration stops on duplicates). Tests: `backend/tests/test_sso_link.py`, `test_sso_link_integrity.py`, `frontend/src/components/SsoIdentities.test.tsx`.
* **A browser image per Playwright release, chosen from the version the project pins (issue #315).** `images.yml` builds the browser sandbox for each release of `vscode-daemon/images/browser/playwright_versions.json` (1.63.0 and 1.64.1, the default), each with its lockfile and its headless shell checked by sha256, tagged `X.Y.Z-playwright-<release>` and signed, attested and recorded by digest; `playwright_matrix.py` checks the list before any value reaches a build. The daemon reads the Playwright the project pins from its `package.json` and lockfile (npm, pnpm, Yarn, Bun; `vscode-daemon/playwright_pin.py`) into `workspace.inspect`'s snapshot. With `DELIVERY_BROWSER_IMAGES` (`release=image@sha256:…`, a tag refused), the application check runs a browser e2e command in the image of the project's release, falls back to `DELIVERY_BROWSER_IMAGE` with the mismatch recorded, and with a version nobody could tell starts the application without the browser suite: `e2e_run` is unverifiable with the reason, never a pass. Empty, nothing changes. Tests: `backend/tests/test_playwright_pin.py`, `test_browser_images_playwright.py`, `test_supply_chain.py`.
* **A company's SSO domains are verified by DNS before SSO creates or links accounts in them (issue #512; `docs/design/SSO.md`, T16–T24).** Saving the connection issues a random token per company and domain; the Owner publishes `la-fabrique-domain-verification=<token>` as a TXT record at `_la-fabrique-verify.<domain>` and asks for a check (`GET /v1/companies/{id}/sso/domains`, `POST …/sso/domains/{domain}/check`, Owner only, rate-limited); a daily re-check (`SSO_DOMAIN_RECHECK_HOURS`) unverifies a record that is definitely gone and verifies a newly published one. Every lookup is recorded (`sso_domain_checks`: time, trigger, requester, outcome and the strings seen) and every status change is audited. An unverified domain refuses account creation and linking with `domain_unverified`; an identity already linked keeps signing in, and a transient DNS failure changes nothing. A domain another company verified can no longer be listed, while an unverified listing no longer keeps anyone out (the first-come rule is gone), and a newer proof re-checks the older claim first. **Upgrade:** migration `0049` marks every existing domain `legacy`; legacy domains keep working for `SSO_LEGACY_DOMAIN_GRACE_DAYS` (30) while `SSO_LEGACY_DOMAIN_GRACE` is on (the default), so verify them in that time. New dependency: `dnspython` (ISC), since the standard library cannot read TXT records; the resolver is isolated in `services/platform/dns_client.py`. New settings `SSO_DNS_TIMEOUT_SECONDS` and `SSO_DNS_NAMESERVERS` (`docs/CONFIGURATION.md`). `docs/design/SSO.md` also now records the member-removal endpoint and the login rate limit, which exist. Tests: `backend/tests/test_sso_domains.py`, `test_sso_domain_sign_in.py`, `test_sso_dns_client.py`.
* **The security programme's exception register, metrics and training notes (issue #522, the parts PR #526 left out).** `SECURITY.md` §17 adds the exception register (the five licence exceptions of `.github/licence-exceptions.txt` with their 2026-12-31 review date, listed as open owner decisions and not accepted; the Dependabot `ignore` entries, the non-gating Trivy scan on pull requests and the SLSA generator's tag, each with its reason, mitigation and whether the reason still holds; the closed `safeReturnPath()` and `safety check || true` entries), the open owner decisions (the licences, "Require review from Code Owners", whose two settings disagree on 2026-11-18, and the entries with no date or acceptor), a metrics table read on 2026-11-18 with the source of every number and the ones that could not be read (Dependabot alerts, the audit chain, the daemon's dependency age) marked so, and training notes with the lessons of #39, #524 and #525. §5.4 replaces the 2026-10-29 snapshot (the `react-router` and `pytest` advisories are closed by upgrades), §11 gains the positioning's design rules as rule 11, and `CONTRIBUTING.md` gains a Security onboarding section. Documentation only.

* **Python and Go installs survive between container runs, in an environment volume no other project or company shares (issue #315).** With `DELIVERY_SANDBOX_ENV` (off by default), the daemon mounts `fabrique-env-<key>` at `/fabrique-env` with `PYTHONUSERBASE`, Poetry's and Pipenv's virtualenvs and Go's `GOPATH`, module and build caches pointing into it (`vscode-daemon/sandbox_cache.py`). The key is the project, the company (`scope: company:<id>`), the image and the sha256 of the Python and Go manifests; only an install writes it, every other run mounts it read-only, the image's binaries stay first on `PATH`. A failed install removes it, three in a row quarantine it until the cache's reset, which now removes the company's environments too and makes the next delivery install again; at most three are kept per project and company; `FABRIQUE_SANDBOX_ENV=off` refuses it. Tests in `vscode-daemon/tests/test_sandbox_env.py` (a new daemon suite, run by `backend-tests.yml`) and `backend/tests/test_sandbox_cache.py`.

* **An API token's creator is its account, not its email address (issue #512, after the SDL review of PR #644).** `api_tokens.created_by_user_id` (migration `0048`, nullable, a foreign key to `users.id`) records the creator's account id when a token is minted, and the cap on every use (`services/platform/api_tokens.creator_role`) compares on it: a creator who changes address keeps the token's standing, and whoever later holds the old address does not inherit it. An id whose account is gone is refused, never resolved by email. The migration backfills the id from `created_by` where an account has that address (stripped and lower-cased); a token with no matching account keeps a NULL id and is judged by its email as before, and one with no creator stays uncapped as before. `created_by` is kept for the access review. Separation of duties reads the same id (`sod.actor_of`): a renamed creator's token cannot approve its creator's own request, and a reused address no longer blocks its new holder. Tests in `backend/tests/test_api_tokens.py` (a rename, a reused address, a gone id, a row without an id, the HTTP mint, the backfill) and `backend/tests/test_sod.py` (a renamed creator refused, a reused address not blocking, a gone id not read by email).
* **An API token never outranks its creator's current role (issue #512, threat T5 of `docs/design/TEAMS_AND_USAGE.md`).** On every use, `services/platform/api_tokens.verify` reads the creator's effective role (teams included) in the token's company; a token above it, or one whose creator is no longer a member or has no account, is refused with the same 401 as a revoked token and audited `api_token_refused` with the reason (`creator_role_below_token`, `creator_not_a_member`), at most once per token, reason and hour. It is refused rather than lowered, so an integration fails visibly instead of half-working; it is not revoked, so a creator promoted back carries it again. A token minted while authentication was off has no creator and is not capped. Minting above your own role was already refused (403). Tests in `backend/tests/test_api_tokens.py`: demotion, removal, a deleted account, an equal role, an Owner creator, a team seat ended, the HTTP 401.
* **Account and invitation hardening from a WSTG review (IDNT-04, CONF-05, ATHN-07).** Breaking, read before upgrading:
  - **`POST /v1/company/invite` no longer adds anyone.** It answers `202 {"status": "pending", "detail", "token"}` whether or not the address has an account (it answered 404 "User not found", so anyone who created a company could test addresses) and records a pending invitation (`company_invitations`, migration `0046`: company, normalised address, role, inviter, expiry `INVITATION_TTL_HOURS` (168), single-use token kept only as its sha256). The invitee, signed in with that address, sees it at `GET /v1/invitations` and accepts (`POST /v1/invitations/{id}/accept`, or `POST /v1/invitations/accept` with the token of a link) or declines (`.../decline`); only acceptance creates the membership. A Manager may now invite Viewers and Managers, only an Owner invites an Owner, never with an API token; Managers list and revoke pending invitations (`GET`/`DELETE /v1/companies/{id}/invitations[/{invitation_id}]`). Invite, accept, decline and revoke are audited. A script that relied on the invite making a member must now have the invitee accept, and the invitation routes need a signed-in person even with `AUTH_REQUIRED=false`. The frontend's Members page invites, shows the link and lists and revokes pending invitations; the new Invitations page (company menu, also shown on New company) accepts or declines, and follows a link's token.
  - **The API documentation is off by default.** `API_DOCS_ENABLED` now defaults to `false` (`/docs`, `/redoc`, `/openapi.json` answer 404); `docker-compose.yml` sets it to `true` for local development. Set it explicitly where you want the schema published.
  - **Passwords chosen now have at least 12 characters** (`PASSWORD_MIN_LENGTH`), on registration and any route that sets one; bcrypt's 72-byte maximum is unchanged. Existing accounts keep signing in with their current password.
  - **Email addresses are one account whatever their case.** They are stripped and lower-cased on registration, sign-in, invitation and lookup (`services/contracts/emails.py`). Migration `0045` normalises the stored addresses and adds a unique index on `lower(email)`; **if two existing accounts collide, it stops and names their ids, changing nothing** (it never merges or deletes): see `docs/OPERATIONS.md`, The email migration stops on duplicates.
  - The per-address limits behind a reverse proxy: `TRUSTED_PROXY_IPS` (empty by default: trust none) lists the proxies whose `X-Forwarded-For` is believed; the client is then the right-most address that is not a listed proxy (`security.TrustedProxyMiddleware`). The image runs uvicorn with `--no-proxy-headers`. Setup for nginx and Traefik: `docs/OPERATIONS.md`, Behind a reverse proxy.
  - Registration attempts the insert for a taken address too (the unique index refuses it), so both paths do one bcrypt hash and one insert and answer alike.
  Tests, each written first and failing on the previous `main`: `backend/tests/test_invitations.py`, `test_email_normalisation.py`, `test_trusted_proxies.py`, `test_password_rule.py`, and new cases in `test_security_headers.py`.
* **stdio MCP servers are off by default, and an operator enables them with an allowlist; an HTTP MCP server is reached only on a public address (WSTG review). Breaking for anyone who uses a stdio MCP server.** A stdio server spawned any command a Manager named, as the backend; now its `command` must be exactly one of the absolute paths in the new `MCP_STDIO_ALLOWED_COMMANDS` (empty by default, so stdio is disabled): a bare name such as `npx`, a relative path, `..`, another case or a symlink under another name is refused when saved (400), when enabled (409) and before every start, and an existing row the list does not cover lists with `start_refused` and is never started. **To keep a stdio server, install a fixed server binary or wrapper script in the backend's image, list its path in `MCP_STDIO_ALLOWED_COMMANDS` and save the server again with that path** (`docs/OPERATIONS.md`, MCP servers); allowing an interpreter or a package runner allows any code. Arguments are a bounded list passed without a shell; an environment variable that changes how a program loads code (`PATH`, `LD_*`, `PYTHON*`, `NODE_*`...) and a relative `cwd` are refused. `GET /v1/mcp/servers/{id}/tools` starts the server, so it now takes a Manager (a Viewer gets 403 and nothing runs), and every start, and every refusal, is audited before it happens (`mcp_server_start`, `mcp_server_start_refused`); the task worker audits each start of a stdio server as `agent:<role>` and starts none it cannot audit. An HTTP or SSE server's URL must be https (http only for a host in the new `MCP_HTTP_ALLOWED_HOSTS`) without credentials, on a host that resolves only to public addresses, checked with `services/platform/egress.py` when saved and again before each connection, which goes to the checked address with the host in `Host` and SNI, so loopback, private, link-local (the metadata service) and rebinding names are refused; **a stored server on a private address stops working**. The connection no longer goes through an environment proxy (`HTTPS_PROXY`). A connection failure answers a fixed 502 with the reason only in the backend's log. The backend logs at startup the stdio commands it allows and warns when one is an interpreter, a package runner or a shell. The HTTP and SSE transports, which handed `mcp.Client` the transport's streams instead of the transport and so never connected, now work. A malformed URL is refused with a reason (400, or `start_refused` on a stored row) rather than a 500; a server the task worker refuses and a start refused when connecting are audited as `mcp_server_start_refused`; saving resolves hosts off the event loop. New module `services/tools/mcp_policy.py`; tests: `backend/tests/test_mcp_security.py` and `test_mcp_refusals.py`, negatives first. Reused: the project's own `egress.pin` (#541), as the webhook, the OIDC client and the research fetches use it. Compared with (design only, no code): GitHub Copilot coding agent's firewall, whose outbound allowlist is set by an administrator, not by the agent or the task.
* **Candidate code is graded in the sandbox (PR 12 of `docs/design/rsi-loop.md`, first part; G4, #323).** The self-hosting harness's target measure (`spec_source.run_measure`) and the bench's acceptance tests (`scripts/bench/bench_grade.py`, moved out of `scorecard.py`) run in the workspace daemon's container sandbox, reused through `scripts/bench/sandbox_grading.py`: network off, the root, the candidate's tree and the pinned graders read-only, a fresh scratch and `/tmp` the only writable places, CPU, memory, process and time limits, an image already on the machine run from its content ID and never pulled, no variable of the runner's environment. The verdict is the runtime's exit status and pytest's report printed by the runner's wrapper after every other process in the container was killed, the last frame with this run's nonce, never a file the candidate could write; a pass needs both to agree. No runtime, no image, `bwrap`, a timeout, a kill by a limit or an inconsistent report is `unmeasured` (`self_host.py` exits 4), never passed. The in-process path stays behind `--in-process-measure` / `BENCH_GRADE_IN_PROCESS=1`, says so in its output, and `fitness.decide` refuses a target graded that way (`not_sandboxed`); `vscode-daemon/sandbox.py` and `sandbox_image.py` became protected paths. The held-out set's interface is documented in rsi-loop §2.3, not built. After review: with `run.sh --graders <B>` the daemon's modules the grader imports on the host come from B's git objects, hash-checked, never the candidate's checkout (and `sandbox_cache.py`, `run_logs.py` are protected too); the scratch is a bounded tmpfs, and filling it is `unmeasured`; a grade the sandbox could not give is not measured in `decide.py`, `fitness` and `watch.py`, never a criteria rate of 0; a target result must say `isolation: sandbox` explicitly; a skipped test is told apart from a failed one; the cleanup after a timeout has a deadline. Threat model: `docs/design/SANDBOX_GRADING_THREAT_MODEL.md`. Taken from, design only: OpenHands' Docker runtime per session (an ephemeral container with the workspace mounted and resource limits) and OpenAI Codex cloud's sandboxed runs (network off, the command and its output cited by the runner).
* **The self-improvement cycle is recorded and limited by the backend, and no rule merges a self-change (PR 10 of `docs/design/rsi-loop.md`, REQ-22 to REQ-26).** `rsi_cycles` (migration `0044`; `services/management/rsi_cycle.py`, `rsi_cycle_steps.py`, `rsi_cycle_view.py`, `rsi_cycle_import.py`) holds a cycle per company and finding: B and C, the status, the fitness decision with its reasons, the diff's size the workspace daemon observed in git, the token budget and the reported tokens, the kept files with the hash the backend computed beside the runner's claim, and who merged. `RSI_ENABLED` (off by default) and the company's protected-paths flag (decision 3: the Owner's flag that marks the self-hosting company; no second flag) are the kill switches, checked when a cycle starts and at every step, which stops the cycle and its sprint (REQ-24). The backend refuses, audited `rsi_cycle_refused` with a reason: a second cycle the same day; any cycle after three in a row without a keep until a signed-in Owner resumes (REQ-23; not a Manager, an API token or the Manager agent); a keep over 20 files or 600 changed lines, or whose size the daemon did not show in full, which stays unmeasured and waits for a person (REQ-25); any cycle while the first manual sprint's tokens are unknown, and a cycle past its budget (twice those tokens at most, decision 7), which ends `budget_exceeded` with its sprint stopped (REQ-22). A kept cycle waits in the Manager inbox as `merge_self_change`, now in `ALWAYS_ESCALATE`, so no policy names it and the agent is refused at every autonomy; a signed-in Owner records the merge, pinned to C's sha. A runner's record (`scripts/rsi/cycle.py`) is imported only after it validates by the script's own rules (`services/contracts/rsi_cycle_record.py`, kept in step with `scripts/rsi/cycle_record.py` by a parity test) and every kept file the backend can read hashes to what the record claims (REQ-27). `GET /v1/companies/{id}/rsi/cycles[/{rsi_cycle_id}]` (Viewer); `POST …/rsi/resume`, `…/rsi/cycles/{rsi_cycle_id}/merge`, `…/rsi/cycles/import` (a signed-in Owner). `models/run_cost` joins that context's interface. Taken, design only, no code: OpenHands' confirmation mode (a decision no policy hands to the agent) and its trajectory as an event stream (each step audited `rsi_cycle_<step>`, replayable as Devin's session replay); the GitHub Copilot coding agent's and GitHub's merge with an expected head sha (the merge pinned to C); OpenAI Codex cloud's hashes and logs cited by the runner, never by the party recorded (the backend recomputes each kept file's sha256). After review, a cycle's integration and its sprint's task branches are merged only by a signed-in Owner, enforced at the merge itself (`release/self_change.py`), and every piece of a cycle's evidence fails closed: the size only from the integration of its sprint at C with a complete parsed diff, the usage re-read and complete at a keep, the decision only for its own B and C, and one start at a time per company.
* **What the #541 WSTG review left open.** **A `JWT_SECRET_KEY` shorter than its algorithm's hash (32 bytes for HS256) now counts as unset**, so login answers 503 instead of signing with a key that one captured token lets an attacker guess offline (WSTG-SESS-10, weak HMAC keys; the documented generator gives 64). The per-account login backoff no longer loses a lock when its bounded record fills: making room drops a record without a running lock first, so failures spread over other addresses cannot reset the attacked account's backoff (WSTG-v42-ATHN-03). A 422 now carries each error's `type`, `loc` and `msg` only, without FastAPI's `input` and `ctx`, which echoed the value sent, a password or key included (WSTG-v42-ERRH-01). The web frontend's Vite dev server (what `docker compose up` serves) and `vite preview` send `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer` and COOP, so no other site can frame the page where approvals and undo are clicked (WSTG-v42-CLNT-09).
* **The loop's findings are records, and a reverted specification does not silently start again (PR 9 of `docs/design/rsi-loop.md`, REQ-18, REQ-20).** A retrospective finding becomes a `Finding` row per company (migration `0043`; `services/learning/findings.py`): its source (the retrospective's file and item, `F5`), title, the specification drafted for it, its target measure (the repository path of the person-written check) and the outcomes of its cycles, each with the fitness decision (`keep` / `revert` / `unmeasured`), its reasons, the baseline's and the candidate's sha and the date. The outcomes are observations only the platform writes — `record_outcome` refuses any other `produced_by`, an unknown decision or a missing sha (REQ-27) — and the finding's status follows them (`open`, `in_cycle`, `kept`, `reverted`, `unmeasured`, `closed_by_person`, the last one by a signed-in person alone). `create_from_specification_file` reads a specification in the PO's shape and computes the sha256 of its *canonical* text itself, whatever the file claims (rule 6): JSON re-serialised with sorted keys and no whitespace between tokens, its string values kept exactly, and any other text with only its line endings and trailing spaces dropped; a duplicate of the company's specification is refused, by the service and a unique constraint. `may_start` is REQ-20: the same canonical text as a specification whose cycle was reverted — so a pretty or compact rewrite makes no difference — starts no cycle unless a person asks, a signed-in Manager or Owner of the company; an agent, an API token's synthetic user, a user that was never persisted, a Viewer or another company's person is refused, as `routers/sod.owner_person` refuses a token, and another company's reverts are never read. The person's request is `retry_by_person` (a reverted or unmeasured finding back to `in_cycle`, its outcomes kept; a running, kept or person-closed one refused), audited like `close_by_person`. Read-only routes: `GET /v1/findings` (status filter) and `GET /v1/findings/{id}`, any company Viewer; no route writes an outcome or starts a cycle — the runner (PR 10) will. Tests: `backend/tests/test_findings.py` and `test_findings_retry.py`, negatives first. Taken from (design only, no code): Kiro's spec-driven findings before tasks, and GitHub Copilot coding agent's rule that the platform's own record, never the agent's report, is the evidence.
* **The merge guard cannot be bypassed by a quoted file name, and follows a changed diff (review of PR #625).** The workspace daemon's `workspace.git.diff` now also lists every changed path from `git diff --name-status -z --no-renames` (`paths`, never quoted, a rename as both sides), which the guard matches and which enters `diff_sha256`; a protected file renamed to a name with a tab, whose patch header the parser skipped, is now refused, as is any reply whose list is missing or disagrees with the parsed files. An acknowledgement may name up to 600 paths. The Manager agent's integration item names the observed diff's hash and the approving review, and a review on a diff that changed since a refused merge replaces the kept check, so a new acknowledgement leads to a new guarded attempt.
* **The integration merge refuses a protected path without an Owner's acknowledgement, and the model-planned follow-up is off for the factory's own company (PR 3 of `docs/design/rsi-loop.md`, REQ-13, REQ-21).** For a company with `protected_paths_enabled`, merging a sprint's integration locally (the web, the Manager agent or the harness) reads the integration's diff from git through the daemon and matches each file, and a renamed file's old path, against the running backend's protected list; a match is merged only when the integration's approving review of that commit, recorded by a signed-in Owner on the same `diff_sha256`, names every matched path in `protected_paths_ack` (`integration_reviews.protected_paths_ack`, migration `0042`; sent with `event: approve` on `POST /v1/sprints/{id}/integration/reviews`, refused for a Manager, an API token and the Manager agent, audited in the review's row). Otherwise the merge is a 409 naming the paths, audited `integration_merge_refused_protected_paths` and kept on the integration (`details["protected_paths"]`), so the Manager agent's inbox shows the refusal (`:protected_awaiting_ack`) and its `merge_local` rule waits for the acknowledgement; the paths the tasks declared are never read, and a diff the daemon cut short is refused (`services/release/protected_merge.py`). The model-planned follow-up sprint (`_plan_follow_up`) never runs for such a company, whatever `AUTO_SELF_IMPROVEMENT_ENABLED` says: the close answers `protected_paths_enabled`, logs it and audits `follow_up_sprint_skipped`. Without the flag nothing changes. Taken from (design only, no code): GitHub's code-owner review on the head commit (an approval is of a sha, and a new push needs a new one), as layer 4 will require on pull requests.
* **The Verifier holds a protected path for a person (PR 2 of `docs/design/rsi-loop.md`, REQ-3, REQ-10, REQ-11).** A company an Owner marks as hosting the factory (`companies.protected_paths_enabled`, migration `0041`, false for every company; `GET`/`PUT /v1/companies/{id}/protected_paths`, a Viewer reads the flag and the list in force, only a signed-in Owner changes it, never an API token, audited `protected_paths_setting_changed`; on the Duties and access page) gets a Verifier check, `protected_paths` (`services/evidence/protected_check.py`): the paths the daemon observed the delivery write, and those it saw a console producer change, plus the paths the producer declared (which may add to a match, never remove one) are matched with `contracts.protected_paths.matches` against the running backend's list, never the company's project. A match is named in the check (outcome `pass`: a reason for a person, not a fault) and `risk.classify` gives it the tier `high` with the new area `grader`, so the task waits for a person at every autonomy level. The Manager agent's `accept_high_risk` (and `accept_delivery`) refuses a delivery that touches a protected path, the Verifier's match or the run's paths matched again when it was verified before the flag, so a person reviews it through the normal review; `change_protected_paths` joins `ALWAYS_ESCALATE`. * **Tasks in the order they depend on.** The PO's plan says which tasks must be done before another starts; `POST /v1/start_sprint` keeps it (`depends_on`, checked: an unknown task, a task depending on itself or a cycle is refused). A person answers, asks for a revision, edits in a structured form, approves; **Write to the repository** sends `docs/ARCHITECTURE.md` through the workspace daemon and keeps the sha256 it read back. The PO plans along the modules, and each task's prompt and QA's review carry the modules its requirements map to, with their interfaces, and the decisions and conventions every task follows (`/v1/architectures`).
* **The specification: what the agents build from, as data.** A Manager gives the PO a brief and gets a draft: numbered requirements (`REQ-1`), each with acceptance criteria written as given / when / then (`REQ-1.2`), quality attributes with a number to measure them by (`NFR-1`), constraints, and the questions the PO could not decide. The ids are assigned by the backend, never by the model. A deterministic check says what blocks approval (a requirement without a criterion, a criterion with an empty step, a target without a number, an unanswered question) and what only warns ("fast", "easy", "rápido" without a number). A person answers the questions, asks the PO for a revision (the answers go into its prompt), edits in a structured form, and approves; an approved version is never edited, a revision is a new draft that supersedes it. Planning from an approved specification has the PO split it into tasks that name the criteria they cover, lists the criteria no task covers, and the sprint keeps that: each task's prompt and QA's review carry only the requirements it covers, and the specification shows, per criterion, whether a task got done, is blocked, is planned or does not exist (`/v1/specifications`, `POST /v1/plan_sprint` and `POST /v1/start_sprint` with `specification_id`; the Specifications page and the Plan a sprint form).
* **Comments from the pull or merge request, back in the run.** A Manager presses **Bring comments** on a published run: the workspace daemon reads the request's line comments, reviews and conversation with the person's `gh` or `glab` login (`workspace.git.reviews`), and each one appears on its line in Files changed, marked as written on GitHub or GitLab, with its link and, for a review, its state. Reading again never duplicates; the next review submitted here carries them to the agent like any comment, naming who wrote each and where (`POST /v1/agent_runs/{id}/publications/{pid}/sync`).
* **Publish a task's branch as a pull or merge request.** From a run's Files changed, a Manager publishes `fabrique/task-<id>`: the workspace daemon pushes it to `origin` with the person's own Git credentials and opens a draft pull request (`gh`) or merge request (`glab`), or answers with the page that opens one (`workspace.git.publish`). The description carries the evidence the Verifier observed, the producer's claims apart and a `Fabrique-Run:` trailer; each publication is kept and audited (`POST /v1/agent_runs/{id}/publish`, `GET .../publications`).
* **Git branch per task.** With the company's Git workflow on (`PUT /v1/companies/{id}/git`, the Board's toggle), each task's deliveries are commits on `fabrique/task-<id>`, in a worktree under the repository's git directory, from the base the company names or the checked-out commit; the person's checkout, index and branch are never touched. The daemon reports the branch, commit and parent as git said them (`vscode-daemon/git_workspace.py`), kept on the evidence; delivery tests run in the worktree; Files changed names the commit.
* **Review comments and decisions, as on a pull request.** A Manager comments on a changed line (new or old side), resolves comments, and submits a review: Comment, Approve or Request changes, carrying the open comments. On a task the agents delivered, Request changes sends a task blocked for a person back to work with the comments, file by line, as its `NEEDS WORK:` feedback, and Approve accepts a delivery QA approved that waits for a person; anything else is refused with the reason, since QA and the Verifier decide. On another producer's run the review records the approval or rejection. Audited, never evidence (`/v1/agent_runs/{id}/comments`, `/v1/agent_runs/{id}/reviews`).
* **Review a run like a pull request.** The run page has a **Files changed** tab laid out as GitHub and GitLab show a pull request: files with additions and deletions, hunks with old and new line numbers, **Viewed** to fold a file. For a delivered task the diff is what the workspace daemon observed on disk (the bytes before the write against the bytes it read back, `vscode-daemon/file_diff.py`); for an ingested pull request, GitHub's diff. Files only declared by the producer are listed apart. `GET /v1/agent_runs/{id}/changes` serves it.
* **You decide when the agents work.** The New company wizard can leave Sprint 0 planned (always at autonomy level 1) and the Sprint page starts it. Pause now stops dispatch, QA reviews and retries, not only new tasks, and Stop cancels a sprint for good with no follow-up. When a provider refuses a call for lack of credit, the sprint pauses itself with the reason and the task waits to run again, instead of blocking every task and looping into follow-up sprints. The autonomy level can be changed after creation (`PUT /v1/companies/{id}/autonomy`), and level 1 now does what it promises: every approved task waits for a person to accept it.
* **MCP tools for the agents.** A Manager gives a company MCP servers with the standard `mcpServers` map (`POST /v1/mcp/servers`: stdio by `command`, streamable HTTP or SSE by `url`, secrets in `env`/`headers`, optional `roles`); secrets are stored Fernet-encrypted and the API lists only their names. The task worker offers the servers' tools to the model (`<server>__<tool>`, through the proxy to every provider, Gemini included) and runs a bounded loop (`MCP_MAX_TOOL_ROUNDS`, then one request without tools). Every call is recorded as an observation the backend made — server, tool, arguments, error, duration, sha256 of the result — on the Verifier's evidence (`tools_used`), apart from the model's claims; results are masked for the server's secrets and cut at `MCP_RESULT_MAX_CHARS`; a tool without a read-only annotation raises the delivery's risk tier. `GET /v1/mcp/servers/{id}/tools` connects and lists what a server advertises. Design taken from OpenHands' `software-agent-sdk` (`openhands/sdk/mcp`), on the official `mcp` package.
* **Nebius Token Factory as a first-class model provider.** The LLM proxy routes `nvidia/`, `meta-llama/`, `mistralai/`, `deepseek-ai/`, `qwen/` and `google/` model ids to Token Factory's OpenAI-compatible API, fetches the catalogue at startup and hourly, and lists what it found on `GET /v1/models`. `NEBIUS_API_KEY` enables it; `NEBIUS_PROXY_URL` retargets it at your own Serverless Endpoint. This is what serves the NVIDIA open models (Nemotron).
* **Per-role Nemotron opt-in.** `ModelFactory.model_for_role()` honours `NEMOTRON_ROLES` with `NEMOTRON_MODEL` / `_STRATEGIC` / `_FAST`, so agent roles can run on Nemotron. Unset, the Qwen/DeepSeek defaults are untouched.
* **Documentation overhaul.** README.md, README.es.md, CONTRIBUTING.md, and CLAUDE.md restructured following industry best practices. Added SECURITY.md, CODE_OF_CONDUCT.md, and GitHub issue/PR templates.
* **Architect consultation step.** Before a Developer starts a high-priority, design-sensitive, or QA-reworked task, the worker asks the company's Architect agent for a short technical brief, appends it to the card as an `ARCHITECT_CONSULTED:` comment (feeding the *Architect Consult Frequency* KPI), streams it to the Glassroom, and injects it into the Developer prompt. At most one consultation per implementation attempt. Disable with `ARCHITECT_CONSULT_ENABLED=false`.
* Backend tests for the KPI emitters and their contract with the analytics queries (`backend/tests/test_orchestration_metrics.py`).
* **Competition-ready documentation.** Repo description and topics, evidence-page screenshots, a `docs/README.md` index and a `docs/HACKATHON.md` entry page for the Nebius × NVIDIA Global AI Hackathon, plus a Roadmap and Responsible-use section in the README.

### Changed

* **QA reviews every file, and the prompt is cache-friendly.** The deliverable QA reviews is a digest (`services/review_digest.py`): every file the delivery wrote with its lines and bytes, and an excerpt of each sharing a fixed size, each cut saying how many lines it left out. The board kept 4000 characters and QA read the first 3000, so a delivery of three files reached QA as one, and QA's request for the "missing" files regenerated all of them. The Developer prompt now runs from what is the same for every task of a sprint (output format, procedures, lessons) to what changes between attempts (Architect brief, review feedback, last), so the providers' prefix cache bills the shared start at the cached rate.
* **Fewer tokens per task, with the evidence design unchanged.** A send-back by the Quality gate or the Verifier no longer earns a second Architect brief (it asked for the same deliverable); a rework quotes the console assistants' first advice instead of running the CLIs again; a review answer without `APPROVED:`/`NEEDS WORK:` is asked again with the format named; a Developer answer the model cut at its length limit is sent back as such (`finish_reason: length`, which the proxy now reports for Gemini too) rather than as "deliver the complete result again". The proxy client retries only a request that never reached the proxy (an error the proxy answered already cost its upstream call and fallbacks), waits as long as the proxy's own budget (`LLM_UPSTREAM_TIMEOUT_SECONDS` + 10 s; the planner's 12 s and the triage's 45 s discarded answers already billed), and caps the fixed-form answers (`max_tokens`: QA review, Architect brief, ScrumMaster, planner, Support and Reviewer agents). The Developer's deliverable keeps no cap, since every file goes in full.

### Fixed

* **The test engine's one SQLite connection is used by one checkout's transaction at a time (PR #658's CI).** `test_the_loop_closing_a_sprint_emits_sprint_closed_and_release_integrates_it[reclosed_after_reopen]` failed on a loaded runner with `Integration of sprint 1 failed: cannot rollback - no transaction is active`. The close runs `_observe_effort` with `asyncio.to_thread` while the event loop runs the sprint's integration job, and the test engine (`conftest._engine`, in-memory behind a `StaticPool`) hands every session of every thread the same `sqlite3` connection: one thread's commit or rollback ended the other's transaction, and a commit landing inside `rollback()`'s check-then-`ROLLBACK` raised the error. On Postgres each session has a connection of its own, so the application was right and the harness wrong. `backend/tests/shared_sqlite.py` makes the connection's open transaction belong to the checkout that opened it (the pool's connection proxy the dialect is handed), as separate connections would: every call is made under one lock, a write through another checkout on another thread waits for that transaction to end, and that checkout's `commit()` or `rollback()` ends nothing. A checkout that moves between threads (`TestClient`'s pool threads) still ends its own transaction, and checkouts on one thread share the connection as before. With the effort thread kept busy during the integration and a 1 µs GIL switch interval, 4 × 80 runs failed 46 times before (5 with the CI assertion, 20 `cannot rollback` lines) and none after. `backend/tests/test_shared_sqlite.py` forces both interleavings with events and fails on the old engine.

* **Every workflow that calls `changes.yml` failed at startup.** Since 2026-11-16 05:43 UTC the backend tests, the frontend build, the Docker builds, e2e and the file sizes all reported `startup_failure` with no job and no check run: the reusable workflow used `dorny/paths-filter`, whose owner is not Marketplace-verified, and this repository's Actions policy allows only GitHub-owned and verified-creator actions, so the called workflow was refused before it ran. The filter job now uses no third-party action: it checks out with `fetch-depth: 0` and runs `git diff --name-only <base>...<head>` through `scripts/changed_paths.py`, which reads the same `FILTERS` block scalar the workflow already held and prints one `<filter>=true|false` line per filter; a filter that cannot run still fails the job, so every caller runs. `backend/tests/test_changed_paths.py` covers the glob, the filter text, renames and a failed diff, and `test_ci_paths.py` holds the job's new shape; the `changes` job and its six callers need only `contents: read`. Allowlisting `dorny/paths-filter` in Settings → Actions → General would also have worked; removing the dependency keeps the default policy.
* **`Workflows` failed at startup for the same reason, one step further on.** `workflows.yml` ran actionlint from its published container image (`docker://rhysd/actionlint@sha256:…`), and the same policy counts a `docker://` step as a third-party action: the run reported `startup_failure` with no `lint` job, no log and no check run, so no pull request could lint its workflows at all (the `changes / filter` job of that run passed, which is what made the cause visible). The job now downloads the pinned `actionlint_1.7.7_linux_amd64.tar.gz` release, verifies its sha256 and runs the binary — the pattern `security-scan.yml` already uses for uv, gitleaks and semgrep — and `test_workflow_pinning.py` fails on any `docker://` step, because a digest would not get one past the policy either.
* **Each Docker build in CI tags its image per run.** `docker-build.yml` tagged every image `fabrique-<name>:ci`, and the self-hosted runners share one Docker daemon: a job's cleanup (`docker rmi -f`) could delete the image another job had just built, so its smoke test failed with "pull access denied" (PR #588). The tag now carries the run id and attempt.
* **A test's sprint is never blocked by a lock an earlier test left (#600's CI).** Since the database is emptied after every test, ids repeat; a background integration that an earlier test's event loop dropped mid-attempt kept sprint 1's key in the process's local lock set, so a later test's sprint 1 was never integrated (`running` instead of `tests_passed`, seen once in `test_the_loop_closing_a_sprint_emits_sprint_closed_and_release_integrates_it`). `sqlite_session` now also clears `locks._local_held`, `integration._LOCKS` and `integration_jobs._RUNNING` after each test.
* **The task filter's pull-request guard is relative to the machine's load.** The 1 s guard failed when seven runners loaded the shared machine (best of five 1.23 s, against 0.26 s here). A pull request now holds the filter to five times a reference read of the same 5000 task rows, timed in the same moment, so the load weighs on both sides (about 1.5 times on an idle machine); the statement count still catches per-task queries exactly, and the nightly bench keeps the specification's 300 ms with `PERF_STRICT=1`.
* **The task filter's page budget is measured where it can be (#535).** The test held the median of five wall-clock timings to 300 ms on the shared self-hosted runners and failed on every busy run (0.37–0.55 s there, 0.10–0.25 s on a quiet machine). Every pull request now checks the deterministic half, that the filter's SQL statements grow only by its id chunks and never per task, and holds the timing (best of five after a warm-up) to a 1 s guard; the nightly bench job holds it to the specification's 300 ms with `PERF_STRICT=1`.
* **The history check dates a task's close once.** `worked_before_dependency` read a task's *last* approval or person's note as its close, so a person's note on a task already done moved its close later and blamed the tasks that depended on it (e2e run 43752094404). A task now closes at the first approval, person's note or Manager agent acceptance after the last thing that reopened it: a deliverable, a high-risk hold, or an override.
* **Under the Git workflow a task is judged on the acceptance tests its branch holds (#329 retrospective).** A task's branch merges only the done tasks it depends on, so QA's tests for a sibling requirement are on the sibling's branch; the guard compared every acceptance test of the sprint, found the sibling's missing, called it an edit, copied it in and ran it, and a task was refuted (then blocked) on a test it could not hold, which then failed the integration. With a delivery on a task branch, `acceptance.evidence_for` now guards the test files of the task's lineage (itself and its done dependencies, transitively) and excuses criteria by the implementations merged into it; a sibling's test file is guarded only when it is on the branch's disk (its base holds it), and one that is not is listed in `acceptance.not_on_branch`, never restored, never an edit and never run for that task. The sprint's integration still merges every branch and runs the whole suite. Without the Git workflow nothing changes.
* **A `verified` task event names the verification it renders.** None did (0 of 37 in the self-hosting run), so the documentation pack's traceability matrix read "Latest verification: none recorded". The task worker's `verified` events now carry `verification_id` (the run's latest verification) and `payload.verification` (`{id, verdict}`), and the pack also reads an older `verified` event by its run.
* **`SECURITY.md` matches the code.** Reviewed on 2026-11-15 against the code and Microsoft SDL practices with the `sdl-program` skill (#522, part A): §8.3 describes the sandbox modes, `FABRIQUE_SANDBOX_REQUIRED`, the command policy, the image identity per run, the dependency cache with its quarantine (#514), the versioned daemon protocol and heartbeat (#517), and what remains open (no per-company command policy, console-assistant consultations on the host); §3 describes the HS256 JWT in a bearer header, bcrypt, hashed API tokens with roles and Owner > Manager > Viewer, and marks OIDC, PKCE, mTLS and short-lived tokens as planned (#512, phase 3); vulnerabilities are reported through GitHub private vulnerability reporting instead of a placeholder address; a new §15 says which versions get security fixes and how they ship; the frontend's token in `localStorage`, the images running as root and the CI scans that do not gate are written down as gaps.
* **The quality gate matched documentation keywords inside words.** It now matches them as whole words, trusts the files a delivery wrote, and "api" is no documentation keyword; a task that asks for a document stays one (#508; #509).
* **Orchestration health KPIs were structurally zero.** `GET /v1/analytics/orchestration_health` filtered `audit_log` on `details.role` / `details.company_id` and counted `ARCHITECT_CONSULTED:` comments, but the task pipeline never wrote either. The worker now records every Developer execution and QA review to `audit_log` (canonical role, company scope, `result_type`, proxy-reported token cost) via the new `services/orchestration_metrics.py` module, so *Avg Developer Tokens* and the QA *NEEDS WORK* rate read real data.
