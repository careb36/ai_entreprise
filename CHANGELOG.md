## [Unreleased]

### Security

* **The audit chain anchored outside the factory (#542).** The chain is keyed by `AUDIT_SIGNING_KEY`, which the factory holds, so a row rewritten and re-signed with it still verified. Its head is now recorded where the factory cannot rewrite it: an RFC 3161 token from the timestamping authority the Owner chose, checked against the certificate the Owner pinned (read with a small DER reader and `cryptography`; no new dependency; checked against `openssl ts` both ways); a signature by an Ed25519 key the customer holds (the factory stores the public half: `GET /v1/audit/anchors/statement`, `POST /v1/audit/anchors/signature`); and a post to the company's webhook, whose answer is kept as a claim unless a customer key signed it. Anchors are taken on the Owner's cadence (default hourly), when a sprint closes, when a run or a sprint's integration is published and on demand (`POST /v1/audit/anchors`), through the outbox with its retries. `GET /v1/audit/anchors` and the new `anchors` field of `GET /v1/audit/chain` report which range each anchor covers, the tail none covers, and every anchor that no longer matches the chain (`hash_mismatch`, `row_missing`) or its own proof; `GET /v1/audit/anchors/{id}/export` gives the statement and proof to verify with `openssl`. Settings (`GET`/`PUT /v1/audit/anchors/settings`) are changed only by an Owner in person and audited; the page is `/company/audit-anchors`. Tables `audit_anchors` and `audit_anchor_settings` (migration `0032`); the chain's rows are unchanged. New HTTP adapter `integrations.tsa_client`. Design and threat model: `docs/design/AUDIT_ANCHORS.md`; a signed git tag and KMS keys are designed, not built.
* **A security probe in the application check, as WSTG observations (#540).** With the application check on, the daemon now sends the running application a fixed set of requests inside the same run and sandbox (`vscode-daemon/security_probe.py`; `security_probe: true` on `workspace.app.check`, additive in protocol v1): the probe path's headers and parsed `Set-Cookie` attributes (a cookie's value only as its length), the answers to `Origin: https://evil.example` with and without a cookie and to a CORS preflight, OPTIONS and TRACE, a missing path and a malformed JSON body (the head of each body), and whether `/.git/HEAD` and `/.env` are served (`.env` only as the names it assigns). In container mode the module runs with `python3 -c` inside the application's container; an image without `python3` is reported not observed. The Verifier's new `security_probe` check (`services/evidence/security_probe.py`) maps each answer to a versioned OWASP WSTG item (`WSTG-v42-CLNT-07`, `CONF-04`, `CONF-06`, `CONF-07`, `SESS-02`, `CLNT-09`, `ERRH-01`, `ERRH-02`; Content Security Policy and Other HTTP Security Header Misconfigurations, not in release 4.2, as `WSTG-87cf4a4-CONF-12` and `-CONF-14` from the guide's commit): a credentialed CORS answer to any origin, a stack trace in an error body or a served `.git` / `.env` refutes the delivery and the gate sends it back (`security probe refuted`, a code problem); missing headers and cookie attributes, TRACE enabled and a server error on a bad request are findings; over plain http HSTS and a cookie without `Secure` are unverifiable with the reason, never a pass; a probe asked for and not answered (an older daemon) is unverifiable. Every value is the daemon's observation; the producer's report is never read. The Verifier bench gains a seeded insecure CORS that is refuted and a clean control. Taken from: OWASP WSTG (IDs and names only, commit 87cf4a4), Codex cloud (the requests sent cited in each observation), Copilot coding agent (CI as the evidence of a run). Next: an optional ZAP baseline scan image pinned by digest, its JSON parsed into the same WSTG items.

* **OWASP WSTG gaps in La Fabrique itself (#541).** An unhandled error answers `{"detail": "Internal server error", "error_id": ...}` with the traceback only in the backend's log; the traceback export to `FABRIQUE_VENDOR_SUPPORT_URL` (with a hard-coded vendor id, and a missing `json` import that made it fail) is removed, and an opt-in `ERROR_REPORT_URL` (https) receives only the error id, the exception's class, the method and the route template. Password login is limited per address (`LOGIN_RATE_LIMIT`) and per account with a doubling backoff (429 with `Retry-After`), registration per address (`REGISTER_RATE_LIMIT`); **registration now answers `{"status": "accepted", "detail", "email"}` whether or not the email had an account (no `user_id`)**, and login spends the same bcrypt work on an unknown email. Access tokens and Glassroom tickets carry and require `iss` and `aud` (`JWT_ISSUER`, `JWT_AUDIENCE`), and `JWT_ALGORITHM` must be HMAC: **a Bearer token issued before the upgrade is refused** (log in again; browser sessions renew from the refresh cookie). Headers: `X-XSS-Protection: 0`, `Cross-Origin-Opener-Policy: same-origin`, a CSP of `default-src 'none'; frame-ancestors 'none'` on the API, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` on every answer but the documentation, also on the unhandled-error 500; `API_DOCS_ENABLED=false` turns off `/docs`, `/redoc` and `/openapi.json`. Every route declares who may call it in `docs/architecture/authorization.json`, and a test calls each as five callers (an undeclared route fails); it found `POST /v1/agents/generate_prompt` public by omission, now signed-in only. Request bodies refuse an undeclared privileged field (`company_id`, `role`, `human_role`...) with 422, and the sign-in and membership bodies any unknown field. The notification webhook, the OIDC client and the research fetches go through `services/platform/egress.py`: public addresses only (NAT64 and multicast now refused too), resolved once and connected to by that address, so DNS rebinding cannot steer them; a research host on a company's list may no longer be private (only `RESEARCH_ALLOWED_HOSTS`). `SECURITY.md` gains the yearly penetration-test scope (§16) and the DAST plan (§5.2); the SDL skills cite WSTG ids.

* **The browser's session moves to HttpOnly cookies (#524).** Password login and the SSO handoff exchange set `fabrique_session` (the access token, `HttpOnly; Secure; SameSite=Strict; Path=/`), `fabrique_refresh` (`HttpOnly`, `Path=/v1/auth`) and `fabrique_csrf` (readable by the page) instead of returning a token: the frontend persists no credential (only the profile and when the session ends; a test checks `localStorage` and `sessionStorage`), sends `credentials: 'include'` and `X-Fabrique-CSRF` on unsafe methods, and on a 401 refreshes once, then signs out. Access tokens now live 15 minutes (`ACCESS_TOKEN_EXPIRE_MINUTES`); refresh tokens are stored hashed in families (`session_families`, `refresh_tokens`, migration `0023`), rotated on every use, a reused one revokes its family, and a family ends after `REFRESH_TOKEN_ABSOLUTE_DAYS` (7); `POST /v1/auth/refresh` is rate-limited (`REFRESH_RATE_LIMIT`) and `POST /v1/auth/logout` revokes the family. An unsafe request authenticated by the cookie needs the CSRF header matching the cookie and the digest signed into the token; Bearer callers (API tokens, scripts) are unchanged, a request with both is treated as Bearer, and a script gets a Bearer access token from login only by asking (`"token_delivery": "bearer"`): **a script that read `access_token` from `POST /v1/auth/login` must add that field** (or use an API token). Turning on "require SSO" ends the password-started sessions it would refuse, and removing a member (`DELETE /v1/company/{id}/members/{user_id}`, new, Owner) ends that person's sessions; access tokens of a revoked family are refused at once. CORS allows credentials only with explicit `CORS_ORIGINS`, never `*`. `SESSION_COOKIE_SECURE=false` relaxes `Secure` for plain-http development. Threat model and design: `docs/design/SESSIONS.md`.
* **The packaged desktop app keeps its session (#524).** It loaded the frontend from `file://`, which is not the API's site, so the `SameSite=Strict` cookies were never sent. Its main process now serves `dist/` from `http://127.0.0.1:<port>` (a port the system picks at each launch; Node's `http`, no new dependency) and forwards `/v1/*`, Server-Sent Events included, to `BACKEND_URL` (https, or plain http only on localhost; anything else stops the app at launch), with `Set-Cookie`'s `Domain` dropped and every other attribute kept (`Secure` included: Electron accepts it on 127.0.0.1), and the desktop build calls the API on its own origin. The server refuses a foreign `Host` (DNS rebinding), another `Origin`, a request `Sec-Fetch-Site` marks as from another site and an unsafe method without its own `Origin`; forwards only `/v1/*`, only to that backend; never passes `Origin` on or `Access-Control-*` back; refuses paths outside `dist/`; and sends the page with a CSP without `unsafe-inline` scripts, `nosniff`, `X-Frame-Options`, `no-referrer` and `Cross-Origin-Opener-Policy`. The main window stays on the local origin (other links open in the system browser), single sign-on runs in a window without the preload, with the provider's callback and the backend's `/login/sso` redirect taken through the local origin, and IPC answers only the local page. The desktop build's asset base is now `/` like the web build's. Design, threat model (new boundary B10) and smoke run: `docs/design/SESSIONS.md`, Desktop app.
* **The daemon's sandbox floor reaches every command.** A `workspace.execute` without a `sandbox` is now read as a `host` request, so `FABRIQUE_SANDBOX_REQUIRED=container` (or `bwrap`) on the daemon's machine runs it in that mode (`forced_by_daemon`) or, when that mode cannot run, refuses it; never the host. Without the floor nothing changes, and the reply of a request that did not ask carries no `sandbox`. The console assistants send the company's sandbox with the new purpose `assistant` (the network as `DELIVERY_SANDBOX_NETWORK` sets it, the provider's key by name from `console_env`); one that cannot run there is skipped with the reason in the Glassroom (`skipped_sandbox`) and the task goes on. Protocol version 1, additive (#525).

* **CI supply chain and scans that can fail.** Every third-party action in every workflow is pinned by commit sha with its version in a comment, and `backend/tests/test_workflow_pinning.py` fails on a tag (the SLSA generator, which only runs from a `vX.Y.Z` tag, is the one exception); `security-scan.yml` replaces `safety check || true` with `pip-audit` over the backend's and the llm-proxy's lockfiles and `npm audit --omit=dev --audit-level=high` over the frontend's, failing on a known vulnerability unless `.github/pip-audit-ignore.txt` lists it with a reason and a review date that has not passed; gitleaks over a pull request's commits and Semgrep on the findings it adds now run on every pull request, beside the weekly full scans. The OpenTelemetry packages move from 1.45.1 to 1.45.2 (0.66b1 to 0.66b2) in both lockfiles for CVE-2026-126360 in `opentelemetry-api` (#522).
* **Release supply chain: SBOMs, signed images, a licence scan, the daemon locked (#522, part C).** A release attaches a CycloneDX SBOM of the backend's, the llm-proxy's, the daemon's and the frontend's locks with a `SHA256SUMS` (syft, pinned and checksummed), and `images.yml` signs each published image by digest with keyless cosign (GitHub OIDC, Fulcio, Rekor; `id-token: write` on the publish job only) and attaches its SBOM as a signed attestation; how to verify both is in `docs/OPERATIONS.md`, Releasing. The workspace daemon's `requirements.txt` becomes a lock compiled with hashes from `requirements.in` (nats-py 2.16.0, nkeys 0.2.1 now always installed), installed with `--require-hashes` by its Dockerfile (which pinned an older nats-py of its own) and both start scripts, and audited by `pip-audit`. A new `licences` job (`scripts/licence_scan.py`) fails on a runtime dependency whose licence is off the allowlist or unknown, with exceptions in `.github/licence-exceptions.txt`; the first run's five findings are listed there pending the owner's decision. `.github/CODEOWNERS` covers authentication, the bus, migrations and the architecture rules too; pre-commit runs gitleaks; actionlint runs by digest and `test_workflow_pinning.py` requires digests on `docker://` images; the bench reads pytest's JUnit report with `expat`, refusing a DTD or entity (Semgrep `use-defused-xml`). the self-hosted runner proposal records the self-hosted runner's risks and a recommendation.

### Changed

* **A pull request runs only the CI jobs its files can affect, and e2e jobs can be limited to two at once.** The seven self-hosted runners share one machine of about 4 cores and 16 GB, and every pull request ran its jobs against each other (wall-clock test failures, runs killed for lack of memory). A new reusable workflow, `changes.yml` (`dorny/paths-filter` v4.0.3 by sha), lists a pull request's files once, and the backend tests, frontend build, the five Docker builds, the two e2e runs, the file sizes and actionlint each run only for the paths that feed them (`docs/TESTING.md`, CI); the security scans always run, a workflow change or a push to `main` runs everything, and a docs-only change runs only the scans. No workflow filters `on.pull_request.paths` any more, so a skipped job reports as skipped and a required check never waits; the matrix jobs start and skip their steps to keep their check names, and a failed filter runs every job. With the repository variable `E2E_RUNS_ON` set to include the label `e2e` (off by default; label two runners first, `docs/OPERATIONS.md`, Runner capacity), an e2e job that runs the loop needs a runner with that label, so further e2e jobs queue instead of starting; the repository variables `E2E_RUNS_ON`, `BACKEND_TEST_WORKERS`, `E2E_POSTGRES_MEMORY` and `E2E_NATS_MEMORY` are the capacity knobs. `backend/tests/test_ci_paths.py` holds the filters, the gating and the concurrency rules, and fails when a backend test reads a path the backend filter leaves out.
* **The backend suite runs in parallel.** pytest-xdist joins the dev group and `tests/conftest.py` makes `-n auto --dist loadgroup` the default (`-n 0` for one process; CI uses `-n 4` on the shared runners); `sqlite_session` empties the shared in-memory database after each test, so a worker cycle no longer reads every earlier test's tasks, and the wall-clock tests share one worker and keep their best timing after a warm-up. On 4 cores: 557 s serial before, about 370 s serial and 105 s parallel now.
* **The browser sandbox image is published for linux/amd64 only (#529).** Its arm64 variant builds under QEMU on the runner, but its browser aborts under emulation (the first `browser-image-probe.yml` run), so nobody has seen it work; `images.yml` no longer sets up QEMU or publishes arm64 until it has been run with its probe on arm64 hardware.

* **The e2e web project's port is picked at run time.** `E2E_WEB_PORT` was fixed at 18765, and the self-hosted runners share one machine: when two runs reached step 9c together, the daemon refused the second greeting's busy port, no browser check ran, no hold was placed and step 10 reported a misleading `worked_before_dependency`. `e2e.yml` now picks it like the backend's and the fake model's ports, `run.sh` defaults to a free port, and step 9c checks the port is free first.

* **The e2e self-hosting step fails loudly and keeps its logs.** Every local git call of `scripts/self_host/self_host.py` now times out after `GIT_TIMEOUT_SECONDS` (120 s) and raises `GitTimeoutError` naming the command, and the `e2e-logs` artifact also keeps the harness's `self-host/*.log` and `*.json`, so a step that hangs (as on #575, 18 minutes with nothing to diagnose) leaves its output.

* **The runners' docker state is swept weekly.** `e2e.yml` started a pgvector
container per job, that image declares a `VOLUME`, and both cleanup sites used
`docker rm -f`: every run on this machine left an anonymous volume behind, and
273 of them had reached 22 GB. They now use `docker rm -fv`; a new
`runner-hygiene.yml` sweeps daily — this repository's stopped e2e and smoke
containers with their volumes, dangling images older than a week, an anonymous
dangling volume older than a week, and the buildkit cache kept under 2 GB. It
never prunes by name: the named volumes here (`la-fabrique_*`) are a person's
development data and read as `dangling` while their stack is down, and the named
images belong to the other repositories sharing this host (#566).

* **A new push to `main` cancels the run it replaces.** The checks on the self-hosted runners (backend tests, e2e, frontend build, Docker build, file sizes, workflows, security scan, security baseline) already cancelled a pull request's superseded run; on `main` every merge ran in full and queued ahead of the pull requests, so a burst of merges kept the runners busy validating commits a newer run already covered. Release tags and the image publish (`images.yml`) still never cancel.

* **No source file over 600 lines.** `llm-proxy/app.py` is split into modules with one job each (`routing.py`, `providers.py`, `quota.py`, `embedding.py`, with the listing in `catalogue.py` and tracing in `telemetry.py`), keeping `app.py` as the entry point, and `scripts/verify_infra.py` keeps its command line while its checks move to `scripts/infra_checks/`; the file-size baseline is empty (#519).
* **The backend in fourteen contexts with a checked dependency rule.** `backend/app/services` is divided into contexts, each a folder with one responsibility and a document; `scripts/check_architecture.py` holds the imports to `docs/architecture/contexts.json` in CI, the task worker is split into stages and the flat shims are retired (#469; #470 to #500, #502).
* **Versioned schema migrations.** Alembic owns the schema (`backend/alembic/`): the baseline migration creates what the models define and converges a database an older backend or `db/init-db/init.sql` created (the `ALTER TABLE` statements the startup used to apply by hand live there now, readable and reversible). The backend refuses to start on a database behind head, naming both versions; the container's entrypoint runs `alembic upgrade head` before the app, the e2e does too and then `alembic check` on Postgres, and CI checks on a SQLite file that the models and the migrations agree. `DB_AUTO_UPGRADE=true` runs the migrations at startup for a local database. How to write one: `CONTRIBUTING.md` §5.

### Added

* **The architecture is the company's, versioned (#329, finding F3 of the self-hosting retrospective).** A company has one architecture: each approved revision is a new version numbered per company, approving it supersedes the company's other approved version, and the earlier versions stay readable (`GET /v1/companies/{id}/architecture`, `…/architecture/versions`, `…/architecture/versions/{version}`). The revision for a new specification is the next version of the same architecture (`POST /v1/companies/{id}/architecture/revisions`, `POST /v1/architectures/{id}/revise` with a `specification_id`, or a draft for a specification the current version does not cover): each module's covers of the earlier specifications are kept under `earlier_covers`, by specification id, so `REQ-1` of one specification is never mistaken for `REQ-1` of another. A specification names the version it was planned against (`architecture_id`, set on approval and when a sprint starts from it). `arch_check` and the coverage read every specification a version covers, task prompts read the covers of their own specification, and the documentation pack has a section per approved specification (scope statement, WBS, traceability matrix, schedule, index). Migration `0038` turns the existing architectures into versions of their company's architecture, ordered by approval, keeping their specification links. The architecture page shows the version and the company's history. The self-hosting harness posts #535's revision as version 2 of La Fabrique's one architecture, without rewriting #469's covers. Taken from Kiro (one design per project revised for each new spec, design only).

* **A person's review of a sprint's integration (F7 of the self-hosting retrospective).** The integration (`fabrique/sprint-<id>`) is reviewed as a run is, whether or not it is published: line comments and a review (comment, approve, request changes) on the sprint's latest integration, recorded and audited with the account (`GET`/`POST /v1/sprints/{id}/integration/reviews`, `POST …/integration/comments`, `…/comments/{id}/resolve`; a Viewer reads, a Manager reviews). The diff comes from the workspace daemon (`workspace.git.diff`, new and read-only, additive in protocol v1: files, hunks and each side's sha256 from git's objects), never from the browser: a comment is accepted only on a line of that diff and keeps the file's hash; a review keeps the commit, the merge base and a `diff_sha256` the backend computes. `GET /v1/sprints/{id}/integration` shows the latest review. A company setting, off by default (`GET`/`PUT /v1/companies/{id}/integration_review`, Owner, audited), makes the local merge of an integration wait for an approving review of its commit, from the web, the Manager agent and the self-hosting harness alike; the merge records the review it stood on. An approval follows segregation of duties (#582): whoever started the sprint does not approve its integration. A published integration's forge review stays the forge's; this one gates the local merge. The sprint's Overview shows the reviews, the diff with line comments and the form; `self_host.py --merge` records an approving review before merging. Tables `integration_reviews`, `integration_review_comments` and `companies.integration_review_required` (migration `0037`). Taken from (design only): Devin's session review, GitHub Copilot's pull request review, Factory's review flow.
* **A stack profile per folder, and commands every delivery runs (self-hosting retrospective F5, follow-up 5).** A repository whose root has no manifest (La Fabrique: `backend/` Poetry, `frontend/` npm, `llm-proxy/` Poetry) is searched for folders with their own manifest, two deep, each with its own install and test commands; a company names or overrides folders and adds every-delivery commands in its stack profile (`folders`, `every_delivery` on `PUT /v1/companies/{id}/stack_profile`; a profile in the old shape is the root's alone, no migration). A delivery runs the suites of the folders the daemon saw it write in, every folder's for a file outside them when the root has no suite, then the every-delivery commands, in the company's sandbox; a manifest in a folder is installed by that folder's install; a sprint's integration runs every folder's suite. The Verifier's new `required_commands` check records each run (kind, folder, command, exit status, the sha256 of the output the backend computed): a failure refutes and sends the task back (`required command failed`), a runtime that is not installed leaves the delivery unverifiable. A single-root project runs and records exactly as before. The self-hosting harness's `company` step sets La Fabrique's suites per folder and its architecture and file-size checks (`--profile sprint-tests` keeps one root command, for the e2e). Taken from: GitHub Copilot coding agent and OpenHands (each workspace's own CI and checks), Factory and OpenAI Codex cloud (every command run cited with its result); design only.

* **The weight of each prompt section is shown (#443).** `GET /v1/agent_runs/{id}/cost`, `/v1/tasks/{id}/cost` and `/v1/sprints/{id}/cost` now carry `prompt_weight`: each prompt section's estimated tokens, share, and how often the budget left it out, added up from the measure the task worker keeps on each run's evidence (`services/models/prompt_weight.py`). The run and task cost cards fold it under the cost, and each sprint on the Sprints page shows it on demand.
* **An intake queue for incoming requests (#532).** Support tickets sent with a `company_id`, the client's brief, calls with an API token (`POST /v1/companies/{id}/intake`) and `request <text>` in Slack or Teams enter one company-scoped queue (`IntakeItem`, migration `0035`) with the source the backend observed. A Manager accepts a request as a task in an open sprint or into a specification revision (as an open question), declines it with a reason, marks it a duplicate of another request or a task, or snoozes it until a date, when it comes back by itself; a Viewer reads and sends. The request keeps the link to what it became, and the task's thread names the request. The Support agent suggests a decision, a category and a duplicate (a claim, in `suggested_*`), stored apart from the person's decision; every status change is an audit row with its actor. The Review page lists the requests by status (`components/IntakeQueue.tsx`), the inbox counts the pending ones, and `GET /v1/companies/{id}/intake-record` gives the share closed with a recorded outcome, the median time to a decision and the agent's agreement with people per category. Every intake route is declared in `docs/architecture/authorization.json` (Viewer reads and sends, Manager decides), the bodies are `schemas.RequestModel`s, and an item's path parameter is `intake_id` (the URLs are unchanged). Design after Plane's intake (AGPL-3.0, design only).

* **A security test plan and checklist per project, from OWASP WSTG (#539).** The OWASP Web Security Testing Guide's checklist is kept as a versioned catalogue (`backend/app/data/wstg/catalogue.json`, CC BY-SA 4.0 with its attribution, built by `scripts/wstg_catalogue.py` from commit 87cf4a4; ids `WSTG-v42-…`, or `WSTG-87cf4a4-…` where release 4.2 lacks the test, the security probe's scheme). A fixed rule table (`services/planning/wstg_plan.py`) selects the tests that apply from the specification, the architecture and the detected stack (an HTTP surface, a browser client, sign-in, roles, an API, uploads, a database, outbound fetches, payments, OAuth, SAML, GraphQL, WebSockets, JWT), each `auto` (the daemon's security probe, or a QA test named `test_wstg_<cat>_<nn>_…`, read back by the Verifier's new `wstg_tests` check) or `manual`, with its reason; a model may only propose additions, as claims. The documentation pack gains a WSTG checklist (observed-pass / observed-fail / not-run / needs-manual / not-applicable, each observed row citing its verification, run, evidence sha256 and tool, or a person's recorded review) and a security test report after the guide's chapter 5, in English or Spanish, both with the CC BY-SA 4.0 footer; the check results measure the applicable tests observed passing against the specification's security target (STD-PO-1). A Manager records a person's review of a manual test (`POST /v1/companies/{id}/security/wstg/reviews`: who, when, the artifact, the result; audited; table `wstg_reviews`, migration `0034`); `GET /v1/companies/{id}/security/wstg` serves the plan and its statuses. The three routes are declared in `docs/architecture/authorization.json` (Viewer reads, Manager records) and the review body is a `schemas.RequestModel`.

* **A manual multi-arch probe of the browser sandbox image (#529).** `browser-image-probe.yml` (`workflow_dispatch` only — nothing a pull request controls reaches it, and it pushes nowhere) builds `vscode-daemon/images/browser` for `linux/amd64,linux/arm64` with buildx under QEMU on the self-hosted runner, then runs the arm64 image once with its probe under emulation the way the daemon runs it in production (network off, capabilities dropped, `no-new-privileges`, an unprivileged uid). It answers whether the runner can do the multi-arch publish `images.yml` lacks before a release tag discovers it, and whether the headless browser launches under QEMU (the Dockerfile skips its build-time probe on arm64, as Flow found the browser aborting there); a green run is the gate for the `browser-sandbox` publish job. The image's two per-architecture sha256 pins were re-verified on a clean network against the Playwright CDN and are unchanged (#528 computed them through an intercepting proxy).
* **Sprint progress from the task-event chain: claimed done versus verified, sealed at close (#531).** `services/tasks/progress.build` replays a sprint's task events into a time series (per day or per event) of its tasks by status and, apart, by the Verifier's latest verdict, with two lines that are never merged: delivered (the producers' claim, from `delivered` events) and verified (from `verified` events with the verdict `verified`); the same events give the same bytes. The `verified` event now carries the verdict in its payload. At a sprint's close the series and the retrospective's counts are stored as a snapshot (`sprint_progress_snapshots`, migration `0031`) whose sha256 the backend computes and seals into the company's audit chain (`sprint_progress_sealed`); a reopened sprint keeps its first snapshot and adds one. `GET /v1/sprints/{id}/progress` (Viewer) answers the live series of an open sprint and the snapshot of a closed one with its check; `GET /v1/specifications/{id}/progress` (Viewer) the coverage per requirement across the specification's sprints; the Sprint page's Overview draws the two lines. The claimed-but-not-verified share (`claim_gap_rate`) joins the numbers a procedure is kept or reverted by. Design studied from Plane's burndown and cycle progress snapshot (AGPL-3.0, design only), without its rebuilding of history from a mutable `completed_at`.

* **Typed relations between tasks across sprints (#533).** A task can be related to another task of the company, in any sprint, as `blocked_by` (read `blocking` from the other side), `duplicate` or `relates_to` (`task_relations`, migration `0030`; one row per pair under a unique constraint, the reverse name read from one fixed table, after Plane's issue relations, design only). A relation is `proposed` (a claim) until a person or a deterministic rule confirms it: carry-over writes a confirmed `relates_to` between the two attempts (`rule:carry_over`). * **Tasks in the order they depend on.** The PO's plan says which tasks must be done before another starts; `POST /v1/start_sprint` keeps it (`depends_on`, checked: an unknown task, a task depending on itself or a cycle is refused). The worker follows that order instead of the queue's: a task waits in *todo*, with a note saying for what, until every task it depends on is done, and is queued the moment the last one closes; tasks with nothing between them run in parallel as before. A task waiting on one a person must act on is blocked with the reason, so the sprint closes around it and the inbox shows what the person's decision unblocks; when that dependency gets done after all, the task is released. The board shows `depends_on` and `waiting_for` per task, a carried task keeps a dependency carried with it, and the independent history check refuses a task that delivered before every task it depends on had closed. A hold is the System's last word on the task (a comment anyone appends does not hide it), a chain of holds follows its root (a task behind one is released when the root is back in work, and held again when it is not), a sprint reconciles its holds before it counts as settled, and with the Git workflow the daemon merges the branches of the done tasks a task depends on into its worktree before writing (`merge` in the delivery, `merged` in its report).
* **The architecture: how the specification is built, as data.** Once a specification is approved, a Manager asks the Architect for a design: modules with their responsibility, their place in the repository, what they depend on and which requirements they cover; interfaces with a contract a test can hold them to; decisions (ADRs) with their consequences; conventions; and the questions the Architect could not decide. The ids (`MOD-1`, `IF-1`, `ADR-1`) are assigned by the backend, which maps the draft's names onto them. A deterministic check blocks approval on an unknown module or requirement, a dependency cycle, a decision without its decision or an unanswered question, and warns on a requirement no module covers. A person answers, asks for a revision, edits in a structured form, approves; **Write to the repository** sends `docs/ARCHITECTURE.md` through the workspace daemon and keeps the sha256 it read back. The PO plans along the modules, and each task's prompt and QA's review carry the modules its requirements map to, with their interfaces, and the decisions and conventions every task follows (`/v1/architectures`).
* **The specification: what the agents build from, as data.** A Manager gives the PO a brief and gets a draft: numbered requirements (`REQ-1`), each with acceptance criteria written as given / when / then (`REQ-1.2`), quality attributes with a number to measure them by (`NFR-1`), constraints, and the questions the PO could not decide. The ids are assigned by the backend, never by the model. A deterministic check says what blocks approval (a requirement without a criterion, a criterion with an empty step, a target without a number, an unanswered question) and what only warns ("fast", "easy", "rápido" without a number). A person answers the questions, asks the PO for a revision (the answers go into its prompt), edits in a structured form, and approves; an approved version is never edited, a revision is a new draft that supersedes it. Planning from an approved specification has the PO split it into tasks that name the criteria they cover, lists the criteria no task covers, and the sprint keeps that: each task's prompt and QA's review carry only the requirements it covers, and the specification shows, per criterion, whether a task got done, is blocked, is planned or does not exist (`/v1/specifications`, `POST /v1/plan_sprint` and `POST /v1/start_sprint` with `specification_id`; the Specifications page and the Plan a sprint form).
* **Comments from the pull or merge request, back in the run.** A Manager presses **Bring comments** on a published run: the workspace daemon reads the request's line comments, reviews and conversation with the person's `gh` or `glab` login (`workspace.git.reviews`), and each one appears on its line in Files changed, marked as written on GitHub or GitLab, with its link and, for a review, its state. Reading again never duplicates; the next review submitted here carries them to the agent like any comment, naming who wrote each and where (`POST /v1/agent_runs/{id}/publications/{pid}/sync`).
* **Publish a task's branch as a pull or merge request.** From a run's Files changed, a Manager publishes `fabrique/task-<id>`: the workspace daemon pushes it to `origin` with the person's own Git credentials and opens a draft pull request (`gh`) or merge request (`glab`), or answers with the page that opens one (`workspace.git.publish`). The description carries the evidence the Verifier observed, the producer's claims apart and a `Fabrique-Run:` trailer; each publication is kept and audited (`POST /v1/agent_runs/{id}/publish`, `GET .../publications`).
* **Git branch per task.** With the company's Git workflow on (`PUT /v1/companies/{id}/git`, the Board's toggle), each task's deliveries are commits on `fabrique/task-<id>`, in a worktree under the repository's git directory, from the base the company names or the checked-out commit; the person's checkout, index and branch are never touched. The daemon reports the branch, commit and parent as git said them (`vscode-daemon/git_workspace.py`), kept on the evidence; delivery tests run in the worktree; Files changed names the commit.
* **Review comments and decisions, as on a pull request.** A Manager comments on a changed line (new or old side), resolves comments, and submits a review: Comment, Approve or Request changes, carrying the open comments. On a task the agents delivered, Request changes sends a task blocked for a person back to work with the comments, file by line, as its `NEEDS WORK:` feedback, and Approve accepts a delivery QA approved that waits for a person; anything else is refused with the reason, since QA and the Verifier decide. On another producer's run the review records the approval or rejection. Audited, never evidence (`/v1/agent_runs/{id}/comments`, `/v1/agent_runs/{id}/reviews`).
* **Review a run like a pull request.** The run page has a **Files changed** tab laid out as GitHub and GitLab show a pull request: files with additions and deletions, hunks with old and new line numbers, **Viewed** to fold a file. For a delivered task the diff is what the workspace daemon observed on disk (the bytes before the write against the bytes it read back, `vscode-daemon/file_diff.py`); for an ingested pull request, GitHub's diff. Files only declared by the producer are listed apart. `GET /v1/agent_runs/{id}/changes` serves it.
* **You decide when the agents work.** The New company wizard can leave Sprint 0 planned (always at autonomy level 1) and the Sprint page starts it. Pause now stops dispatch, QA reviews and retries, not only new tasks, and Stop cancels a sprint for good with no follow-up. When a provider refuses a call for lack of credit, the sprint pauses itself with the reason and the task waits to run again, instead of blocking every task and looping into follow-up sprints. The autonomy level can be changed after creation (`PUT /v1/companies/{id}/autonomy`), and level 1 now does what it promises: every approved task waits for a person to accept it.
* **MCP tools for the agents.** A Manager gives a company MCP servers with the standard `mcpServers` map (`POST /v1/mcp/servers`: stdio by `command`, streamable HTTP or SSE by `url`, secrets in `env`/`headers`, optional `roles`); secrets are stored Fernet-encrypted and the API lists only their names. The task worker offers the servers' tools to the model (`<server>__<tool>`, through the proxy to every provider, Gemini included) and runs a bounded loop (`MCP_MAX_TOOL_ROUNDS`, then one request without tools). Every call is recorded as an observation the backend made — server, tool, arguments, error, duration, sha256 of the result — on the Verifier's evidence (`tools_used`), apart from the model's claims; results are masked for the server's secrets and cut at `MCP_RESULT_MAX_CHARS`; a tool without a read-only annotation raises the delivery's risk tier. `GET /v1/mcp/servers/{id}/tools` connects and lists what a server advertises. Design taken from OpenHands' `software-agent-sdk` (`openhands/sdk/mcp`), on the official `mcp` package.
* **Nebius Token Factory as a first-class model provider.** The LLM proxy routes `nvidia/`, `meta-llama/`, `mistralai/`, `deepseek-ai/`, `qwen/` and `google/` model ids to Token Factory's OpenAI-compatible API, fetches the catalogue at startup and hourly, and lists what it found on `GET /v1/models`. `NEBIUS_API_KEY` enables it; `NEBIUS_PROXY_URL` retargets it at your own Serverless Endpoint. This is what serves the NVIDIA open models (Nemotron).
* **Per-role Nemotron opt-in.** `ModelFactory.model_for_role()` honours `NEMOTRON_ROLES` with `NEMOTRON_MODEL` / `_STRATEGIC` / `_FAST`, so agent roles can run on Nemotron. Unset, the Qwen/DeepSeek defaults are untouched.
* **Documentation overhaul.** README.md, README.es.md, CONTRIBUTING.md, and CLAUDE.md restructured following industry best practices. Added SECURITY.md, CODE_OF_CONDUCT.md, and GitHub issue/PR templates.
* **Architect consultation step.** Before a Developer starts a high-priority, design-sensitive, or QA-reworked task, the worker asks the company's Architect agent for a short technical brief, appends it to the card as an `ARCHITECT_CONSULTED:` comment (feeding the *Architect Consult Frequency* KPI), streams it to the Glassroom, and injects it into the Developer prompt. At most one consultation per implementation attempt. Disable with `ARCHITECT_CONSULT_ENABLED=false`.
* Backend tests for the KPI emitters and their contract with the analytics queries (`backend/tests/test_orchestration_metrics.py`).
* **Competition-ready documentation.** Repo description and topics, evidence-page screenshots, a `docs/README.md` index and a `docs/HACKATHON.md` entry page for the Nebius × NVIDIA Global AI Hackathon, plus a Roadmap and Responsible-use section in the README.

### Changed

* **QA reviews every file, and the prompt is cache-friendly.** The deliverable QA reviews is a digest (`services/review_digest.py`): every file the delivery wrote with its lines and bytes, and an excerpt of each sharing a fixed size, each cut saying how many lines it left out. The board kept 4000 characters and QA read the first 3000, so a delivery of three files reached QA as one, and QA's request for the "missing" files regenerated all of them. The Developer prompt now runs from what is the same for every task of a sprint (output format, procedures, lessons) to what changes between attempts (Architect brief, review feedback, last), so the providers' prefix cache bills the shared start at the cached rate.
* **Fewer tokens per task, with the evidence design unchanged.** A send-back by the Quality gate or the Verifier no longer earns a second Architect brief (it asked for the same deliverable); a rework quotes the console assistants' first advice instead of running the CLIs again; a review answer without `APPROVED:`/`NEEDS WORK:` is asked again with the format named; a Developer answer the model cut at its length limit is sent back as such (`finish_reason: length`, which the proxy now reports for Gemini too) rather than as "deliver the complete result again". The proxy client retries only a request that never reached the proxy (an error the proxy answered already cost its upstream call and fallbacks), waits as long as the proxy's own budget (`LLM_UPSTREAM_TIMEOUT_SECONDS` + 10 s; the planner's 12 s and the triage's 45 s discarded answers already billed), and caps the fixed-form answers (`max_tokens`: QA review, Architect brief, ScrumMaster, planner, Support and Reviewer agents). The Developer's deliverable keeps no cap, since every file goes in full.

### Fixed

* **Each Docker build in CI tags its image per run.** `docker-build.yml` tagged every image `fabrique-<name>:ci`, and the self-hosted runners share one Docker daemon: a job's cleanup (`docker rmi -f`) could delete the image another job had just built, so its smoke test failed with "pull access denied" (PR #588). The tag now carries the run id and attempt.
* **The task filter's page budget is measured where it can be (#535).** The test held the median of five wall-clock timings to 300 ms on the shared self-hosted runners and failed on every busy run (0.37–0.55 s there, 0.10–0.25 s on a quiet machine). Every pull request now checks the deterministic half, that the filter's SQL statements grow only by its id chunks and never per task, and holds the timing (best of five after a warm-up) to a 1 s guard; the nightly bench job holds it to the specification's 300 ms with `PERF_STRICT=1`.
* **The history check dates a task's close once.** `worked_before_dependency` read a task's *last* approval or person's note as its close, so a person's note on a task already done moved its close later and blamed the tasks that depended on it (e2e run 43752094404). A task now closes at the first approval, person's note or Manager agent acceptance after the last thing that reopened it: a deliverable, a high-risk hold, or an override.
* **Under the Git workflow a task is judged on the acceptance tests its branch holds (#329 retrospective).** A task's branch merges only the done tasks it depends on, so QA's tests for a sibling requirement are on the sibling's branch; the guard compared every acceptance test of the sprint, found the sibling's missing, called it an edit, copied it in and ran it, and a task was refuted (then blocked) on a test it could not hold, which then failed the integration. With a delivery on a task branch, `acceptance.evidence_for` now guards the test files of the task's lineage (itself and its done dependencies, transitively) and excuses criteria by the implementations merged into it; a sibling's test file is guarded only when it is on the branch's disk (its base holds it), and one that is not is listed in `acceptance.not_on_branch`, never restored, never an edit and never run for that task. The sprint's integration still merges every branch and runs the whole suite. Without the Git workflow nothing changes.
* **A `verified` task event names the verification it renders.** None did (0 of 37 in the self-hosting run), so the documentation pack's traceability matrix read "Latest verification: none recorded". The task worker's `verified` events now carry `verification_id` (the run's latest verification) and `payload.verification` (`{id, verdict}`), and the pack also reads an older `verified` event by its run.
* **`SECURITY.md` matches the code.** Reviewed on 2026-11-15 against the code and Microsoft SDL practices with the `sdl-program` skill (#522, part A): §8.3 describes the sandbox modes, `FABRIQUE_SANDBOX_REQUIRED`, the command policy, the image identity per run, the dependency cache with its quarantine (#514), the versioned daemon protocol and heartbeat (#517), and what remains open (no per-company command policy, console-assistant consultations on the host); §3 describes the HS256 JWT in a bearer header, bcrypt, hashed API tokens with roles and Owner > Manager > Viewer, and marks OIDC, PKCE, mTLS and short-lived tokens as planned (#512, phase 3); vulnerabilities are reported through GitHub private vulnerability reporting instead of a placeholder address; a new §15 says which versions get security fixes and how they ship; the frontend's token in `localStorage`, the images running as root and the CI scans that do not gate are written down as gaps.
* **The quality gate matched documentation keywords inside words.** It now matches them as whole words, trusts the files a delivery wrote, and "api" is no documentation keyword; a task that asks for a document stays one (#508; #509).
* **Orchestration health KPIs were structurally zero.** `GET /v1/analytics/orchestration_health` filtered `audit_log` on `details.role` / `details.company_id` and counted `ARCHITECT_CONSULTED:` comments, but the task pipeline never wrote either. The worker now records every Developer execution and QA review to `audit_log` (canonical role, company scope, `result_type`, proxy-reported token cost) via the new `services/orchestration_metrics.py` module, so *Avg Developer Tokens* and the QA *NEEDS WORK* rate read real data.
