and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Security

* **The daemon's sandbox floor reaches every command.** A `workspace.execute` without a `sandbox` is now read as a `host` request, so `FABRIQUE_SANDBOX_REQUIRED=container` (or `bwrap`) on the daemon's machine runs it in that mode (`forced_by_daemon`) or, when that mode cannot run, refuses it; never the host. Without the floor nothing changes, and the reply of a request that did not ask carries no `sandbox`. The console assistants send the company's sandbox with the new purpose `assistant` (the network as `DELIVERY_SANDBOX_NETWORK` sets it, the provider's key by name from `console_env`); one that cannot run there is skipped with the reason in the Glassroom (`skipped_sandbox`) and the task goes on. Protocol version 1, additive (#525).

* **CI supply chain and scans that can fail.** Every third-party action in every workflow is pinned by commit sha with its version in a comment, and `backend/tests/test_workflow_pinning.py` fails on a tag (the SLSA generator, which only runs from a `vX.Y.Z` tag, is the one exception); `security-scan.yml` replaces `safety check || true` with `pip-audit` over the backend's and the llm-proxy's lockfiles and `npm audit --omit=dev --audit-level=high` over the frontend's, failing on a known vulnerability unless `.github/pip-audit-ignore.txt` lists it with a reason and a review date that has not passed; gitleaks over a pull request's commits and Semgrep on the findings it adds now run on every pull request, beside the weekly full scans. The OpenTelemetry packages move from 1.45.1 to 1.45.2 (0.66b1 to 0.66b2) in both lockfiles for CVE-2026-126360 in `opentelemetry-api` (#522).

### Changed

* **No source file over 600 lines.** `llm-proxy/app.py` is split into modules with one job each (`routing.py`, `providers.py`, `quota.py`, `embedding.py`, with the listing in `catalogue.py` and tracing in `telemetry.py`), keeping `app.py` as the entry point, and `scripts/verify_infra.py` keeps its command line while its checks move to `scripts/infra_checks/`; the file-size baseline is empty (#519).
* **The backend in fourteen contexts with a checked dependency rule.** `backend/app/services` is divided into contexts, each a folder with one responsibility and a document; `scripts/check_architecture.py` holds the imports to `docs/architecture/contexts.json` in CI, the task worker is split into stages and the flat shims are retired (#469; #470 to #500, #502).
* **Versioned schema migrations.** Alembic owns the schema (`backend/alembic/`): the baseline migration creates what the models define and converges a database an older backend or `db/init-db/init.sql` created (the `ALTER TABLE` statements the startup used to apply by hand live there now, readable and reversible). The backend refuses to start on a database behind head, naming both versions; the container's entrypoint runs `alembic upgrade head` before the app, the e2e does too and then `alembic check` on Postgres, and CI checks on a SQLite file that the models and the migrations agree. `DB_AUTO_UPGRADE=true` runs the migrations at startup for a local database. How to write one: `CONTRIBUTING.md` §5.

### Added

* **A pinned browser image, a browser probe and full logs as evidence (#315).** `vscode-daemon/images/browser` builds the image QA's Playwright smoke tests run in: Node, Playwright 1.64.1 from a lockfile (`npm ci`, integrity-checked) and the Chrome Headless Shell it launches, downloaded and checked against a sha256 pinned per architecture (amd64 and arm64), the base pinned by digest, a non-root user and nothing downloaded at run time; `DELIVERY_BROWSER_IMAGE` makes the application check use it for a browser e2e command in container mode, recording the content ID that ran. Before a browser e2e command the daemon runs a probe where the command runs (`browser_probe`), and `e2e_run` says whether a browser was present from that observation. The install, the tests and the application check upload their whole output (up to 50 MiB a stream) to the JetStream object store `FABRIQUE_RUN_LOGS`; the backend reads each object back and records its size and the sha256 it computed (`full_log`), never a hash from the daemon; an older daemon is recorded as `full_log: {observed: false, reason}` (`DELIVERY_FULL_LOGS`, `FULL_LOG_RETENTION_DAYS`, `FULL_LOG_BUCKET_MAX_MB`; additive fields of protocol v1). Install state is kept per sandbox mode, so a company that moves from host to container installs again, and the application check's container mounts the dependency cache. The image's per-architecture checksums and build-time probe are adapted from AixleHQ/flow's `docker/base/Dockerfile` and `probe-browser.js` (Apache-2.0, `NOTICE`).
* **Single sign-on over OpenID Connect (#512, phase 3).** An Owner connects the company to its identity provider (`/company/sso`; `GET`/`PUT`/`DELETE /v1/companies/{id}/sso`, `POST …/sso/test`): issuer, client id, a client secret encrypted with `FERNET_SECRET_KEY` and never returned, allowed email domains, the role for new members (Viewer or Manager, never Owner) and auto-join. Google and Microsoft Entra ID are presets of the same connection. People sign in with "Sign in with SSO" on the login page (by work email or the company's SSO name): Authorization Code with PKCE, a one-time `state` bound to the browser, the ID token validated by the backend (signature against the provider's JWKS, `iss`, `aud`, expiry, nonce, `email_verified`), the account resolved by `(issuer, sub)` and the same access token the password login issues. An existing account is linked by email only when it belongs to that company alone, since any Owner can run a provider. The Owner can require SSO, which turns off password sign-in for the company's members once an Owner has signed in through the connection; the operator keeps a break-glass list (`SSO_BREAK_GLASS_EMAILS`). Every sign-in and change is audited. Threat model and design: `docs/design/SSO.md`; setup: `docs/OPERATIONS.md`, Single sign-on.
* **A checked dependency rule for the frontend.** `frontend/src` is divided into layers (foundation, services, lib, state, components, pages, app) in `docs/architecture/frontend.json`; `scripts/check_frontend_architecture.py` fails, in the frontend build, on an import from a layer above, a shipped module importing a test, or the network (`fetch`, `EventSource`, `WebSocket`, `XMLHttpRequest`, `axios`) outside the listed `services` modules, with an allowlist that may only shrink. The network rule mirrors the backend's "HTTP only in adapters" (#511), itself after AixleHQ/flow's design rules (design only). The query keys, a source's type and the specification badges moved down a layer, the architecture document's download into the API client and the Glassroom's stream into `services/api/stream.ts` (#519).
* **Security skills for Claude Code, based on Microsoft's SDL practices.** `.claude/skills/` holds `sdl-review` (a diff, PR or plan checked against SDL practices 2 to 9, with findings by severity, file:line, practice and fix), `threat-model` (a STRIDE threat model of a new design over this system's trust boundaries) and `sdl-program` (the quarterly or pre-release review of `SECURITY.md`, metrics, the incident plan and training); `sdl-review/reference.md` maps each practice to what the repository has and lacks. `.gitignore` now versions `.claude/skills/` while keeping the rest of `.claude/` out.
* **Versioned releases.** A pushed `vX.Y.Z` tag on `main` becomes a GitHub Release whose notes are this file's section for that version (a pre-release `vX.Y.Z-rc.N` shows `[Unreleased]`), and the five images are published to GHCR from the same tag; how to cut one is in `docs/OPERATIONS.md`, Releasing (#512).
* **The Verifier's grounded check.** A delivery that names a package no registry has, an exact version that does not exist or a project import that names no file is refuted; a call to a project function with arguments its signature does not take is a finding (#444; #503, #504).
* **A prompt budget.** Each section of the Developer's prompt is measured on the run's evidence, and `PROMPT_BUDGET` (or `PROMPT_BUDGET_<ROLE>`) drops whole sections, least needed first, from a prompt over it (#443; #505).
* **Related code in the Developer's prompt.** The daemon's parse of the repository answers which files the task's starting files use and are used by, and the prompt shows them with the recent runs that touched them (#438; #506).
* **Bench v3.** The scorecard records each prompt's weight (schema v3), the bench gains three reference specifications, and the first v3 scorecard (five specifications) is kept as the reference (#316; #507).
* **A sprint is delivered as one integrated branch.** With the Git workflow on, a sprint that closes is integrated on its own (a Manager can also ask, `POST /v1/sprints/{id}/integrate`): the workspace daemon starts `fabrique/sprint-<id>` from the company's base in a worktree and merges the done tasks' branches in dependency order with real git (`workspace.git.integrate`); the first merge git cannot make is aborted and reported with its conflicted files and hunks. The project's test command runs on the integrated worktree like a delivery's tests, in the company's sandbox. The result is kept and audited as an observation (`tests_passed`, `tests_failed`, `untested`, `conflict`); a conflict or a failing suite waits in the inbox. The suite runs in a worktree detached at the integrated commit, so a later integration never changes what was tested; a done task whose branch is missing makes the integration `incomplete`; an integration no daemon could take when the sprint closed is kept `pending` and retried (`INTEGRATION_RETRY_SECONDS`), one the daemon refused is an `error`; all three wait in the inbox. A Manager publishes the branch as one pull or merge request for the sprint, whose description carries every task's evidence with the producers' claims apart (`POST /v1/sprints/{id}/integration/publish`); `GET /v1/sprints/{id}/integration` shows the plan and the integrations. The description is built from each task's run and verification as recorded at integration, and a diff a producer only sent is listed as its claim. Migrations `0011` and `0012` (`vscode-daemon/sprint_integration.py`, `services/integration.py`, `services/integration_publish.py`).
* **Sandboxed execution: agent-written code runs isolated, and the evidence says where.** `DELIVERY_SANDBOX` (and a company's own, `GET`/`PUT /v1/companies/{id}/sandbox`) picks where the delivery test run and the Developer's test runs execute: `host` (as before), `container` (an ephemeral Docker or Podman container per run with the worktree mounted, network off, CPU/memory/process limits, every capability dropped, no privilege escalation) or `bwrap` (bubblewrap namespaces). A sandboxed run sees only the environment variables the company lists by name, with values from the daemon's machine. The daemon reports what it applied, never falls back to the host on its own, and can refuse the host for everything (`FABRIQUE_SANDBOX_REQUIRED`). The Verifier records the report as the `sandbox` check: a host run is a finding, never a refutation. Migration `0002` adds the company's fields; `0003` creates the baseline's indexes a table `init.sql` made was missing. The e2e runs in both modes in CI (`vscode-daemon/sandbox.py`, `services/sandbox.py`).

* **The roles that decide read official sources.** The PO, the Architect, SecOps and TechWriter get three research tools in the same bounded loop as the workspace and MCP tools: `research__fetch` (one page of documentation, release notes or a standard, as text, from a host on the company's list), `research__package` (a dependency's record at PyPI, npm, crates.io or the Go proxy) and `research__advisories` (its known vulnerabilities from OSV). The list of sources starts with the official documentation hosts, the registries and the advisory databases; a Manager adds hosts (`GET`/`PUT /v1/companies/{id}/research`), `RESEARCH_ALLOWED_HOSTS` adds some for a deployment, and nothing removes a default; a fetch carries no credential and follows a redirect only while it stays on the list. Every call is an observation the backend made (URL, when, status, sha256, bytes, whether the host was allowed), kept on an agent-drafted specification or architecture as `sources` (shown on its page) and on a task's run as the Verifier's `sources` check, which also names the dependencies a delivery's manifests declare without a registry lookup. The prompt of a research role says its knowledge has a cut-off date and that a fact it did not check at the source is a guess (`services/research_tools.py`, `research_registries.py`, `research_schemas.py`; `RESEARCH_TOOLS_ENABLED`, `RESEARCH_ROLES`, `RESEARCH_TOOL_ROUNDS`).
* **The Developer's tools speak like SWE-agent's interface, and it can edit with a check.** From SWE-agent's agent-computer interface (MIT, issue #359): `workspace__read` shows a window of 100 numbered lines headed `lines X–Y of N` and says which `start_line` pages on; a search with more matches than it shows answers how many and in which files and asks to refine, instead of cutting silently; `workspace__find_file` finds files by name or glob the same way; an empty answer says it is empty ("the command finished with no output"). `workspace__edit` replaces a line range or one SEARCH/REPLACE block of an existing file, applied by the daemon only if the file still parses (Python, JSON, `node --check` for JavaScript), else refused with the error and the file untouched; each applied edit is an observation with the sha256 before and after. The edits are a working copy for the task's tool loop: when it ends the daemon puts the originals back and the worker delivers the edited files like any other, so the diff, the Git commit and the Verifier see them, and an edit never delivered never stays on disk. Offered only in the task's worktree or a project without the Git workflow (`vscode-daemon/workspace_edit.py`, `services/workspace_edits.py`, `services/developer_tool_replies.py`).
* **A Developer with tools: it reads the project before it writes.** The roles that deliver files (Developer, QA) get four workspace tools served by the daemon on the project as it is on disk, beside the company's MCP tools and in the same bounded loop: `workspace__list`, `workspace__read`, `workspace__search` and, with `DELIVERY_TESTS_ENABLED`, `workspace__run_tests` (the project's test command, or a narrower one on the same runner; never an arbitrary command). Each task's prompt opens with a map of the repository, and the model may call the tools for `DEVELOPER_TOOL_ROUNDS` rounds before it delivers (`DEVELOPER_TOOLS_ENABLED`, on by default). Every call is an observation on the run's evidence (`tools_used`); a read also records the file's sha256 and size as the daemon read them, and the Verifier's new `context_read` check says which of the files the delivery modified were read first and which were not. A file modified without being read raises the risk tier, so the delivery waits for a person. What the model says it learned is a claim, and its own account of a test run is never evidence. The tools never open a file that may hold secrets or a symlink out of the project, redact a secret-looking line, and a search runs in a child process stopped at its deadline (`services/developer_tools.py`, `services/context_read.py`, `vscode-daemon/workspace_read.py`).
* **Quality standards every project is held to.** A fixed catalogue by discipline (architecture, development, QA, security, evidence and audit, documentation, operations, product; `services/standards.py`, `docs/STANDARDS.md`) that no model, request or procedure edits. It goes into every prompt by role (the PO's draft and plan, the Architect's design, each task, QA's review), binds before any task-specific instruction, and a company procedure adds to it, never relaxes it. Where a standard can be checked without a model, it is: the Verifier records a `standards` check over the files a deliverable declares (a secret-looking value refutes the delivery and sends it back; code without a test, a `TODO` left behind and an unpinned dependency are findings the reviewer sees), and the specification check warns on a quality area (security, performance, reliability, accessibility) left out. `GET /v1/standards` serves the catalogue and the Procedures page shows it with what is checked.
* **An acceptance test per criterion.** A sprint planned from a specification gets, before its implementation tasks, one test-writing task per requirement for QA: one test per acceptance criterion, named after its id (`test_req_1_2_…`), delivered through the daemon like any file; each implementation task depends on the test tasks of the criteria it covers and its prompt names the tests to make pass. With `DELIVERY_TESTS_ENABLED`, the runner's per-test lines are read back into criterion ids and the Verifier records them (`criteria_tests`): QA's tests are expected to fail before their implementation, an implementation that leaves its criterion failing is sent back, and one that rewrites an acceptance test is refuted, the test restored from QA's delivery before the run (the daemon reports the files' sha256 on disk, `workspace.hash`). The specification shows, per criterion, **verified** only when its test passed in an observed run, the pull request's description says how many criteria are verified, and the independent history check refuses a criterion verified without an observed test run.
* **Tasks in the order they depend on.** The PO's plan says which tasks must be done before another starts; `POST /v1/start_sprint` keeps it (`depends_on`, checked: an unknown task, a task depending on itself or a cycle is refused). The worker follows that order instead of the queue's: a task waits in *todo*, with a note saying for what, until every task it depends on is done, and is queued the moment the last one closes; tasks with nothing between them run in parallel as before. A task waiting on one a person must act on is blocked with the reason, so the sprint closes around it and the inbox shows what the person's decision unblocks; when that dependency gets done after all, the task is released. The board shows `depends_on` and `waiting_for` per task, a carried task keeps a dependency carried with it, and the independent history check refuses a task that delivered before every task it depends on had closed. A hold is the System's last word on the task (a comment anyone appends does not hide it), a chain of holds follows its root (a task behind one is released when the root is back in work, and held again when it is not), a sprint reconciles its holds before it counts as settled, and with the Git workflow the daemon merges the branches of the done tasks a task depends on into its worktree before writing (`merge` in the delivery, `merged` in its report).
* **The architecture: how the specification is built, as data.** Once a specification is approved, a Manager asks the Architect for a design: modules with their responsibility, their place in the repository, what they depend on and which requirements they cover; interfaces with a contract a test can hold them to; decisions (ADRs) with their consequences; conventions; and the questions the Architect could not decide. The ids (`MOD-1`, `IF-1`, `ADR-1`) are assigned by the backend, which maps the draft's names onto them. A deterministic check blocks approval on an unknown module or requirement, a dependency cycle, a decision without its decision or an unanswered question, and warns on a requirement no module covers. A person answers, asks for a revision, edits in a structured form, approves; **Write to the repository** sends `docs/ARCHITECTURE.md` through the workspace daemon and keeps the sha256 it read back. The PO plans along the modules, and each task's prompt and QA's review carry the modules its requirements map to, with their interfaces, and the decisions and conventions every task follows (`/v1/architectures`).
* **The specification: what the agents build from, as data.** A Manager gives the PO a brief and gets a draft: numbered requirements (`REQ-1`), each with acceptance criteria written as given / when / then (`REQ-1.2`), quality attributes with a number to measure them by (`NFR-1`), constraints, and the questions the PO could not decide. The ids are assigned by the backend, never by the model. A deterministic check says what blocks approval (a requirement without a criterion, a criterion with an empty step, a target without a number, an unanswered question) and what only warns ("fast", "easy", "rápido" without a number). A person answers the questions, asks the PO for a revision (the answers go into its prompt), edits in a structured form, and approves; an approved version is never edited, a revision is a new draft that supersedes it. Planning from an approved specification has the PO split it into tasks that name the criteria they cover, lists the criteria no task covers, and the sprint keeps that: each task's prompt and QA's review carry only the requirements it covers, and the specification shows, per criterion, whether a task got done, is blocked, is planned or does not exist (`/v1/specifications`, `POST /v1/plan_sprint` and `POST /v1/start_sprint` with `specification_id`; the Specifications page and the Plan a sprint form).
* **Comments from the pull or merge request, back in the run.** A Manager presses **Bring comments** on a published run: the workspace daemon reads the request's line comments, reviews and conversation with the person's `gh` or `glab` login (`workspace.git.reviews`), and each one appears on its line in Files changed, marked as written on GitHub or GitLab, with its link and, for a review, its state. Reading again never duplicates; the next review submitted here carries them to the agent like any comment, naming who wrote each and where (`POST /v1/agent_runs/{id}/publications/{pid}/sync`).
* **Publish a task's branch as a pull or merge request.** From a run's Files changed, a Manager publishes `fabrique/task-<id>`: the workspace daemon pushes it to `origin` with the person's own Git credentials and opens a draft pull request (`gh`) or merge request (`glab`), or answers with the page that opens one (`workspace.git.publish`). The description carries the evidence the Verifier observed, the producer's claims apart and a `Fabrique-Run:` trailer; each publication is kept and audited (`POST /v1/agent_runs/{id}/publish`, `GET .../publications`).
* **Git branch per task.** With the company's Git workflow on (`PUT /v1/companies/{id}/git`, the Board's toggle), each task's deliveries are commits on `fabrique/task-<id>`, in a worktree under the repository's git directory, from the base the company names or the checked-out commit; the person's checkout, index and branch are never touched. The daemon reports the branch, commit and parent as git said them (`vscode-daemon/git_workspace.py`), kept on the evidence; delivery tests run in the worktree; Files changed names the commit.
* **Review comments and decisions, as on a pull request.** A Manager comments on a changed line (new or old side), resolves comments, and submits a review: Comment, Approve or Request changes, carrying the open comments. On a task the agents delivered, Request changes sends a task blocked for a person back to work with the comments, file by line, as its `NEEDS WORK:` feedback, and Approve accepts a delivery QA approved that waits for a person; anything else is refused with the reason, since QA and the Verifier decide. On another producer's run the review records the approval or rejection. Audited, never evidence (`/v1/agent_runs/{id}/comments`, `/v1/agent_runs/{id}/reviews`).
* **Review a run like a pull request.** The run page has a **Files changed** tab laid out as GitHub and GitLab show a pull request: files with additions and deletions, hunks with old and new line numbers, **Viewed** to fold a file. For a delivered task the diff is what the workspace daemon observed on disk (the bytes before the write against the bytes it read back, `vscode-daemon/file_diff.py`); for an ingested pull request, GitHub's diff. Files only declared by the producer are listed apart. `GET /v1/agent_runs/{id}/changes` serves it.
* **You decide when the agents work.** The New company wizard can leave Sprint 0 planned (always at autonomy level 1) and the Sprint page starts it. Pause now stops dispatch, QA reviews and retries, not only new tasks, and Stop cancels a sprint for good with no follow-up. When a provider refuses a call for lack of credit, the sprint pauses itself with the reason and the task waits to run again, instead of blocking every task and looping into follow-up sprints. The autonomy level can be changed after creation (`PUT /v1/companies/{id}/autonomy`), and level 1 now does what it promises: every approved task waits for a person to accept it.
* **MCP tools for the agents.** A Manager gives a company MCP servers with the standard `mcpServers` map (`POST /v1/mcp/servers`: stdio by `command`, streamable HTTP or SSE by `url`, secrets in `env`/`headers`, optional `roles`); secrets are stored Fernet-encrypted and the API lists only their names. The task worker offers the servers' tools to the model (`<server>__<tool>`, through the proxy to every provider, Gemini included) and runs a bounded loop (`MCP_MAX_TOOL_ROUNDS`, then one request without tools). Every call is recorded as an observation the backend made — server, tool, arguments, error, duration, sha256 of the result — on the Verifier's evidence (`tools_used`), apart from the model's claims; results are masked for the server's secrets and cut at `MCP_RESULT_MAX_CHARS`; a tool without a read-only annotation raises the delivery's risk tier. `GET /v1/mcp/servers/{id}/tools` connects and lists what a server advertises. Design taken from OpenHands' `software-agent-sdk` (`openhands/sdk/mcp`), on the official `mcp` package.
* **Nebius Token Factory as a first-class model provider.** The LLM proxy routes `nvidia/`, `meta-llama/`, `mistralai/`, `deepseek-ai/`, `qwen/` and `google/` model ids to Token Factory's OpenAI-compatible API, fetches the catalogue at startup and hourly, and lists what it found on `GET /v1/models`. `NEBIUS_API_KEY` enables it; `NEBIUS_PROXY_URL` retargets it at your own Serverless Endpoint. This is what serves the NVIDIA open models (Nemotron).
* **Per-role Nemotron opt-in.** `ModelFactory.model_for_role()` honours `NEMOTRON_ROLES` with `NEMOTRON_MODEL` / `_STRATEGIC` / `_FAST`, so agent roles can run on Nemotron. Unset, the Qwen/DeepSeek defaults are untouched.
* **Documentation overhaul.** README.md, README.es.md, CONTRIBUTING.md, and CLAUDE.md restructured following industry best practices. Added SECURITY.md, CODE_OF_CONDUCT.md, and GitHub issue/PR templates.
* **Architect consultation step.** Before a Developer starts a high-priority, design-sensitive, or QA-reworked task, the worker asks the company's Architect agent for a short technical brief, appends it to the card as an `ARCHITECT_CONSULTED:` comment (feeding the *Architect Consult Frequency* KPI), streams it to the Glassroom, and injects it into the Developer prompt. At most one consultation per implementation attempt. Disable with `ARCHITECT_CONSULT_ENABLED=false`.
* Backend tests for the KPI emitters and their contract with the analytics queries (`backend/tests/test_orchestration_metrics.py`).
* **Competition-ready documentation.** Repo description and topics, evidence-page screenshots, a `docs/README.md` index and a `docs/HACKATHON.md` entry page for the Nebius × NVIDIA Global AI Hackathon, plus a Roadmap and Responsible-use section in the README.

### Changed

* **QA reviews every file, and the prompt is cache-friendly.** The deliverable QA reviews is a digest (`services/review_digest.py`): every file the delivery wrote with its lines and bytes, and an excerpt of each sharing a fixed size, each cut saying how many lines it left out. The board kept 4000 characters and QA read the first 3000, so a delivery of three files reached QA as one, and QA's request for the "missing" files regenerated all of them. The Developer prompt now runs from what is the same for every task of a sprint (output format, procedures, lessons) to what changes between attempts (Architect brief, review feedback, last), so the providers' prefix cache bills the shared start at the cached rate.
* **Fewer tokens per task, with the evidence design unchanged.** A send-back by the Quality gate or the Verifier no longer earns a second Architect brief (it asked for the same deliverable); a rework quotes the console assistants' first advice instead of running the CLIs again; a review answer without `APPROVED:`/`NEEDS WORK:` is asked again with the format named; a Developer answer the model cut at its length limit is sent back as such (`finish_reason: length`, which the proxy now reports for Gemini too) rather than as "deliver the complete result again". The proxy client retries only a request that never reached the proxy (an error the proxy answered already cost its upstream call and fallbacks), waits as long as the proxy's own budget (`LLM_UPSTREAM_TIMEOUT_SECONDS` + 10 s; the planner's 12 s and the triage's 45 s discarded answers already billed), and caps the fixed-form answers (`max_tokens`: QA review, Architect brief, ScrumMaster, planner, Support and Reviewer agents). The Developer's deliverable keeps no cap, since every file goes in full.

### Fixed

* **`SECURITY.md` matches the code.** Reviewed on 2026-11-15 against the code and Microsoft SDL practices with the `sdl-program` skill (#522, part A): §8.3 describes the sandbox modes, `FABRIQUE_SANDBOX_REQUIRED`, the command policy, the image identity per run, the dependency cache with its quarantine (#514), the versioned daemon protocol and heartbeat (#517), and what remains open (no per-company command policy, console-assistant consultations on the host); §3 describes the HS256 JWT in a bearer header, bcrypt, hashed API tokens with roles and Owner > Manager > Viewer, and marks OIDC, PKCE, mTLS and short-lived tokens as planned (#512, phase 3); vulnerabilities are reported through GitHub private vulnerability reporting instead of a placeholder address; a new §15 says which versions get security fixes and how they ship; the frontend's token in `localStorage`, the images running as root and the CI scans that do not gate are written down as gaps.
* **The quality gate matched documentation keywords inside words.** It now matches them as whole words, trusts the files a delivery wrote, and "api" is no documentation keyword; a task that asks for a document stays one (#508; #509).
* **Orchestration health KPIs were structurally zero.** `GET /v1/analytics/orchestration_health` filtered `audit_log` on `details.role` / `details.company_id` and counted `ARCHITECT_CONSULTED:` comments, but the task pipeline never wrote either. The worker now records every Developer execution and QA review to `audit_log` (canonical role, company scope, `result_type`, proxy-reported token cost) via the new `services/orchestration_metrics.py` module, so *Avg Developer Tokens* and the QA *NEEDS WORK* rate read real data.

There is no tagged release yet: the project has not been versioned since the
original scaffold, and `main` is the web product. The changes above are the
accumulated work between the initial scaffold and the current head. Releases
are `vX.Y.Z` tags on `main`; how one is cut is in
[docs/OPERATIONS.md](docs/OPERATIONS.md#releasing). Every pull request adds
its line under `[Unreleased]`.
